##### 요청 한 번에 실제로 보내는 것 — 프롬프트 캐싱

요청을 보낼 때 실제로 전달되는 것은 다음과 같이 구성된다.

1. 지침
2. 읽은 파일과 명령 결과
3. 지금까지의 대화 전체 — **매번 똑같이 다시 붙는 부분(캐시 대상)**
4. 마지막에 내가 친 질문 한 줄 — **이것만 새로 추가되는 부분**

**캐시가 깨질 때**
1~3번 중 앞쪽 내용이 바뀌면, **바뀐 지점부터 끝까지 전부 다시 계산**해야 한다.

- `/compact`: 자동 압축
- `/clear`, `/resume`: 새 세션 시작
- 한동안 자리를 비움: 캐시 만료

> 💡 캐시 수명은 마지막 사용으로부터 **5분**이며, **클로드 코드는 1시간**까지 유지된다.

##### [Rules] — 항상 지켜야 하는 규칙

| 도구 | 파일명 |
|---|---|
| Claude Code | `CLAUDE.md` |
| Codex | `AGENTS.md` |

**룰을 잘 작성하는 방법** — 스스로에게 이렇게 물어본다: **"이 줄을 지우면 에이전트가 실수하는가?"**

**넣는다**
- 코드만 봐서는 알 수 없는 것 (예: 작업 브랜치는 `develop`에서 딴다)
- 기본값과 다른 우리만의 방식 (커밋 규칙, 금지 구역)
- 자주 걸리는 함정 (예: 로컬 DB는 8433 포트다)

**뺀다**
- 코드를 읽으면 알 수 있는 것 (파일별 구조 설명)
- 모델이 이미 아는 상식 (예: "클린 코드로 짜라")
- 자주 바뀌는 정보 (이번 주 작업 목록)

**몇 줄이 적당한가?** — 기준은 줄 수가 아니라 **증상**이다.

- 룰을 적어놨는데도 자꾸 어긴다 → **너무 길다는 신호. 쳐낸다.**
- 안 시켜도 이미 잘한다 → **그 줄은 지운다.**
- 어기면 절대 안 되는 것이다 → **문장이 아니라 Hook으로 강제한다.**

##### [Skills] — 반복 가능한 작업 절차와 참고 지식

필요할 때 불러와서 재사용하는 **"작업 설명서"**다. 폴더 하나로 저장해두고, 필요할 때 이름으로 불러 쓴다.

**예시 — 주간 보고 Skill (`/weekly-report`)**
1. 이번 주 커밋과 작업 기록을 모은다.
2. 팀 양식에 맞춰 초안을 쓴다.
3. 빠진 항목이 없는지 확인한다.

**Skill의 기본 구조**
- 폴더 이름이 곧 스킬 이름이다.
- `SKILL.md`가 **유일한 필수 파일**이며, 작업 방법은 여기에 적는다.
- 나머지(참고자료, 스크립트, 양식)는 전부 옵션이며, 필요한 것만 넣는다.

**`SKILL.md`의 frontmatter — `description`**
무엇을 하는지, 언제 쓰는지를 짧게 설명한다. 본문은 스킬이 호출된 뒤에야 읽히며, **호출할지 말지는 `description`만 보고 정해진다** — 그래서 스킬에서 가장 공들여야 할 부분이다.

**Skill이 호출되는 두 가지 방식**

| 방식 | 설명 |
|---|---|
| 수동 호출 | 사용자가 이름으로 직접 부른다 |
| 자동 호출 | 에이전트가 설치된 Skill들의 `description`을 보고 상황에 맞게 스스로 고른다 |

> 💡 자동 호출은 검색 엔진이 아니라 **독해**다. 키워드 매칭이 아니라, 에이전트가 `description` 문장을 읽고 판단한다. 비슷한 `description`을 가진 스킬이 두 개 있으면 엉뚱한 쪽이 불려올 수도 있다.

**좋은 Skill의 조건**
- **잘 불린다**: `description`만 읽어도 언제 쓸지 알 수 있다.
- **잘 끝난다**: 하나만 한다.

##### [Hooks] — 이벤트마다 반드시 실행할 자동화

정해진 순간이 오면, 정해둔 명령이 **에이전트의 판단을 거치지 않고** 자동으로 실행된다.

**작성 구조와 동작 방식**
- `settings.json`에 등록한다.
- **동작**: 이벤트 발생 → 등록된 명령이 실행됨 → 명령이 남긴 종료 코드가 판정이 됨 (`0 = 통과`, `2 = 차단`)

##### [Agents] — 하위 에이전트

별도의 역할, 컨텍스트, 모델, 도구 범위를 가지고 **특정 하위 문제를 맡는 추상화 요소**다.

**활용처**
- 큰 작업에서 메인 컨텍스트 오염 방지
- 서로 다른 도구 권한을 가진 전문 역할 구성

**Skill vs Agent**

| 구분 | 용도 |
|---|---|
| Skill | 방법을 아는 것 |
| Agent | 일손을 나누는 것 |

- 절차와 지식만 필요하다 → **Skill**
- 컨텍스트 격리, 병렬 실행, 권한 분리가 필요하다 → **Agent**

> 💡 둘은 대체재가 아니다. **Agent가 Skill을 불러와 사용하기도 한다.**

##### [MCP] — 외부 시스템 연결

외부 시스템의 데이터와 기능을 **표준 인터페이스**로 연결한다. 에이전트와 외부 시스템 사이에서 도구와 데이터를 제공하는 연결고리다.

```
Claude Code / Codex → MCP Server → 외부 시스템
```

**활용처**
- GitHub 이슈, PR, Actions 조회와 변경
- 브라우저 조작
- DB, Redis 같은 Storage 조회 및 수정
- 노션, 슬랙, 구글 등 다양한 서비스가 이미 각자의 MCP를 제공하고 있다

---

##### [Plugins] — 여러 자원을 하나로 묶은 패키지

Skill, Agent, Hook, MCP 설정과 관련 여러 자원을 **하나의 설치·업데이트 단위**로 묶은 패키지다.

**공개 사례 — Superpowers**
계획, 테스트 주도 개발(TDD), 체계적 디버깅, 코드 리뷰 같은 개발 방법을 14개 Skill로 구성한 공개 Plugin이다.

> ⚠️ 그대로 주력으로 계속 쓰는 것은 추천하지 않는다. 범용으로 설계된 **강제 워크플로우**라서, 내 팀·내 업무의 맥락과 맞지 않는 단계가 반드시 생긴다. 하지만 **꼭 설치해서 써보고, Skill과 Plugin의 구조를 직접 뜯어보길 권한다** — 워크플로우 Skill들의 교과서 같은 존재다.

##### 에이전트 환경을 잘 구성하는 방법

- **AI가 찾아갈 수 있게 프로젝트 구조를 나눈다.** 목적이 분명한 폴더가 있으면 AI가 어디에 무엇을 넣을지 스스로 찾아간다.
- 구조가 잡혀 있으면 시간이 갈수록 AI 산출물의 품질이 올라간다. **구조가 없으면 시간이 갈수록 품질이 떨어진다.**
- **레이어별 책임 분리**: 도메인/서비스/인프라 분리, 의존성 방향의 일관성, "새 기능 = 기존 패턴 복제"가 가능한 구조.

##### 에이전트 엔지니어링 기법의 변화

| 단계 | 정의 |
|---|---|
| **Prompt Engineering** | 질문 하나를 효율적으로 잘 던지기 위한 방법 |
| **Context Engineering** | AI가 알아야 할 배경(맥락)을 챙겨주는 단계 |
| **Harness Engineering** | AI가 효율적으로 일할 수 있는 전체적인 환경을 구축해주는 단계 |
| **Loop Engineering** | 내가 안 시켜도 스스로 돌아가게 만드는 기술 |

**하네스에서 자주 쓰는 용어**

| 용어 | 의미 |
|---|---|
| OS | 모든 작업 밑에 항상 깔리는 기본 지침 레이어 |
| KB | 팀의 문서·지식을 모아둔 창고 |
| 샌드박스 | 실수해도 밖에 피해가 없는 격리된 작업 공간 |
| 가드레일 | 위험한 행동을 막는 선 |
| 스캐폴딩 | (기본 골격/뼈대를 미리 갖춰두는 것) |
| HITL | Human-in-the-loop, 사람이 루프 안에서 검토·개입 |
| RAG | 외부 지식을 검색해 답변에 반영하는 방식 |
| 컨텍스트 윈도우 | 모델이 한 번에 참조할 수 있는 정보의 범위 |

> 💡 이 엔지니어링 기법들은 **서로의 대체재가 아니라, 서로가 서로의 재료**다.

##### 계획과 실행의 분리

**무엇을 할지 먼저 정하고, 그다음 실행한다.** 작성과 실행을 분리하면 **작성 → 검수의 사이클이 빨라지고, 토큰 비용도 절약**된다.

> 💡 사람은 자기 전제를 다 적지 못한다. 그래서 계획 단계에서 **에이전트가 되묻게** 만든다 — "지금 이해한 내용을 정리해서 보여달라", "모호한 지점을 질문해서 확인해달라" 같은 방식으로.

**계획을 다루는 수단**

| 수단 | 설명 |
|---|---|
| `/plan` | 코드 변경 전에 계획을 세운다 |
| `brainstorming` | 모호한 요구사항을 질문과 답변으로 구체화하면서 계획 파일로 작성한다 |
| `executing-plans` | 승인된 복잡한 계획을 단계별로 실행한다 |

##### 어디까지 정해줄 것인가?

**무엇은 정하되, 어떻게는 신중하게.**

정할 것:
- 해야 할 것
- 하지 말아야 할 것
- 업무에 필요한 맥락 제공

> ⚠️ 하지만 **"어떻게 할 것인가"를 정의하는 것은 신중해야 한다.** 인간이 정의하는 HOW는 대부분 에이전트의 자율성을 침해한다. 사람이 정의한 실행 방법은 에이전트에게 도움이 되기보다, 오히려 선택지를 제약하는 경우가 대부분이다 — **모델이 너무 빠르게 진화하기 때문이다.**

> 💡 **하네스는 모델이 진화함에 따라 점점 축소된다.** 가드레일, 프롬프트 팁, 모델의 한계를 보완하려던 우회 장치들도 결국 같은 운명을 맞는다.

> 💡 왜 필요한가? 현업에서는 세션을 동시에 3~5개, 많게는 5~8개까지 굴린다. **어떤 세션이 어디까지 작업했는지, 어떤 작업이 끝나지 않은 채 멈춰 있는지**를 한눈에 볼 수 있어야 한다.

**자주 사용하는 Workflow Skills**

**Plugin 운영 — `issue-goal-loop`**
서비스에 이슈가 있을 때 쓰는 스킬이다. 이슈 내용을 입력하면 **재현 가능한 API를 확보**하고, 원인 가설과 수정을 거쳐 테스트 실행으로 검증한다.

> 💡 **재현 계약**: 재현에 성공하면 명령, 필요 데이터, 실패 출력, 기대 출력을 기록해두고, **수정할 때마다 이 계약을 그대로 재실행**해서 검증한다.

##### 현업 활용 사례 — 카카오톡 선물하기

**Atlas**
선물하기 MSA 서비스와 외부 MSA 서비스를 합쳐 **총 100여 개의 코드 레포를 그래프로 연결한 지식베이스**다. 호스트, 서비스, 레포를 호출 간선으로 그래프화해서, 마치 하나의 코드 레포를 탐색하듯 동작하게 만드는 프로젝트다.

> 실사례: "선물하기 메뉴 목록은 어떻게 만들어지지? 메뉴 타입 값은 어떤 종류가 있지?" → "A 서비스 → B → C 호출로 만들어지고, 메뉴 타입은 C 서비스에서 a, b, c, d 네 종류로 만들어집니다." **API 스펙을 외부 조직에 문의하지 않고 바로 얻을 수 있다.**

**Boost MCP**
사내 시스템 22종을 **에이전트의 도구 하나로** 연결한다. 사내 메신저, 챗봇, 알림, 메일, 아지트, Jira, 위키, 전자결재, 조직도, 계산 등과 연동된다.

> 사용 사례: "조금 전 메신저에서 오간 내용 중 내가 참고해야 하는 것들 요약해줘", "DB 신규 발급을 위해 필요한 업무 요청 절차 찾아줘", "2시에 비어 있는 회의실 예약해줘"

**boost-kb**
선물하기 서비스와 관련된 모든 지식을 하나의 저장소로 모은다. 위키, 드라이브, 아지트, 메신저, 코드 저장소에 흩어져 있던 조직 지식을 하나의 원격 지식 저장소로 모아, **사람과 에이전트가 함께 쓰는 MCP**다.

**Viking**
만든 것을 접속 가능한 서비스로 올려주는 플랫폼이다. **프롬프트 하나면 아이디어가 접속 가능한 서비스가 된다** (프롬프트 → 코딩 → 검증 → 빌드 → 배포 → 접속 가능한 서비스). 이를 통해 바이브 코딩이 가능해지면서, 아이디어를 가진 비개발 직군도 바이브 코딩에 참여할 수 있게 되어 전사적으로 큰 호응을 얻고 있다.

**Troubleshooter**
장애 알림을 받아 원인을 분석하고 코드 수정을 제안한다.

> 💡 왜 필요한가? 장애가 발생하면 로그, 메트릭, 코드 같은 여러 맥락을 에이전트가 알지 못하기 때문에, 사람이 하나하나 에이전트에게 전달해야 한다 — 느리고 반복적이며 사람마다 편차가 있다. Troubleshooter는 흩어진 관측 도구와 인프라 시스템을 연결해 이 문제를 해결한다.

**제공하는 도구 (11군)**: Prometheus, O11y, Kubernetes, DB, Redis, MongoDB, RMQ, Kafka 등

```
Webhook으로 장애 신호 수신 → 서버 에이전트 → MCP로 장애 분석
→ 진단 리포트 → 코드 수정 PR
```

사람이 하는 일은 **리포트 검토와 PR 승인**뿐이다.

##### Q&A

**AI의 답과 코드를 어떻게 믿고 다루나?**

> ⚠️ **AI 코드를 전부 보려고 노력해서는 안 된다.** 실무는 멀티태스킹이다 — 모든 코드를 이해하려 들면 내가 병목이 된다. **검증 대상은 코드가 아니라 워크플로우다.** "코드가 정확한지 눈으로 확인"하는 게 아니라, **"코드가 올바른 방향으로 짜일 수밖에 없는 워크플로우가 있는가"**를 검증해야 한다. 어디까지 맡겨도 되는지는 서비스의 중요도에 따라 다르다 — 정말 중요하고 민감한 서비스라면 코드를 하나하나 눈으로 보는 것이 필요할 수 있다.

**컨텍스트가 길어지면 잊어버린다**

> 💡 Plan 모드보다 **계획 파일을 적극적으로** 쓸 것을 권한다. 컨텍스트 관련 불안은 모델이 발전하면서 점점 줄어들고 있다.

**토큰을 절약할 수 없나?**

> ⚠️ 품질을 유지하면서 토큰을 획기적으로 줄일 수는 없다. **토큰 비용은 품질과 비례한다.** 토큰 절약을 위한 오픈소스 도구들도 그렇게 큰 영향을 주지는 못한다.

### 🗨️ 오늘의 회고

- 오늘은 지금까지와 완전히 다른 결의 특강이었다. 인프라·백엔드 지식이 아니라, **"AI 에이전트와 함께 일하는 환경을 어떻게 설계할 것인가"**라는 새로운 층위의 엔지니어링을 처음 체계적으로 접했다. Prompt Engineering → Context Engineering → Harness Engineering → Loop Engineering으로 이어지는 흐름이, 지금까지 내가 Claude나 다른 AI 도구를 그냥 "질문 잘 던지는 도구"로만 써왔다는 걸 깨닫게 해줬다.
- **Rule / Skill / Hook / Agent / MCP / Plugin**을 "언제 무엇을 쓰나"라는 표 하나로 정리해준 부분이 가장 실용적이었다. 지금까지는 이 개념들을 각각 따로 알고 있었는데, "매번 지켜야 하는 규칙 → Rule", "반복 작업 → Skill", "무조건 실행돼야 함 → Hook", "역할 분리가 필요 → Agent", "외부 시스템 연결 → MCP", "이것들을 묶어서 공유 → Plugin"이라는 기준으로 나누니 언제 어떤 도구를 골라야 할지 훨씬 명확해졌다.
- **"이 줄을 지우면 에이전트가 실수하는가?"**라는 룰 작성 기준이 특히 인상 깊었다. 그동안 CLAUDE.md 같은 지침 파일을 작성할 때 막연히 "많이 적어두면 좋겠지"라고 생각했는데, 오히려 "안 시켜도 이미 잘하는 것"이나 "코드를 읽으면 알 수 있는 것"은 과감히 빼야 한다는 원칙을 들으니, 지침도 결국 코드처럼 군더더기 없이 다듬어야 한다는 걸 깨달았다.
- Skill의 `description`이 "검색 엔진이 아니라 독해"라는 설명도 새로운 관점이었다. 지금까지는 키워드 매칭처럼 동작할 거라고 막연히 생각했는데, 실제로는 에이전트가 `description` 문장을 읽고 판단한다는 걸 알고 나니, Skill을 만들 때 description 작성에 왜 그렇게 공을 들여야 하는지 이해가 됐다.
- **"인간의 HOW는 대부분 자율성을 침해한다", "하네스는 모델이 진화할수록 축소된다"**는 문장들은 지금까지 내가 AI를 쓸 때 가졌던 태도를 다시 돌아보게 만들었다. 세세하게 방법까지 지시하려 했던 습관이, 사실은 더 나은 결과를 방해하고 있었을 수도 있겠다는 생각이 들었다. 대신 "무엇을, 왜"는 명확히 주고 "어떻게"는 신중하게 맡겨야 한다는 균형점을 계속 의식해봐야겠다.
- 카카오 선물하기 팀의 실제 사례(Atlas, Boost MCP, boost-kb, Viking, Troubleshooter)를 보면서, 오늘 배운 개념들이 실제로 대규모 조직에서 어떻게 조합되어 쓰이는지 감을 잡을 수 있었다. 특히 Troubleshooter처럼 "장애 알림 → 자동 분석 → PR 제안 → 사람은 승인만"으로 이어지는 워크플로우는, 어제까지 배운 Resilience·캐시·부하테스트 같은 인프라 지식이 결국 "사람이 대응하는 영역"에서 "에이전트가 1차 대응하는 영역"으로 옮겨가고 있다는 걸 실감하게 해줬다.
- 오늘 배운 내용은 당장 코드로 옮길 수 있는 지식이라기보다, **앞으로 개발자로 일할 때 AI와 협업하는 방식 자체를 바꿔줄 기초 체력**에 가깝다는 생각이 든다. 지금 진행 중인 개인 프로젝트에도 간단한 `CLAUDE.md` 룰 파일 정도는 작성해보면서, 오늘 배운 "넣는다/뺀다" 기준을 직접 적용해봐야겠다.
