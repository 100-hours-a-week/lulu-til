## 1. 목표와 원칙

메모에 처음부터 명시했던 원칙:

> "오로지 부하테스트가 목적이기 때문에 multi-az, 높은 보안성, 무중단 배포 등은 고려하지 않는다."

이 원칙 덕분에 아키텍처 결정이 훨씬 단순해졌다. 이중화·고가용성에 쓸 시간과 인스턴스 슬롯을 전부 "얼마나 버티는가"를 측정하고 개선하는 데 쓸 수 있었다.

평가 기준으로 삼은 지표:
- Max RPS
- p95 Latency, p99 Latency
- Error Rate
- Break Point (최대 견딜 수 있는 VU)
- Completed(시나리오 완료율)

## 2. 아키텍처 결정과 그 이유

### 왜 EC2 직접 설치인가

MongoDB/Redis 둘 다 **EC2 직접 설치 방식**을 선택했다. 이유:
- 대회 규정상 AWS Managed Service(RDS, ElastiCache, DocumentDB 등) 사용 불가
- 높은 TPS와 대규모 데이터 처리가 필요한 운영 DB 성격상 I/O 레이턴시를 최대한 줄여야 함
- Replica Set 구성 시 노드 단위를 단일 EC2 인스턴스로 전담시켜 안정성 확보

### S3 (파일 업로드) — 거의 순수 이득

> "StoragePort 인터페이스가 이미 있어서 구현체 하나 추가하는 정도의 작업량이다. 지금처럼 로컬 디스크에 저장하면, 백엔드 인스턴스를 2대 이상으로 늘리는 순간 'A 인스턴스에 업로드한 파일을 B 인스턴스가 못 찾는' 문제가 반드시 터진다. 즉 이건 '이득이냐'의 문제가 아니라 수평 확장을 하려면 안 할 수가 없는 전제조건에 가깝다. 리스크가 거의 없다. 실패해도 로컬 스토리지로 롤백하면 그만이다."

### CloudFront (정적 자산 캐싱) — 판단이 필요했던 부분

레포의 `test:artillery` 설명에 **"실제 브라우저를 다수 띄워 부하를 주는 테스트(Artillery + Playwright 엔진)"**라고 되어 있었다. 이게 결정적이었다 — API만 두드리는 게 아니라 진짜 브라우저로 페이지를 연다는 뜻이므로, 가상 유저 1000명이 접속하면 각자 `/_next/static/*` JS 번들·CSS·이미지를 전부 다운로드한다. API 요청과는 별개로 프론트 EC2/원본에 실질적인 부하가 걸린다.

**이득**: 이 정적 자산 트래픽을 CloudFront 엣지에서 캐싱하면 원본(프론트 EC2)은 최초 1회만 응답. 프론트 EC2가 정적 파일 서빙에 쓰던 스레드/대역폭을 아껴서 같은 인스턴스 대수로도 더 많은 동시 세션을 버틸 여지가 생긴다. t3.small 20대 한도 안에서 프론트 인스턴스를 덜 늘려도 되면 백엔드/DB 쪽에 더 배정할 수 있다.

**비용(리스크)**: 배포 생성+전파가 15~25분 걸림 (ACM처럼 1~5분이 아님) — 처음 설정 시 대기시간 감안 필요. **가장 위험한 부분은 캐시 정책 실수** — HTML(`/`, `/chat/*`)까지 실수로 캐싱하면 로그인 상태가 꼬이거나 오래된 화면이 보이는 등 "기능 자체가 깨지는" 사고로 이어질 수 있음. 정적 자산(`/_next/static/*`, `/images/*`, `/public/*`)만 캐싱하고 나머지는 오리진으로 패스스루하도록 캐시 비헤이비어를 반드시 분리해야 함.

### 프론트엔드를 SSR EC2로 유지한 이유

처음엔 S3+CloudFront로 프론트를 완전히 정적화하는 방안도 검토했다. 코드를 열어보니 `pages/`, `app/` 어디에도 `getServerSideProps`, 미들웨어, API 라우트가 없고 전부 `'use client'` — SSR이 꼭 필요해서가 아니라 배포 방식이 그렇게 되어 있을 뿐이었다. 하지만:
- `next.config.js`에 `output: 'standalone'` — Node 서버 Docker 배포용 설정
- `Dockerfile`이 `node server.js`로 Next 서버를 직접 실행
- **`app/chat/[room]/page.js` 동적 라우트**가 걸림돌 — 정적 export로 가려면 빌드 시점에 room id를 알아야 하는데, 채팅방 id는 런타임 생성값이라 불가능. 우회하려면 CloudFront 커스텀 에러/리라이트 설정이 필요한데, 검증 안 된 새 방식을 대회 중 처음 시도하는 리스크가 커서 **SSR EC2 유지 + CloudFront는 정적 자산 캐싱 전용**으로 최종 결정.

### 최초 아키텍처 순서

```
서브넷 라우팅 확인 → 백엔드/DB/Redis EC2 1대씩 기동 → ALB+타겟그룹
→ S3+CloudFront로 프론트 이전(정적 자산만) → 모니터링 배포 → 베이스라인 테스트
```

## 5. Tomcat/Socket.IO 튜닝 라운드별 기록

### 왜 하나씩 바꿔야 하는가

> "스레드는 많으면 컨텍스트 스위칭 비용으로 처리속도도 느려짐. 스레드가 적으면 CPU 자원을 최적으로 활용하지 못함."

t3.small은 2 vCPU라, 무작정 스레드를 늘리는 게 능사가 아니다. RPS/p95/p99가 좋아지다가 꺾이는 지점을 찾는 게 목표였고, 보통 CPU 바운드 작업(로그인 bcrypt 등)이 섞여 있으면 코어 수의 4~8배 수준에서 한계가 온다.

### 계획했던 12라운드 매트릭스

**1단계 — threads.max (accept-count/max-connections 고정)**

| 라운드 | threads.max | accept-count | max-connections | 비고 |
|---|---|---|---|---|
| 0 (베이스라인) | 10 | 10 | 50 | 최초 상태 |
| 1 | 25 | 100 | 8192 | 소폭 증가 |
| 2 | 50 | 100 | 8192 | |
| 3 | 100 | 100 | 8192 | Spring Boot 기본값 절반 |
| 4 | 200 | 100 | 8192 | Spring Boot 기본값 |
| 5 | 400 | 100 | 8192 | 기본값 2배, 오히려 나빠지는지 확인 |

**2단계 — accept-count (threads.max 고정)**

| 라운드 | accept-count | 비고 |
|---|---|---|
| 6 | 50 | |
| 7 | 100 | 기본값 |
| 8 | 200 | |
| 9 | 500 | 스파이크 특성상 순간 대기열 커질 수 있어 넉넉하게 |

**3단계 — max-connections**

지금 50으로 잡힌 게 가장 의심스러운 값이었다 — Keep-Alive 커넥션 총량 제한이라, threads.max를 아무리 올려도 이 값이 낮으면 소용없음. Socket.IO 폴링/장기 연결도 있어 넉넉하게 잡는 게 중요.

| 라운드 | max-connections | 비고 |
|---|---|---|
| 10 | 200 | |
| 11 | 1000 | |
| 12 | 8192 (기본값) | |

**4단계 — 최종 조합 검증**: 개별로 좋았던 값을 조합해도 좋다는 보장은 없음(예: 스레드 100 + 커넥션 8192 조합이 예상외로 메모리 압박 유발 가능). 실제로 12라운드를 다 돌 시간은 부족해서, **1단계 위주로 돌리고 2~3단계는 필요한 조합만 추려서 진행.**

### 실제 실행 결과

**VU 52 (베이스라인, threads=10)**: 완료율 94%, 5xx 0건 — 아직 병목이 안 드러남. 이 규모에선 threads=10도 버팀.

**VU 160~200 (threads=10 그대로)**: 완료율 60%, **5xx 174건 최초 발생**, login TTFB 최대 17.8초. 로그인은 bcrypt 등 CPU 연산이 섞여 스레드 10개로는 순식간에 큐가 밀림.

**threads=30, min-spare=1, accept-count=100, max-connections=8192 (1차 튜닝)**: 완료율 60%→78%, 실패 40%→22%로 확실히 개선. 하지만 5xx 비율은 거의 그대로, 로그인 지연도 여전 — 스레드 부족으로 "대기하다 죽는" 문제는 줄었지만 "처리는 시작했지만 오래 걸려 타임아웃"은 그대로. 여기서 **`min-spare=1`이 스파이크에 불리하다는 걸 발견** — 평소엔 스레드 1개만 대기하다 트래픽 몰릴 때마다 새로 생성해야 해서, 정확히 스파이크가 터지는 순간에 생성 비용까지 얹힘.

**백엔드 3대 + 프론트 2대 증설, min-spare 10으로 조정**: **5xx 0건 달성.** 대신 파일 업로드 시나리오 실패율 80% 신규 발견(4장 문제 #3의 실제 발현).

**최종 결론 (메모에 명시)**: `threads.max=30, accept-count=100, max-connections=8192`로 확정.

### Socket.IO acceptBackLog

Tomcat과 완전히 같은 성격의 병목을 별도로 발견 — `socketConfig.setAcceptBackLog(10)`. 500으로 올리는 걸 코드팀에 요청.

- **판단 기준**: `net.core.somaxconn`(OS 커널 값)이 요청값보다 작으면 그쪽이 우선 적용됨. 확인해보니 이미 4096으로 넉넉해서 별도 조치 불필요.
- **실측 검증 방법**: `nstat -az | grep ListenOverflows` (또는 `netstat -s | grep -i listen`)로 오버플로우 카운터 확인. 0이면 충분, 계속 증가하면 부족.
- **실제로 138건의 SYN drop이 스파이크 테스트 중 확인됨** — `acceptBackLog=500` 배포 여부/시점과 겹쳐서 원인 조사, 결국 배포 시점 확인 후 해소.

## 6. DB/Redis 성능 튜닝

### MongoDB

**즉시 할 수 있는 것부터 (인프라 단독으로 가능)**

1. **EBS 볼륨 IOPS/처리량 상향** — 디스크 I/O가 원인일 때 가장 빠른 해법. gp3 볼륨 IOPS 3000→6000~8000, 처리량 125MB/s→250MB/s. 다운타임 없이 즉시 적용, 재부팅 불필요.
2. **WiredTiger 캐시 크기 명시** — t3.small 2GB 메모리 기준, 기본 캐시 공식 `(전체메모리-1GB)*0.5`면 캐시가 0.5GB밖에 안 됨. `storage.wiredTiger.engineConfig.cacheSizeGB: 1.0`로 명시.
3. **Replica Set 구성 (2대: Primary+Secondary)** — AMI 사용 금지 규정 때문에 User Data 부트스트랩 스크립트로 두 번째 노드 구축. `MONGO_URI`에 `readPreference=secondaryPreferred` 추가해 읽기 분산 검토 — **단, 최종적으로는 이 옵션을 추가하지 않기로 결정**

## 7. 배포 삽질 히스토리 (환경변수/재시작 실수들)

부하테스트 결과가 이상할 때마다 실제 원인은 코드보다 배포 설정 실수인 경우가 압도적으로 많았다. 시간순으로 기록.

### 7-1. `FILE_STORAGE_TYPE` 환경변수 누락

S3 버킷·IAM 권한을 다 세팅해놓고 이미지 업로드를 해봤는데 S3 콘솔에 객체가 0개. `.env`에 `S3_BUCKET`, `AWS_REGION`은 있는데 정작 **`FILE_STORAGE_TYPE`이 빠져있어서 기본값 `local`로 계속 동작 중**이었다. 로컬 `uploads/chat/`, `uploads/profiles/` 폴더에 500개 넘는 파일(각 1MB, 합계 1GB+)이 쌓여있는 걸 확인해 확정. `.env`에 `FILE_STORAGE_TYPE=s3` 추가 후 재시작으로 해결.

### 7-2. `.env` 수정 후 재시작 누락

`spring.mongodb.uri=${MONGO_URI}` 같은 환경변수는 **기동 시 한 번만 읽음**. `.env` 값만 바꾸고 재시작을 안 한 채 재테스트해서 몇 차례 헛다리를 짚었다. 이후 원칙: 값 바꾸면 반드시 재시작 → 재시작 시각을 확인(`ps -o lstart=` 또는 `docker inspect --format '{{.State.StartedAt}}'`)해서 실제 반영 여부부터 검증하는 습관을 들임.

### 7-3. `target/classes` vs `src/main/resources` 혼동

라운드별 A/B 테스트 중엔 `target/classes/application.properties`(빌드 산출물)만 고쳐서 재컴파일 없이 빠르게 재기동. **다만 이건 EC2 로컬에만 유효**하고 `mvn clean`하면 사라짐 — 최적값을 찾은 뒤엔 반드시 `src/main/resources/application.properties`(진짜 소스)에 반영해 커밋.

### 7-4. `CORS_ALLOWED_ORIGINS` 변수명 오타

코드는 `${CORS_ALLOWED_ORIGINS:*}`를 읽는데 `.env`엔 `APP_CORS_ALLOWED_ORIGINS`로 되어 있어 매칭 실패, 조용히 기본값 `*`(전체 허용)로 대체되고 있었음. 기능은 안 깨지지만(오히려 더 허용적) 의도한 제한이 전혀 안 걸리는 상태 — 변수명 수정.

### 7-5. `SOCKETIO_SERVER_ORIGIN` 끝 슬래시

`https://chat.goorm-ktb-005.goorm.team/`처럼 끝에 `/`가 붙어있으면, 브라우저의 실제 `Origin` 헤더(끝 슬래시 없음)와 글자 단위로 불일치해 CORS 체크가 실패할 수 있음. same-origin 구조라 영향은 제한적이지만, Socket.IO 폴링 폴백 시나리오에서 재연결 실패로 이어질 가능성을 우려해 슬래시 제거.

### 7-6. Mongo 인증 실패 디버깅

`mongosh` 접속 시 `Authentication failed` — 계정을 어느 DB 컨텍스트(`admin` vs `bootcamp-chat`)에서 만들었느냐에 따라 `authSource` 파라미터 유무가 갈림. `db.getUsers()`로 실제 계정/역할 확인 후 `?authSource=admin` 붙여서 해결. **DB 자체는 첫 쓰기 시점에 자동 생성되므로 미리 만들 필요 없음** — 계정 권한만 정확히 맞추면 됨.

### "핫 방" 쏠림 — 근본 원인 후보

`e2e/actions/chat.actions.js`의 `joinRandomChatRoomAction`을 코드로 직접 확인:
```javascript
const count = await chatRoomButtons.count();
const randomIndex = Math.floor(Math.random() * count);
await chatRoomButtons.nth(randomIndex).click();
```
**"무작위"가 화면에 렌더링된 방 목록 안에서만 랜덤**이라, 방 목록이 최신순/제한된 개수로 노출되는 구조라면 실제로는 소수의 인기 방에 트래픽이 쏠린다. Mongo 로그로 실제 확인: 같은 room ID(`6a7bb317...`)에 백엔드 3대 전부에서 짧은 시간 안에 여러 유저가 몰려 입장한 것을 크로스 인스턴스 로그 대조로 확인 — 이 방은 이미 메시지 30건 이상 누적(`hasMore: true`), 명백한 핫스팟. 방에 사람이 많을수록 메시지 브로드캐스트 fan-out 비용이 커져 라우팅 지연으로 이어졌을 가능성이 유력.

이 진단 과정에서 사용한 방법(결과가 안 보일 때 재현성 있게 원인을 좁히는 법):
1. Playwright 콘솔로그/스크린샷/네트워크 실패 캡처를 시나리오에 추가 (`page.on('console')`, `page.on('pageerror')`, `page.on('requestfailed')`, 실패 시 `page.screenshot()`)
2. 실패 시각과 room ID로 **백엔드 3대 전부**의 로그를 동시에 grep해 크로스 인스턴스 상태를 대조 — 이게 가장 결정적인 진단 방법이었음
3. ALB 액세스 로그 활성화로 "요청이 ALB까지는 왔는지" 객관적으로 확인
4. 세션/JWT 만료 시간 확인 (JWT 24시간, 세션 TTL 30분 — 둘 다 시나리오 소요시간보다 충분히 길어 기각)

## 11. 배운 점

1. **"배포했다"와 "실제로 반영됐다"는 다르다.** `.env`만 바꾸고 재시작을 안 하거나, 코드 수정 후 jar 재빌드를 안 한 채로 재테스트해서 몇 차례 헛다리를 짚었다. 매 라운드 배포 상태(재시작 시각, 실제 코드 반영 여부)를 먼저 확인하는 습관이 정착되기까지 시간이 걸렸다.
2. **인프라 지표(CPU/메모리)가 깨끗해도 애플리케이션 레벨 실패는 별개로 확인해야 한다.** Grafana/CloudWatch가 정상이어도 특정 시나리오(파일 업로드, 방 입장 라우팅)는 계속 실패할 수 있었다.
3. **라운드마다 DB/Redis/S3 데이터를 초기화하지 않으면 비교가 왜곡된다.** 테스트 계정은 매번 `loadtest_{timestamp}_{randomId}` 형태로 고유 생성되어 재사용 충돌은 없었지만, 데이터 누적과 레이트리밋 잔존 상태는 다음 라운드 결과를 왜곡시킬 수 있었다.
4. **여러 인스턴스의 로그를 정확한 타임스탬프/room ID로 동시에 대조하는 게 제일 확실한 진단 방법이었다.** 크로스 인스턴스 브로드캐스트가 실제로 작동하는지, 특정 방에 트래픽이 쏠리는지를 이 방법으로 확정할 수 있었다.
5. **권장값과 실제 적용값이 갈릴 수 있고, 그건 자연스러운 일이다.** 다만 그 결정을 내린 이유를 기록해두지 않으면 나중에 회고할 때 "왜 이렇게 했는지" 복원하는 데 시간이 든다.

- 10초 안에 메시지가 화면에 안 뜨는 것으로 나타남
