#### | 캐시 문제 해결하기

> ⚠️ 캐시는 데이터베이스의 부하를 줄이기 위한 장치지만, **잘못 설계하면 오히려 트래픽을 데이터베이스로 한꺼번에 전달하는 "장애 증폭기"**가 될 수 있다.

##### 1. 캐시란

자주 조회하거나 계산 비용이 큰 데이터를, 빠르게 서빙하기 위해 임시 저장소에 보관해두는 방식이다. 데이터베이스나 외부 API에 대한 접근을 줄여서 다음과 같은 효과를 얻는다.

- 응답 시간 감소
- 데이터베이스 부하 감소
- 처리량 증가
- 외부 API 호출 비용 감소

##### Cache Aside Pattern — 가장 기본적인 캐시 조회 흐름

**먼저 캐시를 조회하고, 없으면 DB를 조회한 뒤 그 결과를 캐시에 저장한다.**

```
1. 애플리케이션이 캐시를 조회한다.

2. 캐시에 데이터가 있다.
   → Cache Hit
   → 캐시 데이터를 반환한다.

3. 캐시에 데이터가 없다.
   → Cache Miss
   → 데이터베이스를 조회한다.
   → 조회 결과를 캐시에 저장한다.
   → 사용자에게 반환한다.
```

##### 캐시 문제가 발생하는 지점 — 한눈에 보기

| 증상 | 문제 |
|---|---|
| 존재하지 않는 데이터가 반복 조회된다 | **Cache Penetration** |
| 인기 있는 하나의 캐시가 만료된다 | **Cache Stampede / Cache Breakdown** |
| 많은 캐시가 한꺼번에 사라진다 | **Cache Avalanche** |
| 특정 키에 요청이 집중된다 | **Hot Key** |
| 캐시와 데이터베이스의 값이 달라진다 | **Cache Consistency** |

##### 1. Cache Penetration (캐시 침투)

**존재하지 않는 데이터를 반복적으로 조회하여, 요청이 계속 데이터베이스까지 도달하는 문제다.**

**정상적인 캐시 미스**

```
상품 ID 100 조회 → 캐시에 없음 → DB에서 상품 조회 → 캐시에 저장
→ 이후 요청은 캐시에서 처리됨
```

**Cache Penetration**

```
존재하지 않는 상품 ID 99999 조회 → 캐시에 없음 → DB에도 없음
→ 캐시에 저장하지 않음
다시 상품 ID 99999 조회 → 캐시에 없음 → 다시 DB 조회
...(반복)
```

이런 존재하지 않는 값을 무작위로 조회하는 방식은 **DB 커넥션을 점유하는 공격 수단**으로도 악용될 수 있다.

**어떤 문제를 만드나?**
- DB 쿼리 증가
- DB 커넥션 풀 고갈
- CPU 및 디스크 I/O 증가
- 정상적인 요청의 응답 시간 증가
- 캐시 적중률 저하

**해결 방법**

1. **입력값을 검증** — 데이터베이스를 조회하기 전에 클라이언트 요청 값이 유효한지 먼저 검증한다.
2. **존재하지 않는 결과도 캐싱 (Negative/Null Caching)** — DB에 값이 없더라도 "값이 없다"는 사실 자체를 캐시에 저장한다 (예: 상품 ID 99999999 → `null`을 캐시에 저장). 다만 조심해서 사용해야 한다. 존재하지 않는 키를 계속 저장하면 Redis 같은 KV Store는 저장 공간(메모리)이 협소하기 때문에, 자주 접근하지 않는 키나 가장 오래된 키부터 제거하는 Eviction이 발생할 수 있다. **Null 캐싱은 TTL을 상당히 짧게 잡는 것이 좋다.**
3. **블룸 필터(Bloom Filter)** — 특정 데이터가 존재하지 않는다는 것을 확률적으로 빠르게 계산해서 리턴하는 자료구조다.
4. **Rate Limit** — 조회 자체를 많이 못하게 제한한다. 다만 **분산된(Distributed) 공격자**를 막기는 어렵다는 한계가 있다.

##### 2. Cache Stampede (캐시 쏠림)

**인기 있는 캐시 하나가 만료되는 순간, 많은 요청이 동시에 데이터베이스를 조회하는 문제다.**

```
인기 상품의 캐시가 만료되는 순간
요청 1 → 캐시 없음 → DB 조회
요청 2 → 캐시 없음 → DB 조회
요청 3 → 캐시 없음 → DB 조회
...
→ 동시에 수천 개의 쿼리가 데이터베이스로 들어감 → 서비스가 터짐
```

**문제**
- 동일한 DB 쿼리 대량 실행
- DB 커넥션 풀 고갈
- CPU 사용량 급증
- 외부 API 중복 호출
- 동일 데이터 중복 계산
- 응답 지연 및 타임아웃
- DB 장애가 다른 서비스로 전파

**해결 방법**

**① Request Coalescing (요청 합치기 / Single Flight)**
동일한 키에 대한 요청을 하나의 요청으로 합친다. API, Request Body, 대상이 모두 같은 요청 N개가 동시에 WAS에 도착하면, WAS가 요청을 짧게 홀딩(대기)한 뒤, **DB 쿼리는 딱 한 번만 보내고 그 결과를 요청 모두에게 반환**한다.

> ⚠️ Request Coalescing은 **동일 인스턴스, 동일 파드, 동일 애플리케이션 안에서만** 동작한다.

**② 키 단위 락 걸기**
캐시가 없을 때, **가장 먼저 도착한 요청만 락을 획득**해서 DB를 조회하는 방식이다.

```
요청 1: 캐시 없음 → Lock 획득 → DB 조회 → 캐시 저장 → 락 해제
요청 2~N: 캐시 없음 → 락 획득 실패 → 잠시 대기 → 캐시 다시 조회
```

Request Coalescing과 달리 **분산 환경에서도 잘 동작**한다.

> ⚠️ **구현 주의 사항**: 락 자체가 병목이 될 가능성이 있다. 락에 TTL을 걸어두어야 하고, 락 획득에 실패한 2~N번 요청이 "캐시에 값이 들어왔는지" 계속 확인하면서 락 획득을 재시도하는 구조라면, **락 획득 요청 자체에 횟수 제한**을 걸어야 한다.

**③ Stale-While-Revalidate**
캐시가 논리적으로는 만료되었어도, **기존(오래된) 데이터를 잠깐 반환**하면서 백그라운드에서 캐시를 갱신하는 방식이다.

| 장점 | 단점 |
|---|---|
| 사용자는 캐시 갱신을 기다리지 않는다 | 사용자가 잠시 오래된 데이터를 볼 수 있다 |
| DB에 요청이 한꺼번에 몰리지 않는다 | 엄격한 데이터 최신성이 필요한 영역에서는 불리하다 |
| 인기 키를 캐시에서 완전히 제거하지 않을 수 있다 | |

**④ 만료 전 미리 갱신**

```
TTL: 10분
9분 경과  → 백그라운드 갱신 시작
10분 경과 → 이미 새로운 캐시가 준비됨
```

이 방식은 결국 스케줄러가 별도의 트래픽을 발생시키게 된다. 캐시가 특정 인기 키에만 집중적으로 조회되는 환경에서는, 스케줄러의 작업량이 일반 사용자 트래픽보다 많아질 수 있다는 점을 감안해서 **인기 키만 골라 갱신**하는 방식으로 설계한다.

**실무 적용**: 위 방법들은 하나만 쓰기보다 **조합해서 사용**하는 경우가 많다. 예를 들어 "인기 키 감지 → 만료 전 선제 갱신 → 만료됐다면 Request Coalescing으로 대표 요청 하나만 DB 조회 → 나머지 요청은 이전 값을 반환하거나 제한된 시간만 대기" 같은 순서로 조합한다.

##### 3. Cache Avalanche (캐시 눈사태)

**많은 캐시 키가 동시에 만료되거나 캐시 서버 전체에 장애가 발생하여, 캐시 계층이 한꺼번에 무너지면서 전체 트래픽이 DB로 이동하는 문제다.**

**발생 원인**

**① 신규 파드·신규 서비스 시작 시**
서비스가 시작될 때 여러 데이터를 한 번에 캐싱하면서(`product:1 TTL 60분`, `product:2 TTL 60분` ...) 모든 키의 TTL이 동일하게 설정되면, **정확히 60분 뒤 모든 키가 동시에 만료**되어 캐시 미스가 한꺼번에 발생하고, 그대로 DB로 몰려 장애로 이어진다.

**② 캐시 서버 장애**
Redis 서버가 1대만 있는 상태에서 장애가 발생하면 **모든 캐시가 사라지고**, 그 트래픽이 그대로 DB로 몰려 DB 장애로 이어질 수 있다.

**③ Cold Cache (콜드 캐시)**
Redis 재시작, 캐시 클러스터 교체, 신규 리전 오픈, 신규 서버 오픈 등으로 **캐시가 텅 빈 상태로 새로운 캐시 스토리지가 추가**되는 경우다.

**문제**

```
전체 DB 트래픽 급증
Connection Pool 고갈
DB CPU 및 I/O 포화
서비스 전체 응답 지연
Timeout과 Retry 증가
Retry로 인한 추가 부하
장애가 여러 서비스로 확산
```

**해결 방법**

**① Jitter 적용**
모든 캐시의 TTL을 동일하게 설정하지 않고, **TTL에 무작위 값을 더하거나 빼서** 만료 시점을 분산시킨다. 이렇게 하면 만료 시간이 흩어지면서 DB 요청도 함께 분산된다.

> ⚠️ Jitter의 한계: 캐시의 스프레드(분포)가 이미 넓거나, 캐시 자체가 매우 많아지면 TTL을 분산해봐야 결국 총량 자체가 커서 비슷한 현상이 재발할 수 있다.

**② Cache Warm-Up**
콜드 캐시 문제에 대한 해법이다. 캐시 서버를 새롭게 만들 때, **실제 트래픽을 받기 전에 데이터를 미리 캐시에 채워두고**, 준비가 끝난 뒤에야 Redis로 요청을 전달하기 시작한다.

**③ 캐시 서버 고가용성 처리**
캐시 서버 장애 → 모든 캐시 만료 → DB 폭증으로 이어지는 문제는, 캐시 서버 자체의 가용성이 낮기 때문이다. **Redis 관리형 서비스**를 사용하거나, 비용이 감당된다면 **Primary–Replica** 구조로 구성해 캐시 계층 자체의 장애 내구성을 높인다.

##### 4. Hot Key

**전체 요청의 상당 부분이 하나 또는 소수의 캐시 키에 집중되는 문제다.**

하나의 키에 요청이 몰리면 그 키가 위치한 특정 Redis 노드가 병목이 된다. 다만 이 문제는 **발생 확률 자체는 낮은 편**이며, 트래픽 규모가 어마어마하게 큰 서비스일수록 발생 확률이 늘어난다.

**왜 발생하는가? — 문제가 생기는 대표 사례**

- 인기 상품
- 실시간 순위
- 메인 페이지 설정
- 유명인의 게시물
- 콘서트 좌석 정보
- 한정 판매 재고
- 실시간 경기 점수

**문제**
- 특정 Redis 노드의 CPU 사용량 증가
- 특정 노드의 네트워크 대역폭 포화
- 특정 키의 읽기·쓰기 지연
- Redis Cluster 노드별 부하 불균형
- 같은 노드에 있는 다른 키까지 함께 지연됨
- Hot Key가 만료되는 순간 **Cache Stampede**로 이어질 수 있음

**해결 방식**

1. **Hot Key 분산** — 키의 접근 횟수를 카운트하고, 특정 주기별로 접근이 몰린 키를 여러 노드로 분산시킨다.
2. **Hot Key 복제** — Hot Key로 판단된 키를 **모든 노드에 복제해서 배치**해, 특정 노드 하나로 요청이 몰리지 않게 한다.

##### 5. Cache Consistency (캐시 정합성)

**데이터베이스의 최신 값과 캐시에 저장된 값이 서로 달라지는 문제다.**

**해결 방법**

**① 데이터베이스 갱신 시 캐시를 만료시키기**

```
DB 데이터 수정 → 커밋 성공 → 관련 캐시 삭제
→ 다음 조회 시 DB 데이터를 다시 캐싱
```

> 💡 **왜 캐시를 직접 수정하지 않고 굳이 만료시키는가?** 캐시를 직접 수정하려면 "하나의 비즈니스 로직이 데이터베이스와 캐시라는 두 저장소를 모두 갱신"해야 하는 관리 포인트가 늘어난다. 캐시 데이터를 수정하는 것보다 **캐시를 삭제하고 다음 조회에서 새로 캐싱하는 편이 정책적으로 더 깔끔하다.** TTL(만료 시간)을 지정한다는 것 자체가 "이 시점까지만 이 값이 유효하다"는 약속이기 때문이다.

**② TTL을 짧게 설정하기**
값이 자주 변경되거나, **캐싱한 값이 반드시 최신 사실이어야 하는 경우**라면 TTL을 짧게 설정한다. 반대로 설정 값이 변경되는 주기가 매우 빠른 데이터는 애초에 캐싱에 적합하지 않을 수 있다.

---

##### 캐시 문제 정리 — 증상으로 원인 진단하기

| 질문 | 원인 |
|---|---|
| 존재하지 않는 값을 계속 조회하는가? | Cache Penetration |
| 특정 인기 키가 만료되었는가? | Cache Stampede |
| 여러 키가 비슷한 시간에 만료되었는가? | Cache Avalanche |
| Redis 서버 전체가 비어 있거나 장애 상태인가? | Cache Avalanche |
| 특정 Key 또는 특정 Node에만 부하가 몰리는가? | Hot Key |
| DB 값과 캐시 값이 다른가? | Cache Consistency |

### 🗨️ 오늘의 회고

- 오늘은 캐시라는, 겉보기엔 단순해 보이는 장치가 사실은 **잘못 설계하면 장애를 오히려 증폭시키는 장치가 될 수 있다**는 걸 배운 시간이었다. Cache Aside Pattern 자체는 이미 알고 있던 개념이었지만, 그 뒤에 숨어 있는 5가지 실패 패턴(Penetration, Stampede, Avalanche, Hot Key, Consistency)을 하나씩 뜯어보니, 캐시를 "그냥 넣어두면 빨라지는 것"으로만 생각했던 게 얼마나 단순한 접근이었는지 깨달았다.
- 가장 인상 깊었던 건 **Cache Penetration과 Cache Stampede가 결국 어제 배운 Resilience 패턴들과 정확히 같은 문제**라는 점이었다. 존재하지 않는 값을 반복 조회하는 문제는 결국 "요청이 너무 많다"는 Rate Limiter의 영역이고, 인기 캐시가 만료되는 순간 몰리는 요청은 결국 DB라는 하나의 자원에 부하가 집중되는 문제라서 Bulkhead·락과 비슷한 해법(요청 합치기, 락 걸기)으로 풀어낸다는 걸 보면서, 결국 분산 시스템에서 반복적으로 등장하는 "쏠림과 폭주를 어떻게 막을 것인가"라는 하나의 큰 주제가 캐시 계층에서도 똑같이 나타난다는 걸 느꼈다.
- **"캐시를 직접 수정하지 않고 굳이 만료시킨다"**는 Cache Consistency 파트의 설명이 특히 기억에 남는다. 지금까지는 "캐시 값을 업데이트하면 되지 않나?"라고 막연히 생각했는데, TTL이라는 개념 자체가 "이 시점까지는 유효하다"는 명시적인 약속이라는 관점으로 보니, 캐시와 DB라는 두 저장소를 각각 별도로 갱신하는 로직을 만드는 것보다 왜 삭제 후 재캐싱이 더 깔끔한 정책인지 납득이 됐다.
- Cache Avalanche의 세 가지 발생 원인(TTL 동시 만료, 캐시 서버 장애, Cold Cache) 중에서도 특히 **"신규 파드가 시작될 때 여러 데이터를 한 번에 캐싱하면 모든 TTL이 똑같이 맞춰져서 정확히 그 시점에 한꺼번에 만료된다"**는 사례가 실무적으로 놓치기 쉬운 함정처럼 느껴졌다. Jitter를 적용해서 TTL을 의도적으로 흩뜨린다는 해법이 단순하면서도 효과적인 아이디어라는 생각이 들었다.
- Hot Key 문제는 "발생 확률 자체는 낮지만, 발생하면 특정 노드 하나가 통째로 병목이 된다"는 설명을 들으며, 캐시 설계가 단순히 "얼마나 많이 캐싱하느냐"의 문제가 아니라 **"어떻게 분산시키느냐"**의 문제이기도 하다는 걸 다시 확인했다. 인기 상품이나 실시간 순위처럼 지금 만들고 있는 개인 프로젝트에서도 충분히 나올 수 있는 시나리오라서, 나중에 캐시를 도입할 일이 있으면 오늘 배운 체크리스트(존재하지 않는 값 반복 조회? 인기 키 만료? 여러 키 동시 만료? Redis 장애? 특정 키·노드 쏠림? DB-캐시 값 불일치?)를 먼저 점검해봐야겠다.
