### 🚀 Today I Learned

#### | 부하테스트 (Load Testing)

> 💡 부하테스트는 실제와 유사한 사용자와 요청을 시스템에 발생시키고, **처리량·지연 시간·오류·리소스 포화도**를 측정하여 목표 성능을 만족하는지와 병목이 어디인지 확인하는 테스트다.

> ⚠️ 부하테스트는 "그냥 서버에게 많은 요청을 보내는 것"이 아니다. **특정 목표를 정하고, 그 기준을 통과하는지, 통과하지 못한다면 어디에서 어떤 이유로 못하는지를 분석해서 개선하는 작업**이다.

부하테스트로 확인하려는 것들:

- 목표 트래픽을 처리할 수 있는가?
- 사용자가 느끼는 서비스 응답 속도가 목표 안에 들어오는가?
- 부하가 증가할 때 어디에서부터 성능이 저하되는가?
- HPA·CA가 어느 정도 속도로 늘어나고 줄어드는가?

> 💡 **성능 테스트**는 시스템의 속도·안정성·확장성을 검증하는 테스트 전체를 가리키는 큰 범주이고, **부하테스트는 그 성능 테스트의 한 종류**다.

##### 왜 부하테스트를 하는가?

**1. 목표 성능 검증**
"100M MAU를 버티는 시스템을 만들어야 한다"처럼 비즈니스 요구사항을 충족하는지 미리 검증해야 한다. 예를 들어 "초당 300개 처리", "요청의 95%는 500ms 이내 처리", "오류율은 1% 미만" 같은 목표가 있다면, **실제 유저가 그 상황을 만들어주기 전에는 시스템이 버틸 수 있는지 알 수 없다.** 만약 실제 유저가 그 상황을 겪었는데 처리하지 못하면 곧바로 서비스 장애로 이어지기 때문에, 미리 검증해야 한다.

**2. 병목 구간 탐지**
"초당 300개의 요청을 넣으니 서비스가 느려졌다"면, 그 원인이 어디에 있는지 찾아야 한다. Pod Limit, HPA 확장 속도가 트래픽 증가를 못 따라오는 경우, N+1 쿼리, Write-back, Disk I/O, Connection Pool 등 다양한 이유가 있을 수 있다. 이런 문제들은 평상시엔 아무 문제 없이 동작하다가, **트래픽이 급격히 몰리거나 특정 요청이 반복될 때 비로소 가시화되는 경우가 많다.**

**3. 시스템의 한계 지점 파악**

**4. 시스템·구조 변경 전후 성능 비교**

##### 핵심 용어

**Workload**
테스트 중 시스템에 발생시키는 **사용자 행동·요청의 전체 패턴**을 말한다. 어떤 API를 얼마나 자주 호출하는지, 요청 사이에 사용자가 얼마나 대기하는지까지 모두 합친 것이 워크로드다.

```
메인 페이지 접속 → 50ms 대기 → 로그인 버튼 클릭
 → 100ms 대기 → domContentLoaded 대기 → ...
```

**VUser (Virtual User)**
테스트 도구 안에서 실제 사용자의 행동을 흉내내는 **가상의 실행 주체**다. 트래픽을 늘릴 때 이 VU의 수를 조절한다.

```
하나의 VU: 로그인 → 게시글 목록 조회 → 특정 게시글 접근
 → 댓글 작성 → 3초 대기 → 좋아요 → 뒤로 이동 → (반복)
```

**처리량 (Throughput)**
시스템이 일정 시간 동안 처리한 작업의 양이다. HTTP 시스템에서는 주로 다음 단위를 쓴다.

| 단위 | 의미 |
|---|---|
| RPS (Requests Per Second) | 초당 요청 수 — **보통 이걸 가장 많이 본다** |
| TPS (Transactions Per Second) | 초당 트랜잭션 수 |
| QPS (Queries Per Second) | 초당 쿼리 수 |

> 💡 전체 처리량(최대 처리량)은 **가장 느린 구간의 처리량**으로 결정된다(보통 데이터베이스 구간인 경우가 많다). **가장 낮은 처리량을 가진 구간이 곧 병목 구간**이며, 병목이 아닌 곳을 개선해봐야 전체 처리량은 늘어나지 않는다. 병목 구간을 개선하면 병목이 다른 곳으로 "이동"할 뿐이다. → **요청(Request)과 처리량(Throughput)을 구분해서 봐야 한다.**

**응답 시간 (Latency)**
요청을 보낸 시점부터 전체 응답을 받을 때까지 걸린 시간이다. HTTP 요청을 시간 단위로 쪼개보면:

```
TCP 연결 → TLS 교환 → 요청 전송 → 서버 처리(응답 대기)
  → 응답 데이터 수신 → 수신 완료
```

이 전체 과정에 걸리는 시간을 응답 시간이라고 한다.

**동시성 (Concurrency)**
같은 시간대에 진행 중인 요청이나 사용자 작업의 수를 말한다.

> ⚠️ **VU 1000명 = RPS 1000이 아니다.** 사용자는 페이지를 읽고, 입력하고, 다음 버튼을 누르고, 다음 화면으로 이동하는 등 각 행동 사이에 대기 시간이 있다. 예를 들어 각 행동 사이에 1000ms의 대기가 있고, 4초에 1번씩 요청을 보내는 시나리오라면, VU 1000명이 있어도 초당 요청 수는 그보다 훨씬 적다.

**오류율 (Error Rate)**
전체 요청 중 실패한 요청이 차지하는 비율이다. 단 시나리오상 원래 500이나 400대 응답을 **기대한 요청**이라면 오류율에 포함하지 않는다.

##### 부하테스트의 종류

| 종류 | 목적 | 확인 사항 |
|---|---|---|
| **Smoke Test** | 최소한의 부하로 테스트 스크립트와 시스템이 기본적으로 정상 동작하는지 확인 | 테스트 스크립트에 오류가 없는가? 인증과 데이터 설정이 정상인가? URL·환경 변수가 올바른가? 기본 응답이 정상인가? |
| **Load Test** (Average Load Test) | 평상시에 받는 트래픽을 재현해서 정상적인 운영 상태를 확인 | 평상시 RPS를 안정적으로 처리하는가? p95, p99는? 오류율이 허용 범위 안에 있는가? CPU·메모리·DB 커넥션이 안정적인가? HPA가 불필요하게 반복 동작하지 않는가? |
| **Stress Test** | 평상시보다 높거나 예상 최대 수준의 트래픽으로 성능·복구 능력을 확인 | 피크 시간 트래픽을 처리할 수 있는가? 부하가 높아질 때 성능은 어떻게 저하되는가? HPA가 필요한 속도로 Pod를 추가하는가? 부하가 줄면 정상 상태로 복구되는가? 보호 장치가 정상 작동하는가? |
| **Spike Test** | 아주 짧은 시간에 트래픽을 급격히 넣어 시스템이 견디는지, 복구되는지 확인 (쿠폰, 티켓 예매, 라이브 방송 시작, 수강 신청 등) | 갑작스러운 요청을 큐가 흡수하는가? 커넥션 풀이 고갈될 때 어떻게 대응하는가? 스케일 아웃 전에 기존 파드가 버티는가? 부하가 줄면 어떻게 대응하는가? 스파이크 마지막에 들어온 요청은 언제 완료 처리되는가? |
| **Soak Test** (Endurance Test) | 평균적이거나 작은 부하를 아주 오랜 시간 유지해서 성능 저하·자원 누수를 찾음 | 메모리 사용량이 지속적으로 증가하는가? DB 커넥션이 반환되지 않는가? 로그 파일이 디스크를 채우는가? 캐시가 비정상적으로 증가하는가? 장시간 이후 응답 시간이 느려지는가? |
| **Breakpoint Test** | 부하를 점진적으로 증가시켜 시스템이 더 이상 버티지 못하는 지점을 찾음 | 어느 지점부터 오류가 증가하는가? 최대 정상 처리량은 얼마인가? 가장 먼저 포화되는 자원은 무엇인가? 시스템이 점진적으로 느려지는가, 갑자기 무너지는가? |

> 💡 Stress Test라고 해서 항상 평소의 2배 트래픽을 넣는 것은 아니다. 보통은 **과거 최대 트래픽**을 기준으로 설계한다.

##### 부하테스트를 설계하는 방법

**1. 테스트 목표 설정**

예시: "게시글 조회 API가 300 RPS, 오류율 1% 미만, p95 500ms 미만을 만족해야 한다."

| 지표 | 의미 |
|---|---|
| p50 | 응답 시간 분포의 중간값 (하위 50%) |
| p95 | 상위 95% 이상에 해당하는 응답 시간 |
| p99 | 상위 99% 이상에 해당하는 응답 시간 |

**2. 테스트 범위 정하기**

| 방식 | 특징 |
|---|---|
| **단일 API 테스트** (`GET /posts/{randomId}`) | 특정 API의 병목을 찾기 쉽고 결과 해석이 단순하지만, 실제 사용자 흐름과는 다르게 움직일 수 있다. |
| **사용자 시나리오 테스트** | 실제 사용자의 흐름대로 진행해 여러 시스템이 연결된 상태를 검증할 수 있지만, 병목 원인을 분리하기 어렵고 테스트 설계가 복잡하다. |

**3. 실제 트래픽 비율 고려**

커뮤니티 서비스라면 예를 들어 다음과 같은 사용자 행동 비율을 참고해서 워크로드를 설계한다.

```
게시글 목록 조회: 45%
게시글 상세 조회: 25%
로그인 및 인증:   10%
댓글 조회:        10%
게시글·댓글 작성: 10%
```

> 💡 실제 트래픽 비율은 감으로 정하지 않고, **운영 로그나 PLG 지표를 확인해서 API Call 비율을 실제 데이터 기반으로 설정**해야 한다.

**4. 테스트 데이터 준비**

요청 횟수뿐 아니라 **데이터의 크기와 분포도**가 중요하다.

```
테스트 환경 A: 사용자 10명, 게시글 100개, 댓글 200개
테스트 환경 B: 사용자 100만 명, 게시글 1,000만 개, 댓글 5,000만 개
```

테스트할 때는 **실제 사용자 환경과 유사하거나, 그보다 더 가혹한 환경**을 만들어서 진행해야 한다.

**5. 부하 증가 단계를 구분해서 설계**

부하를 한 번에 최대치로 쏘는 대신, **단계별로 끊어서 늘려가야 한다.** 처음에는 아주 적은 부하로 시나리오에 문제가 없는지 확인하고, 이후 작은 부하 → 큰 부하 → 스파이크 → 스트레스 순서로 단계를 나눠 진행하는 것이 좋다.

##### 부하 모델의 차이 — Closed Model vs Open Model

| 모델 | 방식 | 특징 |
|---|---|---|
| **Closed Model** | 사용자가 요청을 끝내야 다음 요청을 보내는 방식. **VU(가상 사용자) 수를 기준**으로 부하를 만든다. | 서버가 느려지면 사용자가 응답을 기다리는 시간도 길어지고, 다음 요청도 그만큼 늦게 나간다. 예: 응답 시간 1초 → 사용자 1명이 초당 1회 요청 / 응답 시간 5초 → 5초마다 1회 요청. **서버가 느려질수록 부하기가 만드는 RPS도 자연스럽게 감소**한다. 실제 사용자가 웹사이트에서 응답을 기다리고 나서 다음 행동을 하는 것과 유사해서, **사용자 시나리오 기준 부하테스트**에 주로 사용한다. |
| **Open Model** | 이전 요청이 끝났는지와 관계없이 **정해진 속도로 새 요청을 계속 보내는 방식**. | 예: 매초 100개씩 요청 시작 → 1초 때 100개 시작 → 2초 때 기존 요청이 처리 중이어도 새 요청 100개를 또 시작. **서버가 느려져도 요청량이 줄지 않고, 처리 중·대기 중인 요청이 계속 쌓인다.** API 단위 부하테스트, 단일 부하테스트에 주로 사용한다. |

**선택 기준**
- "동시에 500명이 사용하는 서비스"를 가정한다 → **Closed Model**
- "초당 300건 요청을 밀어 넣는다" → **Open Model**

##### 부하테스트 결과 해석하기

**1. 트래픽**
목표 RPS, 실제 RPS, 성공 RPS, 동시 사용자 수, iteration/API별 요청 수를 보고 **내가 의도한 대로 트래픽이 전달됐는지**를 먼저 확인한다.

**2. Latency**
사용자가 응답을 받기까지 얼마나 기다렸는지를 본다. 보통 **p50, p95, p99**를 함께 확인하며, **평균값이나 p50만 중점적으로 보지 않는다.** 평상시에는 문제없다가 트래픽이 조금만 몰리면 p95·p99가 확 튀는 API가, 실제로는 더 위험한 API인 경우가 많다.

**3. Error Rate**
전체 요청 중 얼마나 많은 작업이 실패했는지 본다. 단순히 HTTP 4xx·5xx 개수보다는, **우리가 의도하지 않은 에러가 어디에서 얼마나 발생했는지**가 더 중요하다.

**4. H/W·Application 레벨 지표**
PLG Stack 같은 관측성 도구로 CPU, 메모리, DB 커넥션 등을 함께 확인한다. **대시보드가 잘 갖춰져 있어야 부하테스트를 진행했을 때 결과 해석이 의미를 갖는다.**

##### 부하테스트에서 가장 중요한 점

> ⚠️ 부하테스트의 목표는 **최대 RPS 숫자를 찍어내는 것이 아니다.** 목표한 트래픽에서 사용자가 기대하는 성능을 만족하는지, 그리고 **성능이 무너지는 시점과 그 원인을 파악하는 것**이 부하테스트의 진짜 목적이자 목표다.
