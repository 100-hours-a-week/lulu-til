## 1. 목표와 원칙

시작 전에 메모에 가장 먼저 적어둔 문장이 있다.

> "오로지 부하테스트가 목적이기 때문에 multi-az, 높은 보안성, 무중단 배포 등은 고려하지 않는다."

이 한 줄을 처음부터 박아두고 시작한 게 작업 전체를 수월하게 만들었다고 생각한다. 이중화나 고가용성에 들어갈 시간과 인스턴스 슬롯을 전부 "얼마나 버티는가를 측정하고 개선하는 것"에만 쓸 수 있었기 때문이다. 목표가 명확하니 매 순간 "이게 지금 필요한 일인가"를 스스로 판단하기가 쉬워졌다.

내가 보기로 삼은 지표는 다섯 가지였다: Max RPS, p95/p99 Latency, Error Rate, Break Point(최대 견딜 수 있는 VU), 시나리오 완료율(Completed).

## 2. 아키텍처를 이렇게 결정한 이유

### EC2 직접 설치를 선택한 이유

MongoDB와 Redis 모두 EC2 직접 설치 방식으로 결정했다. 이유는 세 가지였다. 대회 규정상 RDS, ElastiCache, DocumentCB 같은 AWS Managed Service는 애초에 쓸 수 없었고, 높은 TPS를 버텨야 하는 운영 DB 성격상 I/O 레이턴시를 최대한 줄이고 싶었고, Replica Set을 구성할 때 노드 하나를 EC2 인스턴스 하나에 전담시키는 쪽이 안정성 측면에서 더 확실했다.

### S3 — 사실상 고민할 필요가 없었던 결정

이건 결정이라기보다 전제조건에 가까웠다. 당시 내가 적어둔 메모:

> "StoragePort 인터페이스가 이미 있어서 구현체 하나 추가하는 정도의 작업량이다. 지금처럼 로컬 디스크에 저장하면, 백엔드 인스턴스를 2대 이상으로 늘리는 순간 'A 인스턴스에 업로드한 파일을 B 인스턴스가 못 찾는' 문제가 반드시 터진다. 즉 이건 '이득이냐'의 문제가 아니라 수평 확장을 하려면 안 할 수가 없는 전제조건에 가깝다. 리스크가 거의 없다. 실패해도 로컬 스토리지로 롤백하면 그만이다."

### CloudFront — 유일하게 진지하게 저울질했던 결정

레포의 `test:artillery` 설명을 읽다가 "실제 브라우저를 다수 띄워 부하를 주는 테스트(Artillery + Playwright 엔진)"라는 문장을 발견했는데, 이게 내 판단을 바꾼 결정적인 단서였다. API만 두드리는 테스트가 아니라 진짜 브라우저로 페이지를 연다는 뜻이니, 가상 유저 1000명이 접속하면 각자 `/_next/static/*` JS 번들·CSS·이미지를 전부 다운로드한다. API 요청과는 별개로 프론트 EC2에 실질적인 부하가 걸린다는 얘기였다.

**내가 계산한 이득**: 이 정적 자산 트래픽을 CloudFront 엣지에서 캐싱하면 원본(프론트 EC2)은 최초 1회만 응답하면 된다. 프론트 EC2가 정적 파일 서빙에 쓰던 스레드·대역폭을 아껴서, 같은 인스턴스 대수로도 더 많은 동시 세션을 버틸 여지가 생긴다. 규정상 t3.small 20대 한도가 있었으니, 프론트에 덜 쓰는 만큼 백엔드나 DB 쪽에 더 배정할 수 있었다.

**내가 우려한 리스크**: 배포 생성과 전파에 15~25분이 걸린다는 점(ACM처럼 1~5분이 아니었다)은 처음 설정할 때 반드시 감안해야 했다. 더 무서웠던 건 **캐시 정책 실수**였다. HTML(`/`, `/chat/*`)까지 실수로 캐싱해버리면 로그인 상태가 꼬이거나 오래된 화면이 보이는 식으로, 성능이 아니라 기능 자체가 깨지는 사고로 이어질 수 있었다. 그래서 정적 자산(`/_next/static/*`, `/images/*`, `/public/*`)만 캐싱하고 나머지는 전부 오리진으로 패스스루하도록 캐시 비헤이비어를 분리하는 걸 가장 신경 써서 확인했다.

### 프론트엔드를 SSR EC2로 남겨둔 이유

처음엔 S3+CloudFront로 프론트를 완전히 정적화하는 방안도 진지하게 검토했다. 코드를 열어보니 `pages/`, `app/` 어디에도 `getServerSideProps`, 미들웨어, API 라우트가 없고 전부 `'use client'`였다 — SSR이 기능적으로 꼭 필요해서가 아니라, 그냥 배포 방식이 그렇게 되어 있을 뿐이었다.

하지만 더 들여다보니 걸리는 부분이 있었다. `next.config.js`에 `output: 'standalone'`이 설정되어 있고, `Dockerfile`은 `node server.js`로 Next 서버를 직접 실행하는 구조였다. 결정적으로는 `app/chat/[room]/page.js` 동적 라우트가 문제였다 — 정적 export로 가려면 빌드 시점에 room id를 알아야 하는데, 채팅방 id는 런타임에 생성되는 값이라 애초에 불가능했다. 우회하려면 CloudFront 커스텀 에러/리라이트 설정이 필요했는데, 대회 중에 검증도 안 된 새 방식을 처음 시도하는 건 리스크가 너무 컸다. 그래서 **SSR EC2는 그대로 유지하고, CloudFront는 정적 자산 캐싱 전용**으로 쓰기로 최종 결정했다.

### 최초 아키텍처를 짠 순서

```
서브넷 라우팅 확인 → 백엔드/DB/Redis EC2 1대씩 기동 → ALB+타겟그룹
→ S3+CloudFront로 프론트 정적 자산 이전 → 모니터링 배포 → 베이스라인 테스트
```

## 3. Day 1 — 인프라 뼈대 구축

### 최소 인프라 구축까지

FE, BE, MongoDB, Redis를 각 1대씩 EC2로 생성하고 보안그룹까지 설정했다. ALB, Route53, CloudFront, S3까지 생성을 마치고 나서야 숨을 돌릴 수 있었다.

### 모니터링을 두 겹으로 가져간 이유

**CloudWatch (인프라 레벨, 기본값)**
IAM Role을 먼저 연결하고, ALB 지표는 설치 없이 `ApplicationELB` 네임스페이스에서 바로 확인할 수 있었다(`RequestCount`, `TargetResponseTime` p95/p99, `HTTPCode_Target_5XX_Count`, `HealthyHostCount`/`UnHealthyHostCount`). 기간을 1분으로 낮추지 않으면 스파이크를 놓칠 수 있다는 걸 알고 있어서 처음부터 1분으로 설정했다. 각 EC2에는 CloudWatch Agent를 설치했는데(`amazon-cloudwatch-agent.deb`), 메모리·디스크 수집이 기본 EC2 모니터링에 포함되지 않아서 이건 꼭 켜야 했다. 대시보드(`ktb-load-test`)는 하나로 통합하고 새로고침 주기는 10초로 뒀다.

**Prometheus + Grafana (애플리케이션 레벨)**
CloudWatch Agent로 Prometheus 엔드포인트를 EC2 환경에서 긁어오는 게 공식적으로 매끈하게 지원되지 않는다는 걸 알고 있었다(ECS/EKS 쪽이 더 잘 되어 있다), 그래서 Tomcat 스레드·JVM 메모리 같은 애플리케이션 지표는 역할을 분리해 별도 모니터링 EC2에 Prometheus+Grafana를 구축했다. 레포의 `docker-compose.o11y.yaml`이 애초에 별도 모니터링 서버를 전제로 설계되어 있었다(`node-exporters.prod.yml`의 `your-o11y-server` 항목, `cluster: monitoring`). mongodb-exporter와 redis-exporter는 각각 해당 EC2에 사이드카로 붙였고, 대상 SG마다 monitoring SG발 인바운드를 허용했다(backend: 9100/5001, mongo: 9100/9216, redis: 9100/9121, frontend: 9100). Grafana 3000번 포트는 인터넷에 열지 않고 SSH 터널로만 접근하게 했다.

## 4. 코드를 직접 열어보고 찾은 문제들

전체 코드를 받아서 직접 읽었다. 대회 취지(결함이 있는 코드)를 염두에 두고 찾은 문제가 다섯 가지였다.

| # | 문제 | 근거 |
|---|---|---|
| 1 | `server.tomcat.threads.max=10` | 기본 Spring Boot 값 200 대비 심각하게 낮음. 동시 요청 20개만 와도 큐가 밀림 |
| 2 | Socket.IO `MemoryStoreFactory` + `LocalChatDataStore` | 주석에 "단일노드 전용"이라고 명시 — 백엔드를 여러 대로 늘리면 채팅방 상태가 인스턴스별로 따로 놀아 오작동 |
| 3 | 파일 업로드 로컬 디스크 저장 | `RoutingStorage`가 `profiles/*`만 S3로, `chat/*`는 무조건 로컬로 라우팅 |
| 4 | `socketConfig.setAcceptBackLog(10)` | Tomcat과 동일한 패턴의 병목, 별도로 발견 |
| 5 | Redisson 의존성은 있지만 미사용 | `pom.xml`엔 있는데 실제 코드 어디에도 import조차 없음 |

세션과 레이트리밋이 이미 MongoDB에 저장되고 있어서 API 서버 자체는 stateless였다 — 수평 확장 자체는 문제가 없었다(다만 매 요청마다 Mongo를 치는 구조라, 고부하에서 DB가 먼저 죽을 리스크는 남아있다고 판단했다).

API(5001)와 WS(5002)가 동일 JVM/jar에서 뜨는 구조라는 것도 확인했다. 그래서 "API 전용 인스턴스"를 따로 만들 필요 없이, 같은 백엔드 인스턴스를 늘려서 `api-tg`, `ws-tg` 양쪽 타겟그룹에 동시에 등록하는 방식으로 확장하기로 했다.

## 5. Tomcat/Socket.IO 튜닝, 라운드별로

### 하나씩 바꿔야 했던 이유

t3.small은 2 vCPU였다. 스레드는 많다고 좋은 게 아니라는 걸 알고 있었다.

> "스레드는 많으면 컨텍스트 스위칭 비용으로 처리속도도 느려짐. 스레드가 적으면 CPU 자원을 최적으로 활용하지 못함."

RPS·p95·p99가 좋아지다가 꺾이는 지점을 찾는 게 목표였고, 로그인 bcrypt처럼 CPU 바운드 작업이 섞여 있으면 보통 코어 수의 4~8배 수준에서 한계가 온다는 걸 염두에 두고 매트릭스를 짰다.

### 내가 계획했던 12라운드 매트릭스

**1단계 — threads.max (accept-count/max-connections 고정)**

| 라운드 | threads.max | accept-count | max-connections | 비고 |
|---|---|---|---|---|
| 0 (베이스라인) | 10 | 10 | 50 | 최초 상태 |
| 1 | 25 | 100 | 8192 | 소폭 증가 |
| 2 | 50 | 100 | 8192 | |
| 3 | 100 | 100 | 8192 | Spring Boot 기본값 절반 |
| 4 | 200 | 100 | 8192 | Spring Boot 기본값 |
| 5 | 400 | 100 | 8192 | 기본값 2배, 오히려 나빠지는지 확인 |

**2단계 — accept-count (threads.max 고정)**

| 라운드 | accept-count | 비고 |
|---|---|---|
| 6 | 50 | |
| 7 | 100 | 기본값 |
| 8 | 200 | |
| 9 | 500 | 스파이크 특성상 순간 대기열이 커질 수 있어 넉넉하게 |

**3단계 — max-connections**

이게 처음부터 가장 의심스러운 값이었다. 50으로 잡혀 있던 Keep-Alive 커넥션 총량 제한이라, threads.max를 아무리 올려도 이 값이 낮으면 아무 소용이 없었다. Socket.IO 폴링·장기 연결도 있어서 넉넉하게 잡는 게 중요하다고 판단했다.

| 라운드 | max-connections | 비고 |
|---|---|---|
| 10 | 200 | |
| 11 | 1000 | |
| 12 | 8192 (기본값) | |

**4단계 — 최종 조합 검증**: 개별로 좋았던 값을 조합해도 좋다는 보장은 없다는 걸 알고 있었다(예: 스레드 100 + 커넥션 8192 조합이 예상외로 메모리 압박을 유발할 수도 있다). 실제로는 12라운드를 다 돌 시간이 없어서, 1단계 위주로 돌리고 2~3단계는 필요한 조합만 추려서 진행했다.

### 실제로 돌려본 결과

**VU 52 (베이스라인, threads=10)**: 완료율 94%, 5xx 0건. 이 규모에선 threads=10도 버텼다 — 아직 병목이 드러나지 않았다.

**VU 160~200 (threads=10 그대로)**: 완료율 60%, **5xx 174건 최초 발생**, login TTFB 최대 17.8초. 로그인에 bcrypt 같은 CPU 연산이 섞여 있어서 스레드 10개로는 순식간에 큐가 밀렸다.

**threads=30, min-spare=1, accept-count=100, max-connections=8192 (1차 튜닝)**: 완료율 60%→78%, 실패율 40%→22%로 확실히 개선됐다. 하지만 5xx 비율은 거의 그대로였고 로그인 지연도 여전했다 — 스레드 부족으로 "대기하다 죽는" 문제는 줄었지만, "처리는 시작했지만 오래 걸려 타임아웃"은 남아있었다. 이 단계에서 `min-spare=1`이 스파이크에 불리하다는 걸 직접 발견했다 — 평소엔 스레드 1개만 대기하다 트래픽이 몰릴 때마다 새로 생성해야 해서, 정확히 스파이크가 터지는 순간에 생성 비용까지 더해지는 구조였다.

**백엔드 3대 + 프론트 2대 증설, min-spare 10으로 조정**: 여기서 **5xx 0건을 달성**했다. 대신 파일 업로드 시나리오 실패율 80%가 새로 발견됐다(4장에서 짚었던 문제 #3이 실제로 발현된 것이었다).

**최종 결론**: `threads.max=30, accept-count=100, max-connections=8192`로 확정했다.

### Socket.IO acceptBackLog

Tomcat과 완전히 같은 성격의 병목을 별도로 하나 더 찾았다 — `socketConfig.setAcceptBackLog(10)`. 500으로 올리자고 코드팀에 요청했다.

판단 기준으로는 `net.core.somaxconn`(OS 커널 값)이 요청값보다 작으면 그쪽이 우선 적용된다는 걸 알고 있어서 먼저 확인했는데, 이미 4096으로 넉넉해서 별도 조치는 필요 없었다. 실측은 `nstat -az | grep ListenOverflows`(또는 `netstat -s | grep -i listen`)로 오버플로우 카운터를 확인하는 방식을 썼다 — 0이면 충분, 계속 증가하면 부족하다는 신호다.

실제로 스파이크 테스트 중 138건의 SYN drop이 확인됐는데, `acceptBackLog=500` 배포 시점과 겹쳐있어서 원인을 조사했고, 결국 배포 시점을 확인한 뒤 해소된 것으로 정리했다.

## 6. DB/Redis 성능 튜닝

### MongoDB

즉시 할 수 있는 것부터 손을 댔다.

1. **EBS 볼륨 IOPS/처리량 상향**: 디스크 I/O가 원인일 때 가장 빠른 해법이라 판단해서, gp3 볼륨 IOPS를 3000→6000~8000, 처리량을 125MB/s→250MB/s로 올렸다. 다운타임 없이 즉시 적용되고 재부팅도 필요 없어서 리스크가 거의 없었다.
2. **WiredTiger 캐시 크기 명시**: t3.small이 2GB 메모리인데, 기본 캐시 공식 `(전체메모리-1GB)*0.5`를 적용하면 캐시가 0.5GB밖에 안 된다는 걸 계산해보고 알았다. `storage.wiredTiger.engineConfig.cacheSizeGB: 1.0`로 명시적으로 늘렸다.
3. **Replica Set 구성 (2대: Primary+Secondary)**: AMI 사용 금지 규정 때문에 User Data 부트스트랩 스크립트로 두 번째 노드를 직접 구축했다. `MONGO_URI`에 `readPreference=secondaryPreferred`를 추가해 읽기 분산을 검토했지만, **최종적으로는 이 옵션을 추가하지 않기로 결정**했다.

### Redis

메모리/삭제정책을 점검했고, 다음을 적용했다.

```
appendfsync everysec → appendfsync no
```

## 7. 배포하면서 겪은 삽질들

부하테스트 결과가 이상할 때마다, 실제 원인은 코드보다 배포 설정 실수인 경우가 압도적으로 많았다. 겪은 순서대로 기록해둔다.

### 7-1. `FILE_STORAGE_TYPE` 환경변수 누락

S3 버킷과 IAM 권한을 다 세팅해놓고 이미지 업로드를 해봤는데 S3 콘솔에 객체가 0개였다. `.env`에 `S3_BUCKET`, `AWS_REGION`은 있는데 정작 **`FILE_STORAGE_TYPE`이 빠져있어서 기본값 `local`로 계속 동작 중**이었다. 로컬 `uploads/chat/`, `uploads/profiles/` 폴더에 500개 넘는 파일(각 1MB, 합계 1GB+)이 쌓여있는 걸 확인하고서야 확신할 수 있었다. `.env`에 `FILE_STORAGE_TYPE=s3`를 추가하고 재시작해서 해결했다.

### 7-2. `.env` 수정 후 재시작 누락

`spring.mongodb.uri=${MONGO_URI}` 같은 환경변수는 기동 시 한 번만 읽힌다는 걸 알고는 있었지만, 급한 마음에 `.env` 값만 바꾸고 재시작을 안 한 채 재테스트해서 몇 차례 헛다리를 짚었다. 이후로는 "값을 바꾸면 반드시 재시작 → 재시작 시각 확인(`ps -o lstart=` 또는 `docker inspect --format '{{.State.StartedAt}}'`)으로 실제 반영 여부부터 검증한다"는 원칙을 스스로 세웠다.

### 7-3. `target/classes` vs `src/main/resources` 혼동

라운드별 A/B 테스트를 빠르게 돌리려고 `target/classes/application.properties`(빌드 산출물)만 고쳐서 재컴파일 없이 재기동했다. 이게 EC2 로컬에만 유효하고 `mvn clean`하면 사라진다는 걸 알고 있었기에, 최적값을 찾은 뒤엔 반드시 `src/main/resources/application.properties`(진짜 소스)에 반영해 커밋하는 걸 마지막 단계로 챙겼다.

### 7-4. `CORS_ALLOWED_ORIGINS` 변수명 오타

코드는 `${CORS_ALLOWED_ORIGINS:*}`를 읽는데 `.env`엔 `APP_CORS_ALLOWED_ORIGINS`로 되어 있어서 매칭이 실패하고, 조용히 기본값 `*`(전체 허용)로 대체되고 있었다. 기능은 안 깨졌지만(오히려 더 허용적이었으니) 의도했던 제한이 전혀 안 걸리고 있다는 걸 뒤늦게 알아채고 변수명을 수정했다.

### 7-5. `SOCKETIO_SERVER_ORIGIN` 끝 슬래시

`https://chat.goorm-ktb-005.goorm.team/`처럼 끝에 `/`가 붙어있으면 브라우저의 실제 `Origin` 헤더(끝 슬래시 없음)와 글자 단위로 불일치해 CORS 체크가 실패할 수 있다는 걸 알게 됐다. same-origin 구조라 영향은 제한적이었지만, Socket.IO 폴링 폴백 시나리오에서 재연결 실패로 이어질 가능성이 마음에 걸려서 슬래시를 제거했다.

### 7-6. Mongo 인증 실패 디버깅

`mongosh` 접속 시 `Authentication failed`가 떴다. 계정을 어느 DB 컨텍스트(`admin` vs `bootcamp-chat`)에서 만들었느냐에 따라 `authSource` 파라미터 유무가 갈린다는 걸 확인하고, `db.getUsers()`로 실제 계정·역할을 확인한 뒤 `?authSource=admin`을 붙여서 해결했다. 이 과정에서 DB 자체는 첫 쓰기 시점에 자동 생성되므로 미리 만들 필요가 없다는 것도 새로 알게 됐다 — 계정 권한만 정확히 맞추면 됐다.

### 스파이크 테스트 최종 결과를 보면서

시나리오 시작 184회 중 정상 종료 165회, 오류 종료 19회로 **성공률 89.7%**를 기록했다. **5xx는 0건**이었다. 핵심 웹 지표로는 TTFB p95 421ms, FCP p95 789ms, **LCP p95 1236ms**였는데, 초반 4~6초대에서 대폭 개선된 수치였다. 401은 184건으로 VU 수와 정확히 일치해 정상 흐름이었고, 404는 22건으로 낮은 수준이었다.

남은 실패 19건은 전부 `URL_MISMATCH`였다. 로그를 뜯어보니 방 입장 API(200)와 WebSocket 연결(`Open WebSockets: 1`)은 성공하는데, 화면 라우팅이 5초 판정 기준을 살짝 넘겨 실패로 잡히는 패턴이었다. `Current URL`(에러 캡처 시점)을 확인해보면 이미 정확한 방 URL로 가 있는 경우가 많아서, "아예 안 됨"이 아니라 "판정 기준보다 조금 늦게 됨"에 가깝다고 결론 내렸다. `massMessageScenario`(95%)와 `fileUploadScenario`(96%)에서만 나타나고 로그인·방 생성은 100%였던 걸 보고, **사람이 몰려있는 방에 입장할 때만** 발생하는 패턴으로 범위를 좁혔다.

### 스파이크 구간 인프라 지표를 보면서 (Grafana)

CPU는 mongodb 인스턴스가 다른 쪽(api+next ~40%, redis ~25%)보다 뚜렷하게 높게 튀었다(~57%) — 다음 대규모 테스트의 병목 1순위 후보로 적어뒀다. System Load Average는 0에서 0.65~0.7까지 튀었다가 수 분 안에 평시 수준으로 회복됐다 — 스파이크를 버티고 넘어갔다는 뜻이었다. Filesystem Usage는 전 인스턴스 5~27%로 여유가 충분했고, Network Traffic도 최대 ~2.7MB/s로 대역폭 여유가 많았다. Redis 호스트에서 Disk I/O 스파이크(~2.5MB Read)가 보였는데, Redis 자체 영속성은 꺼뒀으니 OS 레벨 다른 활동(로그, 에이전트)으로 추정했지만 완전히 규명하지는 못했다.

### "핫 방" 쏠림 — 원인을 파고든 과정

`e2e/actions/chat.actions.js`의 `joinRandomChatRoomAction`을 직접 코드로 확인했다.
```javascript
const count = await chatRoomButtons.count();
const randomIndex = Math.floor(Math.random() * count);
await chatRoomButtons.nth(randomIndex).click();
```
"무작위"라고 되어 있지만 실은 **화면에 렌더링된 방 목록 안에서만 랜덤**이라는 걸 발견했다. 방 목록이 최신순이나 제한된 개수로 노출되는 구조라면, 실제로는 소수의 인기 방에 트래픽이 쏠릴 수밖에 없는 구조였다. Mongo 로그로 실제 확인해보니, 같은 room ID(`6a7bb317...`)에 백엔드 3대 전부에서 짧은 시간 안에 여러 유저가 몰려 입장한 기록이 크로스 인스턴스 로그 대조로 확인됐다. 이 방은 이미 메시지 30건 이상이 누적된(`hasMore: true`) 명백한 핫스팟이었고, 방에 사람이 많을수록 메시지 브로드캐스트 fan-out 비용이 커져 라우팅 지연으로 이어졌을 가능성이 유력하다고 판단했다.

이 진단 과정에서 내가 썼던 방법을 정리하면:
1. Playwright 콘솔로그·스크린샷·네트워크 실패 캡처를 시나리오에 추가 (`page.on('console')`, `page.on('pageerror')`, `page.on('requestfailed')`, 실패 시 `page.screenshot()`)
2. 실패 시각과 room ID로 **백엔드 3대 전부**의 로그를 동시에 grep해 크로스 인스턴스 상태를 대조 — 이게 가장 결정적인 진단 방법이었다
3. ALB 액세스 로그를 활성화해 "요청이 ALB까지는 왔는지" 객관적으로 확인
4. 세션/JWT 만료 시간 확인 (JWT 24시간, 세션 TTL 30분 — 둘 다 시나리오 소요시간보다 충분히 길어서 원인에서 기각)

## 11. 내가 배운 것들

1. **"배포했다"와 "실제로 반영됐다"는 전혀 다른 말이다.** `.env`만 바꾸고 재시작을 안 하거나, 코드 수정 후 jar 재빌드 없이 재테스트해서 몇 차례 헛다리를 짚었다. 매 라운드마다 배포 상태(재시작 시각, 실제 코드 반영 여부)를 먼저 확인하는 습관이 자리 잡기까지 생각보다 시간이 걸렸다.
2. **인프라 지표가 깨끗해도 애플리케이션 레벨 실패는 별개로 확인해야 한다.** Grafana와 CloudWatch가 정상으로 나와도, 특정 시나리오(파일 업로드, 방 입장 라우팅)는 계속 실패할 수 있다는 걸 직접 겪고 나서야 체감했다.
3. **라운드마다 DB/Redis/S3 데이터를 초기화하지 않으면 비교가 왜곡된다.** 테스트 계정은 매번 `loadtest_{timestamp}_{randomId}` 형태로 고유 생성되어 재사용 충돌은 없었지만, 데이터 누적과 레이트리밋 잔존 상태가 다음 라운드 결과를 왜곡시킬 수 있다는 걸 뒤늦게 알았다.
4. **여러 인스턴스의 로그를 정확한 타임스탬프·room ID로 동시에 대조하는 게 가장 확실한 진단 방법이었다.** 크로스 인스턴스 브로드캐스트가 실제로 작동하는지, 특정 방에 트래픽이 쏠리는지는 이 방법이 아니었으면 끝까지 추측에 머물렀을 것이다.
5. **권장값과 실제 적용값은 갈릴 수 있고, 그건 자연스러운 일이다.** 다만 그 결정을 내린 이유를 그때그때 기록해두지 않으면, 나중에 회고할 때 "왜 이렇게 했는지"를 복원하는 데 오히려 더 많은 시간이 든다는 걸 이번에 확실히 배웠다.

## 12. 끝내 발견하지 못한 문제

### S3Client 커넥션 풀 병목

시간이 부족해 끝까지 손대지 못했지만, 나중에 돌이켜보니 짚고 넘어갔어야 할 부분이다. S3Client의 동시 연결 수는 기본 50인데, 여러 VU가 동시에 파일을 업로드하면 동시 S3 PUT 요청이 50개를 넘어가고, 51번째부터는 커넥션이 반환될 때까지 큐에서 대기하게 된다. 이 대기 시간 동안 해당 HTTP 요청, 그리고 그 뒤에 이어지는 메시지 생성·브로드캐스트까지 같이 지연되면서, 10초 안에 메시지가 화면에 안 뜨는 현상으로 나타났을 가능성이 크다. S3StorageConfiguration의 S3Client 빈에 커넥션 풀을 명시적으로 늘렸어야 했는데, 이번엔 거기까지 가지 못했다.
