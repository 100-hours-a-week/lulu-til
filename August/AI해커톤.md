## 1. 목표와 원칙

기획 초반에 메모에 가장 먼저 적어둔 원칙은 이거였다.

> "이론적으로 옳은 아키텍처와 3일 안에 완성 가능한 아키텍처는 다르다. 과설계보다 안정적 완성을 우선한다."

이 원칙이 생기기 전까지는 인스타그램 공식 API 가능성을 따져보는 데만 꽤 긴 시간을 썼다. 원칙이 명확해진 뒤부터는 매 결정 앞에서 "이게 3일 안에 되는가"를 가장 먼저 물었고, 덕분에 기능을 5개에서 3개로, 다시 2개로 줄이는 과정에서도 미련 없이 쳐낼 수 있었다.

평가 기준으로 삼은 건 다음 다섯 가지였다: 공식 API로 접근 가능한가, 3일 내 구현 가능한가, 문제 해결에 직접 기여하는가, 사용자 가치가 명확한가, 기능 목적을 한 문장으로 설명할 수 있는가.

## 2. 아키텍처(및 주제) 결정과 그 이유

### 왜 인스타그램에서 디스코드로, 다시 카카오톡으로 옮겼는가

인스타그램 심리분석 앱에서 출발했지만, Instagram Basic Display API가 2024년 말 종료되어 개인 계정에 공식적으로 접근할 방법이 아예 없다는 걸 확인했다. 비즈니스/크리에이터 계정 전환 + Facebook 페이지 연결 + 60일 심사라는 전제조건은 3일짜리 해커톤에 물리적으로 맞지 않았다.

디스코드는 공식 Bot API가 열려 있어서 괜찮은 대안이었지만, 논의를 거듭하며 "관계 손절을 망설이는 사람"이라는 더 날카로운 문제의식을 발견했고, 카카오톡 대화 내보내기(export) 파일을 활용하는 쪽으로 최종 방향을 잡았다. **공식 API로 데이터에 접근 가능한가**를 가장 먼저 검증하는 습관이 이 과정에서 자연스럽게 자리 잡았다.

### PRQC 척도를 채택한 이유, 그리고 거기서 멈추지 않은 이유

경쟁 서비스들은 답장 속도·이모티콘 사용량 같은 단편적 신호를 감으로 조합해 점수화하고 있었다. 이걸 "심리학 연구에서 검증된 척도"로 대체하면 신뢰도를 높일 수 있겠다고 판단해 PRQC(Fletcher et al., 2000) 6개 구성요소를 채택했다.

다만 여기서 멈추지 않고 한 겹 더 파고든 게 이번 기획에서 가장 중요했던 지점이라고 생각한다. PRQC는 원래 본인이 직접 응답하는 자가보고(self-report) 척도인데, 우리는 제3자(AI)가 텍스트만 보고 추론하는 방식으로 쓰고 있다는 걸 인지했다. 이 방법론적 허점을 숨기는 대신, 근거 인용·신뢰도 지수·주간 자가보고 체크인으로 보정하는 구조를 설계에 넣었다. "이 정도면 과학적으로 검증됐다"고 오버클레임하지 않고, "패턴을 관찰해주는 보조 도구"로 정직하게 포지셔닝하는 쪽을 선택했다.

### EC2 단일 인스턴스 + Caddy — ALB를 포기한 이유

처음엔 private subnet, NAT Gateway, ALB, ACM까지 포함한 정교한 구조를 짰었다. 하지만 시간 제약과 인프라 비중요 이슈를 고려해 t3.xlarge EC2 한 대에 프론트·백엔드·DB·AI를 Docker Compose로 올리는 방식으로 되돌렸다.

이 결정에서 특히 중요했던 포인트는 ALB와 ACM의 관계였다. **ACM 인증서는 EC2에 직접 설치할 수 없고 ALB/CloudFront 같은 AWS 통합 서비스에만 붙는다**는 걸 확인하고 나서, ALB를 뺀다면 ACM도 자연히 포기해야 한다는 결론에 도달했다. 그런데 카카오 로그인 Redirect URI는 신뢰된 HTTPS 도메인이 필요했기 때문에, **Caddy로 Let's Encrypt 인증서 발급·갱신을 자동화**하는 방식으로 대체했다. Nginx+Certbot보다 설정이 훨씬 짧아서(Caddyfile 3줄) HTTPS 세팅에 쓰는 시간을 거의 0에 가깝게 줄일 수 있었다.

```
[사용자] → Route53 (도메인) → EC2 (t3.xlarge, Elastic IP)
                                   │
                            Caddy (Let's Encrypt 자동 발급)
                            ├─ 80/443 포트만 외부 노출
                            ├─ / → Frontend 컨테이너
                            └─ /api/* → Backend 컨테이너
                                            │
                                            ├─ MySQL 컨테이너 (내부망만, 외부 미노출)
                                            └─ FastAPI(AI) 컨테이너 (내부망만, 외부 미노출)
```

### 공유하기(Kakao Share API) 기능을 뺀 이유

처음엔 "AI가 조언을 넘어 실행까지 한다"는 해커톤 주제에 맞추려고 카카오톡 공유하기 API로 메시지를 원클릭 전달하는 기능을 핵심 기능 3번으로 넣었다. 하지만 카카오톡이 개인 채팅방에 대한 자동 발송·알림 제어 공식 API를 제공하지 않는다는 걸 재확인하면서, 실제로는 "클립보드 복사 후 수동 붙여넣기" 수준까지만 가능하다는 걸 인정했다. 이걸 "실행" 기능으로 포장하는 건 기술적 과장이라고 판단해 과감히 제외했고, 대신 서비스 정체성 자체를 "관계 실행 에이전트"에서 **"관계 판단 지원 서비스"**로 조정했다. "할 수 있는 척"보다 "할 수 없는 것을 정직하게 인정"하는 쪽이 심사 질문에도 더 방어 가능하다고 봤다.

## 5. 핵심 기능 축소, 라운드별 기록

### 왜 기능을 단계적으로 줄여야 했는가

강사 피드백 "핵심 기능이 너무 많다"를 받고 나서, 기능이 많다고 설득력이 높아지는 게 아니라는 걸 체감했다. 각 기능이 "3일 안에 안정적으로 구현 가능한가 + 정체성과 정확히 맞물리는가"를 기준으로 하나씩 재검증하는 과정을 거쳤다.

### 라운드별 기능 변화

| 라운드 | 기능 구성 | 비고 |
|---|---|---|
| 0 (최초) | 관계 수치화, 답변 추천, 상담 챗봇, 공유하기, 주간 리포트 (5개) | 각 기능을 개별적으로 설계, 기능 간 통합 고려 안 됨 |
| 1 | 관계 수치화&추이, AI 상담 챗봇(답변추천 흡수), 실행 연결(공유하기) (3개) | 겹치는 기능(답변추천+상담, 수치화+리포트) 통합 |
| 2 (최종) | 관계 수치화&추이 트래킹, AI 상담 챗봇 (2개) | 공유하기의 기술적 한계(4카카오톡 공유 API) 재확인 후 제외 |

### 실제 재구성 결과

**라운드 1 (5→3 통합)**: 기존 "주간 리포트(이메일)"를 독립 기능으로 두지 않고, "관계 수치화" 기능 안에 **주간 체크인 + 시계열 추적**으로 흡수시켰다. 이 통합이 강사 피드백 1번(1회성 콘텐츠 문제)에 대한 직접적인 해법이 됐다 — 관계를 "상태"가 아니라 "과정"으로 재정의하면서, 점수 하나가 아니라 추이 자체가 핵심 가치라는 메시지가 명확해졌다.

**라운드 2 (3→2 통합)**: 공유하기 기능을 실제로 구현했을 때의 기술적 실효성을 재검토했다. 카카오톡 공유 API를 쓰더라도 결국 "클립보드 복사 + 수동 붙여넣기" 수준이라는 걸 인정하고 제외했다. 이 결정으로 "실행"이라는 단어를 정체성 문구에서도 걷어내야 했는데, 처음엔 아쉬웠지만 오히려 **AI의 한계를 인정하는 설계가 신뢰성 피드백(강사 피드백 2번)에 대한 답변 논리와 일관성을 갖게 됐다.**

**최종 결론**: 핵심 기능은 "관계 수치화 & 추이 트래킹"과 "AI 상담 챗봇" 2개로 확정했다.

### 카카오 로그인 OAuth 단일화

로그인 방식도 처음엔 이메일+카카오 두 가지를 고려했지만, 어차피 분석 대상 데이터가 카카오톡 export 파일이라는 점에 착안해 **카카오 OAuth 단일 로그인**으로 단순화했다. 회원가입 폼 자체가 사라지면서 화면 수가 줄었고(로그인 화면 1개 + 최초 동의 화면 1개), 개발 범위도 함께 줄었다.

## 6. 데이터·인프라 설계

### PRQC 채점 스키마

LLM 채점 결과가 구성요소별 1~7 정수 필드를 벗어나지 않도록 Pydantic 스키마로 강제하기로 했다. 구성요소마다 별도 프롬프트·few-shot 예시를 LangGraph 노드로 분리해, 특정 구성요소에서 편차가 발견되면 해당 노드만 수정 가능한 구조로 설계했다.

```
FastAPI (/score 엔드포인트)
  │
LangGraph
  ├─ Node: PRQC 구성요소별 채점 (6개, few-shot + LLM 호출 → Pydantic 파싱)
  ├─ Node: 절단점 기준 위험 구성요소 판별
  └─ Node: 결과 반환 → Spring 백엔드로 응답
LangSmith: 전체 노드 실행 트레이싱, 반복 채점 편차 모니터링
```

### 인프라

- EC2 t3.xlarge 1대 + Docker Compose (frontend, backend, mysql, ai 4개 컨테이너)
- Route53 도메인 → EC2 Elastic IP 직결
- Caddy로 HTTPS(Let's Encrypt) + 리버스 프록시(/ → frontend, /api/* → backend) 처리
- MySQL/FastAPI는 `expose`만 사용해 호스트 포트 미노출, Security Group도 80/443/22(제한)만 개방

## 7. 기획 과정에서 발견한 "삽질"

실제 서버 배포 전이라 코드 레벨 삽질은 아직 없지만, 기획 단계에서 반복적으로 바로잡아야 했던 설계 불일치들이 있었다.

### 7-1. Frontend SSR vs React CSR 불일치

인프라 전략 문서에는 "Frontend SSR + EC2 별도 구동"이라고 되어 있었는데, 기술 스택엔 React.js(CSR 전제)로만 적혀 있었다. 이 불일치는 인프라 피드백 단계에서 발견했고, **아직 팀 내 최종 확정이 안 된 상태로 기획안에 "확인 필요 사항"으로 남겨뒀다.** CSR로 확정되면 EC2 대신 S3+CloudFront로 전환해 인프라 복잡도를 더 줄일 수 있다.

### 7-2. ACM+ALB 구조를 짰다가 통째로 되돌림

처음 인프라 설계는 private subnet, NAT Gateway, ALB, ACM, GitHub Actions+SSM 자동배포까지 포함한 정교한 구조였다. 하지만 "이게 3일 안에 되는가"를 다시 물어보니, GHCR+SSM 기반 private subnet 배포 자동화는 OIDC 연동·SSM Agent 설정·SG 허용까지 하나라도 어긋나면 반나절 이상 날아갈 수 있는 리스크였다. 결국 EC2 단일 인스턴스 + Caddy 구조로 전체를 되돌렸다.

### 7-3. "worst" 표현 — UX 카피 리스크를 뒤늦게 발견

초기 대시보드 설계에 "관계점수 worst 1·2·3등"이라는 표현이 있었는데, 실존 지인의 이름 옆에 낙인성 표현이 붙는 걸 화면 설계 피드백 단계에서야 인지했다. "주의가 필요한 관계"로 전면 수정했다.

## 11. 기획하며 배운 것들

1. **아이디어보다 "데이터 접근 가능성"을 먼저 검증해야 한다.** 인스타그램 아이디어에 쏟은 초기 시간이, 공식 API 유무를 먼저 확인했다면 아낄 수 있었던 시간이었다.
2. **비판적 피드백은 방어할 대상이 아니라 설계를 더 단단하게 만드는 재료다.** "1회성 아니냐", "신뢰성 있냐"는 질문에 대응하면서 오히려 서비스의 핵심 가치(추이 추적, 근거 기반 분석)가 또렷해졌다.
3. **"할 수 있는 척"보다 "할 수 없는 걸 인정"하는 설계가 더 방어 가능하다.** 공유하기 기능을 빼고 정체성 문구까지 수정한 결정이, 당장은 아쉬워도 전체 논리의 일관성을 높였다.
4. **인프라는 이상적으로 옳은 구조가 아니라 제한된 시간 안에 완성 가능한 구조를 기준으로 판단해야 한다.** ALB·NAT Gateway·자동배포까지 포함한 정교한 설계를 통째로 되돌린 경험이 가장 크게 체감됐다.
5. **화면 설계 단계에서야 발견되는 리스크(낙인성 카피 등)가 있다.** 기능 정의서만 봐서는 안 보이던 문제가, 실제 화면으로 옮기는 과정에서 드러났다.
