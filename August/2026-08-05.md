#### | Resilience와 장애 전파 방지

##### 장애 전파 방지란?

> 💡 장애 전파 방지는 **장애를 완전히 없애는 기술이 아니라**, 장애가 발생해도 전체 시스템으로 퍼지지 않도록 **장애의 시간과 범위를 제한**하는 설계다.

- 장애가 발생한 부분을 감지한다.
- 장애가 발생한 부분에 추가적인 요청을 보내지 않는다.
- 하나의 장애가 다른 시스템의 자원을 소진하지 않게 한다.

##### Resilience (회복 탄력성)

시스템의 일부가 느려지거나 장애가 발생하더라도 **정상적인 기능을 제공하고 중요한 기능을 보호**하는 능력이다. 장애가 회복되면 점진적으로 정상 상태로 돌아가고, 그 과정에서는 일부 기능을 제한하거나 간소화한다.

> ⚠️ Resilience는 **모든 요청을 반드시 성공시키는 것이 아니다.** 전체 시스템이 무너지지 않도록, 일부 요청을 빠르게 실패시키거나 의도적으로 제외시키는 것도 Resilience의 일부다.

Spring에서는 특히 **resilience4j**라는 라이브러리가 이런 패턴들을 구현해서 제공한다.

##### 왜 장애 전파 방지가 필요한가?

**MSA(마이크로서비스 아키텍처) 환경**에서 특히 자주 적용되는 개념이며, 모노레포(mono repo) 구조에서도 유사한 개념이 차용되는 경우가 많다. 기준은 결국 **분산 시스템**이다.

분산 시스템에서는 **하나의 요청이 여러 서비스를 거쳐서 완성**된다. 만약 그중 하나의 서비스가 느려지면, 그 지연이 연쇄적으로 퍼져 전체 서비스 장애로 이어질 수 있다. 이런 현상을 **Cascading Failure(연쇄 장애)**라고 부른다.

##### 해결 방식 6가지

1. **기다리는 시간 제한하기 (Timeout)** — 응답하지 않는 서비스를 그대로 기다리면 스레드·커넥션이 계속 점유된다. 특정 시간 이상은 기다리지 않는다.
2. **들어오는 요청량 제한하기 (Rate Limiter / Load Shedding)** — 시스템이 처리할 수 있는 요청보다 많은 요청이 들어오면 거절한다. Rate Limiter는 요청이 들어오는 것 자체를 제한하고, Load Shedding은 이미 들어온 요청이 너무 많으면 버린다.
3. **실패한 요청을 무조건 반복하지 않기 (Retry)** — 일시적인 실패(파드 재생성, 네트워크 이슈 등)라면 재시도 정책을 잡되, 너무 많이 재시도하면 오히려 시스템에 부하를 만든다. 재시도 횟수·대상을 제한해야 한다.
4. **반복해서 실패하면 잠시 호출하지 않기 (Circuit Breaker)** — 특정 서비스가 계속 실패하면 이미 장애 상태라고 판단하고, 그 서비스로의 요청을 잠깐 멈추고 대기한다.
5. **자원을 나눠서 사용하기 (Bulkhead)** — 하나의 외부 서비스가 느려졌다고 해서 모든 커넥션·모든 스레드 풀·모든 자원이 그 서비스에 종속되면 안 된다.
6. **완전한 성공이 안 되면 제한된 기능 제공하기 (Fallback, Graceful Degradation)**

→ 이 6가지 방식을 Spring에서 구현한 라이브러리가 **resilience4j**다.

##### 인프라와 백엔드의 역할 구분

장애 전파 방지는 **인프라, 백엔드 둘 중 하나만 처리하는 게 아니라, 둘 다 함께 처리**해야 한다. 각 계층이 알고 있는 정보가 다르기 때문이다.

| 구분 | 인프라 영역 | 백엔드 영역 |
|---|---|---|
| 대표 구성 요소 | ALB, Nginx, Ingress, API Gateway, Kubernetes | Spring Boot, HTTP Client, DB Client |
| 알고 있는 정보 | IP, 연결, 요청 경로, 응답 코드, 요청량 | 사용자, 주문, 결제, 비즈니스 오류 |
| 주요 목적 | 전체 시스템으로 들어오는 트래픽 보호 | 특정 의존성과 비즈니스 기능 보호 |
| Timeout | 프록시 연결·응답 시간 제한 | 외부 API, DB, 메서드 실행 시간 제한 |
| Retry | 다른 서버 인스턴스로 제한적 재전송 | 예외와 응답의 의미를 판단해 재시도 |
| Circuit Breaker | 비정상 인스턴스를 대상에서 제외 | 특정 서비스 호출 자체를 일시 차단 |
| Bulkhead | 연결 수, Pod, 노드, 큐 격리 | 스레드 풀, Semaphore, 커넥션 풀 격리 |
| Rate Limiter | IP, 경로, API 단위 제한 | 사용자, 테넌트, 기능별 제한 |
| Fallback | 정적 오류 페이지, 캐시 응답 | 대체 데이터, 기능 축소, 명시적인 실패 |

> 💡 요약하면, **인프라는 트래픽과 연결을 보호**하고, **애플리케이션(WAS)은 비즈니스 로직과 실제 재시도 처리를 담당**한다.

##### 요청이 들어올 때의 체크리스트

```
요청이 들어온다
  1. 요청이 너무 많은 거 아닌지?          → Rate Limiter
  2. 너무 오래 기다리는 거 아닌가?          → Timeout
  3. 일시적인 실패인가?                   → Retry
  4. 계속 실패하는 거 아닌가?              → Circuit Breaker
  5. 특정 기능·서비스가 자원을 독점하는가?  → Bulkhead
  6. 정상 결과를 줄 수 없다면?             → Fallback
```

> ⚠️ 이 패턴들은 **서로를 대체하는 관계가 아니다.** 각기 다른 문제를 해결하며, 일반적으로 **여러 패턴을 조합해서 사용**한다.

##### 1. Rate Limiter

**시스템이 감당할 수 있는 범위까지만 요청을 받아들이는 장치다.** 허용 범위를 넘는 요청은 보통 **429 (Too Many Requests)**로 응답한다.

**해결하는 문제**: 서비스의 최대 처리량(RPS)보다 많은 요청은 결국 장애로 이어진다. 일정 수준을 넘으면 그냥 요청을 빠르게 거절하는 편이 시스템 안정성에 도움이 된다.

**인프라에서의 Rate Limit** — 요청을 시스템 입구에서 거절하는 방식으로 구현되는 경우가 많다.

```nginx
limit_req_zone $binary_remote_addr
    zone=api_rate_limit:10m
    rate=30r/s;

server {
    location /api/ {
        limit_req zone=api_per_ip burst=30 nodelay;
        limit_req_status 429;

        proxy_pass http://backend;
    }
}
```

**백엔드에서의 Rate Limit** — **비즈니스 기준**으로 제한해야 할 때 사용한다.

- 사용자당 이메일 인증을 1분에 5회로 제한한다.
- 사용자당 결제 시도를 1분에 10회로 제한한다.

서비스별로 RPS가 크게 차이 난다면, 가장 느린 서비스의 RPS를 기준으로 인프라 레벨에서 Rate Limit을 걸었을 때 다른 서비스들은 상대적으로 널널한 제한을 받게 되어 **자원 효율성이 떨어진다.** 이럴 때는 서비스별로 각각 Rate Limit을 걸 수 있다.

> ⚠️ **Rate Limit ≠ 동시 요청 수(Concurrency)**. Rate Limit은 "초당 몇 개의 요청을 허용할 것인가"이고, Concurrency는 "동시에 몇 개를 처리할 것인가"다. 예를 들어 Rate Limit이 100 RPS인데 요청 하나의 처리에 10초가 걸린다면, 시스템에서 실제로 동시에 처리 중인 요청 수는 최대 1000개까지 쌓일 수 있다(1초=100개, 2초=+100개, 3초=+100개...). 즉 **Rate Limit만으로는 느린 요청으로 인한 자원 고갈을 막기 어렵다** — 이때 **Bulkhead, Timeout**이 함께 필요하다.

##### 2. Timeout

**외부 서비스가 느릴 때, 무한히 기다리지 않고 시스템을 보호하는 시간 제한이다.**

**어떤 문제를 해결하는가?**
타임아웃이 없으면 외부 서비스가 응답하지 않을 때 요청 처리 스레드, HTTP 커넥션, DB 커넥션, 메모리, 요청 큐가 계속 점유되며 **자원 고갈**로 이어진다.

**인프라에서의 Timeout**

```nginx
location /api/ {
    proxy_connect_timeout 500ms;
    proxy_send_timeout    2s;
    proxy_read_timeout    2s;

    proxy_pass http://backend;
}
```

**백엔드에서의 Timeout** — 비즈니스 로직에 따라 **일관된 타임아웃이 아니라, 로직마다 다른 타임아웃**을 적용해야 할 수 있다.

> ⚠️ **Timeout은 작업을 중단한다는 의미가 아니다.** 요청이 실제로 처리되고 있는 도중에 타임아웃이 발생할 수도 있으며, 일반적으로는 해당 요청을 종료시키는 게 맞는 처리다.

분산 시스템·외부 요청 시스템(결제, 주문)에서 타임아웃을 다룰 때는 특히 주의가 필요하다.

```
1. 결제 서비스가 결제를 완료
2. 주문 서비스를 호출
3. 주문 서비스에서 타임아웃 발생
   a. 주문 서비스가 Retry
   b. 결제 서비스는 주문 서비스의 완료를 기다리지 않을 수도 있음
```

타임아웃이 **하나의 비즈니스 로직 중간에** 발생하는 경우, 전체 로직이 한 번에 취소되면 깔끔하지만, 실제로는 전체 로직이 여러 서비스·여러 데이터베이스에 걸쳐 있는 경우가 많아 **요청에 대해 데이터가 변화하는 방식에 일관성이 없어질 수 있다.** 그래서 timeout을 설정할 때는 **Retry 정책**과 **멱등성(Idempotency)**을 함께 고려해야 한다.

> ⚠️ **타임아웃을 너무 짧게 설정하면**, 정상적인 요청도 타임아웃을 발생시킬 수 있다. 그 결과 Retry가 너무 많이 증가하고, 사용자 오류율도 함께 증가할 수 있다.

##### 3. Retry

**일시적인 실패일 가능성이 있을 때, 요청을 제한된 횟수만큼 다시 시도하는 방식이다.**

**어떤 문제를 해결하는가?**
분산 시스템에서는 네트워크, 파드 재생성, 노드의 재생성·초기화처럼 **일시적인 실패 가능성이 항상 존재**한다. 이런 오류들은 요청 자체나 처리 로직의 문제가 아니기 때문에, 재시도로 해결하려는 것이다.

**재시도를 하면 안 되는 경우** — 다시 요청해도 결과가 달라지지 않는 오류는 재시도하지 않는다.

- 잘못된 요청 (예: 회원가입 요청 값 자체가 잘못된 경우)
- 인증 실패 (재시도해도 계속 실패)
- 권한 부족
- 비즈니스 규칙 위반

**인프라에서의 Retry**

```nginx
location /api/ {
    proxy_next_upstream
        error
        timeout
        http_502
        http_503
        http_504;

    proxy_next_upstream_tries 2;
    proxy_next_upstream_timeout 1s;

    proxy_pass http://backend;
}
```

**백엔드에서의 Retry (resilience4j)**

```yaml
# resilience4j 설정
retry:
  instances:
    payment:
      max-attempts: 3
      wait-duration: 200ms
    order:
      max-attempts: 2
```

이후 코드 레벨에서 실제 재시도 로직을 구현한다.

**Retry Storm**
재시도가 폭풍처럼 많아지는 현상을 말한다. 이를 막기 위해 재시도에 몇 가지 제약을 걸어둔다.

- **Exponential Backoff**: 재시도할수록 대기 시간을 점점 늘린다.
- **Jitter**: 재시도 대기 시간에 무작위 값을 추가한다 (예: 1차 → 85ms, 2차 → 405ms, 3차 → 200ms).
- **재시도 횟수 제한**

**여러 계층에서의 재시도 — 주의할 점**

```
하나의 요청: Nginx → 주문 서비스 → 결제 서비스 → DB

만약 각 계층이 모두 재시도를 한다면:
Nginx 재시도 × 주문 재시도 × 결제 재시도 × DB 재시도
→ Retry Storm
```

> ⚠️ **요청 하나에는 하나의 계층에서만 재시도를 하는 것이 안전하다.**

**재시도 정책을 설정할 때는 성공률을 관찰해야 한다.**

- Retry: 최초 요청 성공 여부, Retry 요청 성공 여부(횟수별로 언제 성공하는지), 전체 Retry 횟수, Retry로 추가된 트래픽을 일반 트래픽과 분리해서 관측해야 한다.
- 재시도 정책을 잡고 시행했는데 **재시도 성공률이 계속 떨어진다면, 재시도 정책 자체를 고칠 게 아니라 애플리케이션 로직의 문제를 먼저 확인**해야 한다.

> ⚠️ **Retry는 장애를 복구하는 기술이 아니다.** 잘못 사용하면 오히려 부하를 증폭시키는 역할만 하게 될 수 있다.

##### 4. Bulkhead

**하나의 기능이나 의존성이 전체 자원을 사용하지 못하도록 자원을 분리하는 방법이다.**

**해결하는 문제**: 주문 서비스가 결제 서비스, 재고 서비스, 알림 서비스를 호출한다고 할 때, 이 모든 호출이 **같은 스레드 풀**을 사용하면 상대적으로 덜 중요한 **알림 서비스의 장애가 전체 요청의 장애로 이어질 수 있다.**

**백엔드 영역에서의 Bulkhead**

- **Semaphore Bulkhead**: 동시에 실행할 수 있는 요청 수를 제한한다 (예: 결제 서비스 호출 개수 최대 20개, 주문 서비스 호출 개수 최대 10개). 서비스별로 사용할 수 있는 자원의 최대 수량을 정해두고, 허용된 수를 넘으면 거절한다.
- **Thread Pool Bulkhead**: 의존성별로 Thread Pool과 Queue 자체를 분리한다 (결제 전용 스레드 풀, 재고 전용 스레드 풀, 알림 전용 스레드 풀 등).

```yaml
# resilience4j 설정
bulkhead:
  instances:
    payment:
      max-concurrent-calls: 20
      max-wait-duration: 10
    notification:
      max-concurrent-calls: 30
```

**인프라에서의 Bulkhead**

```nginx
upstream backend {
    server backend-1:8080 max_conns=100;
    server backend-2:8080 max_conns=100;
}
```

k8s에서는 **Pod Anti-affinity**, **Topology Spread**, 또는 특정 서비스에 노드를 몰아두는 방식으로도 격리를 구현할 수 있다.

##### 5. Circuit Breaker

**계속 실패하는 서비스에 요청을 보내지 않고 빠르게 실패시키는 장치다.**

> 💡 서킷 브레이커는 외부 서비스가 실패하거나 느리게 호출될 때 잠시 호출을 차단하는 역할을 하며, **누전 감지기(누전 차단기)**에 비유할 수 있다. 장애가 현재 서비스까지 전파되지 않게 막는 역할이다.

```
주문 서비스 → 결제 서비스 호출
   → 결제 서비스 응답 지연
   → 주문 서비스에 스레드가 계속 응답 대기
   → 계속 실패하면 서킷 브레이커 Open
        → 타임아웃 증가 / Retry 증가 / 내부 트래픽 폭증을 막음
```

외부 서비스의 실패율이 높거나 응답 시간이 지연되면, **실제 호출을 중단**시키고 요청을 **Fallback**으로 처리한다.

**서킷 브레이커의 3가지 상태**

| 상태 | 설명 |
|---|---|
| **Closed** (정상) | 서킷브레이커가 닫혀 있어 호출을 허용한다. 최근 호출 결과(성공/실패/느린 호출 개수)를 기록하며, 임계치에 도달하면 **Open**으로 전환된다. |
| **Open** (장애 감지) | 외부 서비스를 실제로 호출하지 않는다. 대신 Fallback 반환, 캐시 데이터 반환, 기능 임시 비활성화, 작업을 Pending 상태로 전환하는 등의 방식으로 대응한다. |
| **Half-Open** (회복 확인) | 외부 서비스가 회복됐는지 확인하는 상태다. 모든 요청을 한 번에 허용하지 않고, **설정한 개수만 테스트 요청으로 허용**한다. 테스트 요청의 실패율·느린 호출 비율을 비교해서 정상이면 Closed로, 비정상이면 다시 Open으로 전환한다. |

**Spring(resilience4j) 예시**

```yaml
resilience4j:
  circuitbreaker:
    instances:
      payment:
        slidingWindowType: COUNT_BASED
        slidingWindowSize: 20
        minimumNumberOfCalls: 10

        failureRateThreshold: 50

        slowCallDurationThreshold: 800ms
        slowCallRateThreshold: 50

        waitDurationInOpenState: 10s
        permittedNumberOfCallsInHalfOpenState: 3

        automaticTransitionFromOpenToHalfOpenEnabled: false

        eventConsumerBufferSize: 100
```

```java
public class PaymentClient {

    private static final String CIRCUIT_BREAKER_NAME = "payment";

    private final RestClient paymentRestClient;

    @CircuitBreaker(
        name = CIRCUIT_BREAKER_NAME,
        fallbackMethod = "paymentFallback"
    )
    public PaymentResponse pay(PaymentRequest request) {
        return paymentRestClient.post()
            .uri("/payments")
            .body(request)
            .retrieve()
            .body(PaymentResponse.class);
    }

    private PaymentResponse paymentFallback(
        PaymentRequest request,
        Throwable throwable
    ) {
        throw new PaymentTemporarilyUnavailableException(
            "결제 서비스를 일시적으로 사용할 수 없습니다."
        );
    }
}
```

**서킷브레이커가 열렸을 때 운영자의 대응 순서**

1. **지표 확인**: 현재 상태, 실패율, 느린 호출 비율을 확인한다.
2. **원인 파악**: 왜 서킷브레이커가 열렸는지, 코드 레벨·로그(예: Loki)·DB 커넥션 상태를 확인한다.
3. **서킷을 바로 강제로 닫지 않는다**: 외부 서비스가 아직 완전히 복구되지 않은 상태에서 서킷을 강제로 닫으면, **대기 중이던 요청이 한 번에 몰려 들어와** 다시 장애를 일으킬 수 있다. Half-Open 상태로 소량의 테스트 요청만 흘려보내면서 점진적으로 확인해야 한다.

---

##### 6. Fallback

**정상적인 결과를 제공할 수 없을 때, 전체 실패 대신 제한된 결과를 제공하는 방법이다.**

**Fallback을 하면 안 되는 경우**: 결제, 송금, 주문처럼 **비즈니스 로직에 상당한 영향을 끼치는 서비스**는 실패했을 때 애매하게 대체 결과를 주기보다 **전체 실패로 명확히 처리**해야 한다. Fallback은 **안전하게 제공 가능한 대체 결과가 있을 때만** 사용하는 기술이다.

---

##### 패턴별 역할 정리

| 패턴 | 해결하려는 문제 | 핵심 동작 |
|---|---|---|
| Rate Limiter | 처리 용량보다 많은 요청 | 일부 요청 거절 |
| Timeout | 끝없이 기다리는 요청 | 대기 시간 제한 |
| Retry | 일시적인 실패 | 제한적으로 다시 시도 |
| Circuit Breaker | 지속적으로 실패하는 의존성 | 호출 자체를 일시 차단 |
| Bulkhead | 하나의 장애가 모든 자원을 사용 | 자원과 동시성 격리 |
| Fallback | 정상 결과 제공 불가 | 제한된 대체 결과 제공 |

> 💡 **장애 전파 방지는 실패를 숨기는 것이 아니라, 실패를 빠르게 감지하고 제한된 영역 안에서 끝내는 것이다.**

### 🗨️ 오늘의 회고

- 오늘은 지금까지 배운 인프라(k8s, HPA/VPA/CA, PLG Stack, 부하테스트) 지식이, **애플리케이션 코드 레벨의 장애 대응 패턴과 어떻게 맞닿아 있는지** 확인하는 시간이었다. 특히 부하테스트에서 배운 "성능이 무너지는 지점을 찾는다"는 목표가, 오늘 배운 Resilience 패턴들이 바로 그 "무너지는 순간"에 시스템을 지켜주는 안전장치라는 걸 자연스럽게 연결해서 이해할 수 있었다.
- **인프라 영역과 백엔드 영역이 같은 패턴(Rate Limiter, Timeout, Retry, Circuit Breaker, Bulkhead, Fallback)을 각자의 방식으로 구현한다**는 표가 오늘 배운 것 중 가장 유용했다. 지금까지는 이런 패턴들을 그냥 "백엔드 코드에서 처리하는 것"으로만 생각했는데, Nginx·Ingress 같은 인프라 레벨에서도 동일한 역할을 하는 설정이 있고, 각 계층이 알고 있는 정보(인프라는 IP·연결·응답 코드, 백엔드는 사용자·주문·결제 같은 비즈니스 정보)가 다르기 때문에 **둘 다 함께 구현해야 한다**는 설명이 인상 깊었다.
- **Rate Limit ≠ Concurrency**라는 구분도 오늘 새롭게 배운 개념이었다. RPS를 제한한다고 해서 동시에 처리 중인 요청 수까지 자동으로 제한되는 게 아니라는 걸, "요청 처리에 10초가 걸리면 100 RPS로도 동시 요청 수가 1000개까지 쌓일 수 있다"는 예시로 보니 확실히 감이 잡혔다. 이래서 Rate Limiter 하나만으로는 부족하고 Bulkhead·Timeout이 항상 함께 필요하다는 결론이 자연스럽게 이어졌다.
- **Retry Storm**과 "요청 하나에는 하나의 계층에서만 재시도한다"는 원칙도 실무적으로 중요한 교훈이었다. Nginx, 주문 서비스, 결제 서비스, DB가 모두 각자 재시도를 하면 재시도 횟수가 곱해지면서 오히려 장애를 증폭시킬 수 있다는 걸 보고, "재시도 정책의 성공률이 떨어지면 정책을 더 세게 조정하는 게 아니라, 애플리케이션 로직의 문제부터 확인해야 한다"는 조언이 특히 기억에 남는다. Retry는 장애를 복구하는 기술이 아니라는 문장을 계속 곱씹게 된다.
- Circuit Breaker의 **Closed → Open → Half-Open** 흐름은 "누전 차단기"라는 비유 덕분에 개념이 확 와닿았다. 특히 "서킷을 강제로 닫으면 대기 중이던 요청이 한 번에 몰려 들어와 다시 장애를 일으킬 수 있다"는 운영자 대응 원칙은, 급하게 장애를 복구하고 싶은 마음에 성급하게 서킷을 닫아버리는 실수를 왜 피해야 하는지를 명확히 설명해줘서 유용했다.
- 마지막 문장인 **"장애 전파 방지는 실패를 숨기는 것이 아니라, 실패를 빠르게 감지하고 제한된 영역 안에서 끝내는 것"**이 오늘 배운 6가지 패턴 전체를 관통하는 핵심 원칙이라고 느껴진다. 지금 마무리 중인 개인 프로젝트에도 최소한 Timeout과 간단한 Retry 정책 정도는 적용해보면서, 오늘 배운 개념을 직접 코드로 옮겨봐야겠다.
