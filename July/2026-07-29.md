#### | HPA (Horizontal Pod Autoscaler)

> 💡 HPA는 애플리케이션의 부하를 메트릭으로 관찰하고, Deployment와 같은 워크로드의 **Pod 개수**를 자동으로 늘리거나 줄이는 기능이다.

##### HPA가 해결하려는 문제 — 고정된 파드의 숫자

Deployment를 직접 만들든, GitOps(ArgoCD Sync)로 배포하든, **Pod의 수는 "고정"되어 있었다.** "현재" 트래픽을 기준으로 replicas 숫자가 자동으로 변경되지 않는다는 뜻이다.

| 상황 | 문제 |
|---|---|
| 트래픽 증가 | Pod이 처리할 수 있는 요청보다 많은 요청이 들어와 응답 지연이나 오류가 발생할 수 있음 |
| 트래픽 감소 | 사용하지 않는 Pod이 계속 실행되어 CPU·메모리와 인프라 비용이 낭비됨 |
| 갑작스러운 변화 | 관리자가 직접 replicas를 변경하기 전까지 대응하기 어려움 |
| 반복적인 운영 | 부하를 확인하고 Pod 개수를 조절하는 작업을 계속 수동으로 수행해야 함 |

##### HPA를 왜 쓰는가

**1. 부하 대응 자동화**
쇼핑몰 행사, 쿠폰 발급, 이벤트, 광고 집행 등으로 트래픽이 순간적으로 몰리거나 시간에 따라 변화할 때, 매번 `kubectl scale deployment backend --replicas=10`처럼 수동으로 대응하는 대신 **CPU 사용률 같은 메트릭을 기반으로 Pod 개수를 자동 조정**할 수 있다.

```
평상시     사용자 → Service → Pod 2개
트래픽 증가 사용자 → Service → Pod 5개
```

**2. 트래픽 감소 시 파드 축소**
사실 리소스 측면에서는 파드를 줄인다고 해서 당장 실제 비용이 줄어드는 건 아닐 수 있다(여유 자원을 확보해두기 위한 목적도 있기 때문). 그보다는 **비용적인 측면보다 운영 안정성 측면에서** 트래픽이 줄면 파드를 줄이려고 하는 것이다.

**3. 수동 운영 감소**
300대 노드, 3000개 파드, 10개 이상의 파드 카테고리가 있는 클러스터라면, 이 모든 파드의 개수를 사람이 직접 관리하는 건 불가능하다. HPA는 이 과정을 **제어 루프**로 자동화한다.

```
현재 상태 측정 → 목표 상태와 비교 → 필요한 Pod 수 계산 → replicas 변경 → 새로운 상태를 다시 측정
```

##### HPA는 뭘 변경하는가

**HPA는 Pod를 직접 늘리거나 줄이지 않는다. Deployment의 Replicas 값을 수정할 뿐이다.**

```
HPA        → replicas 변경
Deployment → ReplicaSet 관리
ReplicaSet → Pod 생성 또는 감소
```

```
Deployment replicas: 2
  → HPA가 replicas를 5로 변경
  → Deployment와 ReplicaSet이 Pod 3개를 추가 생성
```

| 구성 요소 | 역할 |
|---|---|
| HPA | 필요한 Pod 개수를 계산하고 대상 워크로드의 스케일을 변경 |
| Deployment | 애플리케이션 배포와 ReplicaSet 관리 |
| ReplicaSet | 지정된 개수만큼 Pod이 실행되도록 유지 |

##### HPA가 동작하기 위한 구성

**HPA는 리소스를 만든다고 해서 자동으로 확장이 동작하지 않는다.** 기본적으로 CPU 기반 HPA는 다음 흐름으로 동작한다.

```
애플리케이션 Pod → CPU 사용량
   ↓ 수집
Kubelet
   ↓ Metrics API 제공
Metrics Server
   ↓ 필요한 replicas 계산
HPA Controller
   ↓
Deployment
```

| 구성 요소 | 역할 |
|---|---|
| 대상 워크로드 | HPA가 Pod 개수를 조정할 Deployment 등 |
| Metrics Server | 노드와 Pod의 CPU·메모리 사용량을 수집하여 Metrics API로 제공 |
| HPA 리소스 | 대상, 최소·최대 Pod 수, 목표 메트릭을 정의 |
| Resource requests | CPU·메모리 사용률을 계산할 때 기준값으로 사용 |
| HPA Controller | 메트릭을 확인하고 필요한 복제본 수를 계산 |

##### Metrics Server

> 💡 Metrics Server는 각 Node와 Pod의 현재 CPU·메모리 사용량을 수집하여, HPA와 `kubectl top`이 사용할 수 있도록 제공하는 Kubernetes용 메트릭 수집 애플리케이션이다.

**메트릭 서버가 별도의 애플리케이션인가?** → **그렇다.** 쿠버네티스 내부에 내장된 기본 기능이 아니라, 클러스터에 별도로 설치하는 애플리케이션이다 (`kube-system` 네임스페이스에 Deployment 형태로 설치된다).

```
각 Node의 Kubelet → CPU·메모리 사용량 제공
Metrics Server    → Metrics API로 제공
HPA / VPA / kubectl top
```

Kubelet에서 수집한 데이터를, Metrics Server가 다른 컴포넌트가 사용할 수 있는 API 형태로 표현해주는 역할이다.

**사용처**

```bash
kubectl top node   # CPU 사용량
kubectl top pod

# HPA 에서 CPU 기반, Memory 기반으로 파드 확장·수정
# VPA 사용 시에도 활용
```

> ⚠️ 메트릭 서버는 **장기간 데이터를 저장하고 분석하는 모니터링 시스템이 아니다.** 현재 리소스 사용량을 보여주는 API일 뿐이다.

| 구분 | Metrics Server | Prometheus |
|---|---|---|
| 주요 목적 | HPA·VPA와 kubectl top 지원 | 모니터링·분석·알림 |
| 주요 데이터 | Node·Pod의 CPU와 메모리 | CPU, 메모리, 요청 수, 지연 시간 등 |
| 데이터 저장 | 장기 저장하지 않음 | 시계열 데이터로 저장 |
| 과거 데이터 조회 | 어려움 | 가능 |
| 시각화 | 제공하지 않음 | Grafana와 연동 |
| HPA 연결 | 기본 CPU·메모리 HPA에서 바로 사용 | 기본 상태에서는 직접 연결되지 않음 |

> 💡 **Metrics Server**는 지금 속도계가 몇 km/h인지 알려주는 **계기판**이고, **Prometheus**는 지난 한 달 동안 속도가 어떻게 변했는지 저장하는 **운행 기록 시스템**이다.

**PLG Stack으로 Metrics Server를 대체할 수 있지 않나?**

프로메테우스와 Metrics Server는 제공하는 역할 자체가 다르다.

- **Prometheus**: 데이터를 얻으려면 **PromQL 쿼리**를 거쳐야 한다. 쿼리 언어의 시간 복잡도 때문에 상대적으로 실시간성이 떨어진다.
- **Metrics Server**: Kubelet이 실시간으로 수집하고 있는 OS 데이터를 그대로 가져와 API 결과로 바로 변환해서 전달한다. **가볍고 실시간성이 높다.**

CPU 사용률 기반으로 파드를 늘리는 목적이라면 Prometheus로도 불가능한 것은 아니지만, **일반적으로 OS 레벨 메트릭을 비교하는 HPA에서는 Prometheus를 잘 사용하지 않는다.** 다만 완전히 불가능한 것도 아니라서, 보통 **PLG Stack + Metrics Server를 함께 사용**한다.

```
HPA → metrics.k8s.io → Metrics Server

애플리케이션 → Prometheus → Prometheus Adapter
  → custom.metrics.k8s.io → HPA
```

| 도구 | 역할 |
|---|---|
| Metrics Server | HPA·VPA, `kubectl top`, 현재 CPU·메모리 기반 자동화 |
| Prometheus | 장기간 메트릭 저장, Grafana 대시보드, 장애 분석 및 알림, **사용자 정의 메트릭 기반 확장** |

```
웹 API           → CPU 평균 사용률 60% 기준으로 확장 → Metrics Server 사용
메시지 처리 Worker → 대기 메시지 수를 기준으로 확장   → Prometheus + Metrics Adapter 사용
```

##### Metrics Server 정리

1. Metrics Server는 클러스터에 별도로 설치하는 애플리케이션이다.
2. Kubelet에서 Node와 Pod의 CPU·메모리 사용량을 수집한다.
3. 수집한 데이터를 `metrics.k8s.io` API로 제공한다.
4. HPA, VPA, `kubectl top`이 이 데이터를 사용한다.
5. 장기 저장, 그래프, 알림을 위한 모니터링 시스템은 아니다.
6. Prometheus는 메트릭을 장기간 저장하고 분석하기 위한 도구다.
7. 기본 CPU·메모리 HPA에서는 Metrics Server를 사용한다.
8. Prometheus 메트릭으로 HPA를 동작시키려면 별도의 Metrics Adapter가 필요하다.

##### CPU Utilization은 `request` 기준으로 계산한다

> ⚠️ HPA에서는 `request` 값을 반드시 중요하게 봐야 한다. `HPA → Metrics Server → CPU/Memory Average Usage`로 이어지는 사용량 기준은, **현재 사용량을 request와 비교**해서 계산한다.

`averageUtilization: 60`은 **노드 전체 CPU가 60%라는 뜻이 아니다.** 각 컨테이너에 설정된 **CPU requests 대비 실제 CPU 사용량 비율**을 의미한다.

```yaml
resources:
  requests:
    cpu: 100m
  limits:
    cpu: 500m
```

현재 컨테이너가 CPU를 80m 사용한다면:

```
CPU 사용률 = (실제 CPU 사용량 / CPU request) × 100
현재 케이스 = (80 / 100) × 100 = 80%
→ Pod를 늘리려고 한다
```

즉 **Node 전체의 CPU 사용량을 보는 게 아니라, Pod의 requests 대비 실제 사용량이 얼마인지를 본다.**

| 설정 | HPA와의 관계 |
|---|---|
| `requests.cpu` | CPU 사용률 계산의 기준 |
| `limits.cpu` | 컨테이너가 사용할 수 있는 CPU 상한 |
| `requests.memory` | 메모리 사용률 방식에서 계산 기준 |
| `limits.memory` | 초과 시 OOM 종료 가능성이 있는 메모리 상한 |

##### HPA는 필요한 파드 수를 어떻게 계산할까?

**기본 계산 공식**

```
필요한 파드 수 = 올림((현재 Pod 수 × 현재 메트릭 값) / 목표 메트릭 값)
```

**예시 1**

```
현재 파드 수 = 2개
평균 CPU 사용률 = 90%
목표 CPU 사용률 = 60%

올림((2 × 90) / 60) = 3
→ 필요한 파드 수는 3
```

**예시 2**

```
현재 파드 수 = 3개
평균 CPU 사용률 = 110%
목표 CPU 사용률 = 60%

올림((3 × 110) / 60) = 5.5 → 6
→ 필요한 파드 수는 6개 → deployment.replicas = 6
```

##### YAML 예시

**Deployment**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-api
spec:
  replicas: 2

  selector:
    matchLabels:
      app: web-api

  template:
    metadata:
      labels:
        app: web-api

    spec:
      containers:
        - name: web-api
          image: example/web-api:1.0
          ports:
            - containerPort: 8080

          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi
```

**HPA**

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-api

  minReplicas: 2
  maxReplicas: 10

  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
```

| 필드 | 설명 |
|---|---|
| `scaleTargetRef` | HPA가 관리할 대상 워크로드 |
| `minReplicas` | HPA가 유지할 최소 복제본 수 |
| `maxReplicas` | HPA가 확장할 수 있는 최대 복제본 수 |
| `metrics` | 스케일링 판단에 사용할 메트릭 |
| `type: Resource` | CPU·메모리와 같은 리소스 메트릭 사용 |
| `averageUtilization: 60` | 모든 대상 Pod의 평균 사용률을 request 대비 60%에 맞춤 |

##### 메트릭의 종류

| 메트릭 | 예시 | 특징 |
|---|---|---|
| Resource Metric | CPU, 메모리 | Metrics Server를 통해 비교적 쉽게 구성 |
| Container Resource Metric | 특정 컨테이너의 CPU·메모리 | 사이드카를 제외하고 핵심 컨테이너만 기준으로 삼을 때 유용 |
| Custom Metric | 초당 요청 수, 큐 길이 | 별도의 메트릭 수집 및 어댑터 구성 필요 |
| External Metric | 외부 메시지 큐 길이, 클라우드 서비스 지표 | 클러스터 외부 시스템의 상태를 기준으로 확장 |

CPU만으로는 충분하지 않은 사례들도 있다.

```
메시지 큐 소비자         → CPU는 낮지만 처리 대기 메시지가 계속 쌓일 수 있음
외부 API 응답을 기다리는 서버 → 요청은 많지만 I/O 대기 때문에 CPU는 낮을 수 있음
메모리 캐시 애플리케이션    → 메모리가 부하 감소 후에도 바로 반환되지 않을 수 있음
```

이런 경우 HTTP 요청 수, 응답 지연 시간, 메시지 큐 길이, 동시 연결 수, 처리 대기 작업 수 같은 **Custom/External Metric**을 함께 고려해야 한다.

##### 스케일링 속도 제어 — `behavior`

HPA가 부하 변화마다 Pod을 즉각적으로 수정하면(부하 증가 → 늘리기 → 조금 떨어짐 → 줄이기 → 다시 증가 → 또 늘리기), 파드가 생성될 때 필요한 시간(노드 스케줄링, node affinity 등) 때문에 오히려 **서비스 안정성이 떨어지는 "플래핑(flapping)" 현상**이 생길 수 있다. 이를 제어하는 필드가 `behavior`다.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-api

  minReplicas: 2
  maxReplicas: 10

  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60

  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - type: Pods
          value: 4
          periodSeconds: 60

    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Percent
          value: 25
          periodSeconds: 60
```

| 설정 | 의미 |
|---|---|
| `scaleUp.stabilizationWindowSeconds: 0` | 확장은 별도의 안정화 대기 없이 판단 |
| `type: Pods, value: 4` | 60초 동안 최대 4개까지 증가 |
| `scaleDown.stabilizationWindowSeconds: 300` | 축소 전 최근 5분 동안의 권장값을 고려 |
| `type: Percent, value: 25` | 60초 동안 현재 Pod 수의 최대 25%까지 감소 |

> 💡 확장(scaleUp)은 빠르게, 축소(scaleDown)는 신중하게 — 이것이 일반적인 behavior 설계 방향이다.

##### ArgoCD와 함께 쓸 때 생기는 충돌

ArgoCD는 GitOps를 통해 "배포 환경 == Git에 선언된 단일 진실 공급원"이 일치하도록 유지한다. 그런데 클러스터 안에서 HPA가 알아서 Usage를 보면서 replicas를 바꿔버리면, ArgoCD 입장에서는 **"이건 Git과 다르니 거짓이다, 나는 Git을 믿겠다"**며 replicas를 Git에 적힌 값으로 되돌려버릴 수 있다.

```
HPA:    2 → 5
ArgoCD: 5 → 2
HPA:    2 → 5
ArgoCD: 5 → 2
# 컨트롤러 충돌
```

**HPA를 사용할 때는 워크로드의 복제본 관리 주체가 누구인지 명확히 정해야 한다.**

**해결 방법 1 — Deployment에서 replicas 제거하고 관리 주체를 HPA로 일원화**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-api
spec:
  # replicas: 2   ← 제거
  selector:
    matchLabels:
      app: web-api
```

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-api

  minReplicas: 2
  maxReplicas: 10
```

이렇게 하면 **Git + ArgoCD는 이미지·환경변수·프로브·서비스·Deployment 등 배포 설정을 관리**하고, **HPA는 현재 필요한 Replicas만 관리**하는 식으로 관리 주체가 분리된다.

> ⚠️ Deployment에서 이미 `replicas`를 관리하고 있었다면, 적용 시점에 따라 문제가 생길 수 있으니 인프라 구조 변경 시점에 반영하는 것이 안전하다.

**해결 방법 2 — ArgoCD가 `spec.replicas` 차이를 무시하도록 설정 (`ignoreDifferences`)**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: web-api
  namespace: argocd
spec:
  destination:
    namespace: production
    server: https://kubernetes.default.svc

  source:
    repoURL: https://github.com/example/platform-config.git
    path: web-api
    targetRevision: main

  ignoreDifferences:
    - group: apps
      kind: Deployment
      name: web-api
      namespace: production
      jsonPointers:
        - /spec/replicas
```

다만 이것만으로는 충분하지 않을 수 있다. `ignoreDifferences`는 기본적으로 **ArgoCD가 해당 차이를 OutOfSync로 판단하지 않도록** 만드는 설정이며, 동기화 시점에서 "다르더라도 차이를 무시한다"는 의미다. 확실하게 제외하려면 `RespectIgnoreDifferences=true`를 함께 적용해야 한다.

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      name: web-api
      jsonPointers:
        - /spec/replicas

  syncPolicy:
    syncOptions:
      - RespectIgnoreDifferences=true
```

> ⚠️ **초기 진입 값은 무시할 수 없다.** "차이를 무시한다"는 건 비교할 대상이 있을 때의 이야기다. 클러스터에 리소스를 **최초로 생성**할 때는 비교할 라이브 리소스 자체가 없기 때문에, Git에 선언된 `replicas` 값이 그대로 적용된다.

**실무 조합**: Deployment의 `replicas`는 관리하지 않고 HPA가 replicas를 관리하며, ArgoCD에서도 `replicas`에 대해서는 차이를 무시하도록 설정하는 방식이 일반적이다.

##### HPA 정리

1. HPA는 Pod 한 개의 성능이 아니라 Pod의 개수를 조절한다.
2. HPA는 메트릭을 관찰하고 대상 워크로드의 replicas를 변경한다.
3. CPU Utilization은 CPU limit이 아니라 **CPU request**를 기준으로 계산한다.
4. 기본 CPU·메모리 메트릭을 사용하려면 Metrics Server가 필요하다.
5. Pod이 늘어나려면 노드에 충분한 CPU와 메모리가 있어야 한다.
6. 새 Pod이 실제 트래픽을 받기까지는 생성과 초기화 시간이 필요하다.
7. 빠른 확장과 안정적인 축소를 위해 `behavior` 정책을 조정할 수 있다.
8. HPA는 Stateless하고 수평 확장이 가능한 애플리케이션에서 효과적이다.
9. HPA는 애플리케이션 장애나 데이터베이스 병목을 자동으로 해결하지 않는다.
10. 운영에서는 `requests`, `minReplicas`, `maxReplicas`, Readiness Probe를 함께 설계해야 한다.

---

#### | VPA (Vertical Pod Autoscaler)

> 💡 VPA는 Pod의 실제 CPU·메모리 사용 이력을 분석하여, 컨테이너의 적절한 `requests` 값을 추천하거나 자동으로 조정하는 오토스케일러다.

| 구분 | 조정 대상 | 예시 |
|---|---|---|
| HPA | Pod 개수 | Pod 2개 → 5개 |
| **VPA** | **Pod의 CPU·메모리** | CPU 100m → 300m |
| CA | Worker Node 개수 | Worker Node 2대 → 3대 |

```
변경 전
Pod
├── CPU requests: 100m
└── Memory requests: 128Mi

변경 후
Pod
├── CPU requests: 300m
└── Memory requests: 256Mi
```

> ⚠️ VPA도 기본 제공 기능이 아니다. HPA와 같은 API Group에 속하지만 **별도로 설치해야 하는 애드온**이다.

##### VPA를 왜 사용할까?

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 512Mi
```

애플리케이션이 실제로 얼마나 리소스가 필요한지는 실행해보기 전까지 알기 어렵다.

- **request가 너무 적으면**: 실제로 필요한 CPU가 400m인데 request가 100m으로 설정되면, 스케줄러는 request 기준으로 노드에 배치를 판단한다. 노드 여유 자원이 200m밖에 없어도 request 100m 기준으로는 통과해서 배치되지만, 실제 400m를 쓰려는 순간 **쓰로틀링이 걸려 다른 파드들에게도 영향을 미친다.**
- **memory request가 너무 작게 설정되면**: 실제 사용량이 request를 초과할 때 **OOM으로 죽는다.**

| 문제 | VPA의 역할 |
|---|---|
| 너무 작은 requests | 필요한 수준까지 상향 추천 |
| 너무 큰 requests | 실제 사용량에 맞게 하향 추천 |
| 반복적인 수동 튜닝 | 사용 이력을 기반으로 자동 분석 |
| 잘못된 요청량으로 인한 스케줄링 문제 | 실제 사용량에 가까운 요청값 제공 |
| 리소스 낭비 | 과도하게 예약된 CPU·메모리 감소 |

> 💡 파드에 필요한 리소스를 실제 사용량에 가깝게 맞추는 **RightSizing** 도구다. 자동화 기능을 켜면 파드를 request에 맞게 재배치하는 기능도 있다.

##### VPA가 무엇을 변경하는가

VPA는 주로 **request** 값을 변경한다. request는 단순히 참고용 값이 아니라, **노드 스케줄러가 실제로 스케줄링 판단에 사용하는 "기준 값"**이다.

| 구분 | 의미 |
|---|---|
| 실제 사용량 | 현재 컨테이너가 실제 사용하는 CPU·메모리 |
| requests | 스케줄러에게 이 Pod이 필요하다고 선언한 CPU·메모리 |

```
CPU
  실제 사용량: 300  request: 100   ← under-provisioned
  실제 사용량: 10   request: 500   ← over-provisioned
```

##### VPA의 구성 요소

```
Metrics API
   │
   ▼
Recommender  ── 권장값 계산 ──▶ VPA 객체의 status.recommendation
                                       │
                        ┌──────────────┴──────────────┐
                        ▼                              ▼
                     Updater                 Admission Controller
             (기존 Pod의 변경 필요 여부 판단)   (새로 생성되는 Pod에 권장값 적용)
```

**1. Recommender**

> 💡 파드의 사용량을 분석해서 적절한 리소스 값을 추천한다.

각 컨테이너의 **현재 사용량**과 **과거 사용량**을 함께 분석해, VPA 객체의 `status.recommendation`에 저장한다.

```
현재 CPU 사용량 / 과거 CPU 사용량 / 현재 메모리 사용량 / 과거 메모리 사용량 / OOM 발생 정보
        ↓
   Recommender
        ↓
   추천 requests 계산
```

| 값 | 의미 |
|---|---|
| `target` | 일반적으로 적용하기 적절한 권장값 |
| `lowerBound` | 권장 가능한 최소 범위 |
| `upperBound` | 권장 가능한 최대 범위 |
| `uncappedTarget` | 정책의 최소·최대 제한을 적용하기 전 계산값 |

**2. Updater**

> 💡 실행 중인 파드의 요청값과 권장값을 비교해서, 변경이 필요한지 여부를 판단한다.

```
기존 Pod의 requests
   ↓
VPA 권장값과 비교
   ↓
차이가 충분히 큼
   ↓
Pod Eviction (기존 방식) / In-place (신기술, 1.33 버전, 2025년 11월경)
   ↓
Deployment가 새 Pod 생성
```

Updater는 **Recommender가 만든 값과 현재 파드 값을 비교해서, 변경 대상인지 아닌지만 판단**한다. Eviction 대상이면 제거하거나(구방식), In-place로 처리한다(신방식).

**3. Admission Controller**

> 💡 새롭게 생성되는 파드에 VPA 권장 리소스 값을 주입하는 역할을 한다.

```
Deployment가 새 Pod 생성 요청
   ↓
API Server
   ↓
VPA Admission Controller
   ↓
권장 requests를 Pod 설정에 반영
   ↓
Pod 생성
```

##### YAML 예시

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vpa-demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: vpa-demo
  template:
    metadata:
      labels:
        app: vpa-demo
    spec:
      containers:
        - name: app
          image: example/app:1.0
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 512Mi
```

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: vpa-demo
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: vpa-demo

  updatePolicy:
    updateMode: "Off"

  resourcePolicy:
    containerPolicies:
      - containerName: app
        minAllowed:
          cpu: 50m
          memory: 64Mi
        maxAllowed:
          cpu: "1"
          memory: 1Gi
        controlledResources:
          - cpu
          - memory
```

**`resourcePolicy`**

| 필드 | 의미 |
|---|---|
| `containerName` | 정책을 적용할 컨테이너 |
| `minAllowed` | VPA가 추천할 수 있는 최소값 |
| `maxAllowed` | VPA가 추천할 수 있는 최대값 |
| `controlledResources` | VPA가 관리할 리소스 종류 |

**`updatePolicy` — VPA의 업데이트 모드**

| 모드 | 동작 |
|---|---|
| `Off` | 추천 값을 계산만 하고 실제 Pod에는 적용하지 않는다. VPA는 사용량 분석만 수행한다. |
| `Initial` | 파드가 **생성될 때만** 권장값을 적용한다. 실행 중인 파드에는 적용하지 않고, 새 파드가 생성될 때 Admission Controller가 동작한다. |
| `Recreate` | 권장 값을 적용하려면 Pod을 Eviction하고 새로 생성한다 (`권장값 변경 → Updater 판단 → 기존 Pod Eviction → Deployment가 새 Pod 생성 → Admission Controller가 권장값 적용`). |
| `InPlace` | 실행 중인 파드의 리소스를 제거 없이 변경한다. |
| `InPlaceOrRecreate` | 가능하면 In-place로 변경하되, 리소스 변경이 불가능하면(예: 노드의 남은 자원이 300m인데 100m → 500m로 늘려야 하는 경우) Pod을 Eviction시켜 재생성한다. |

> ⚠️ 실무에서는 **`Off` 모드로 먼저 데이터를 수집**하고, `recommendation`에 저장되는 값을 검토한 뒤 실제로 적용할지 결정하는 방식을 권장한다.

##### HPA vs VPA

| 구분 | HPA | VPA |
|---|---|---|
| 확장 방식 | 수평 확장 | 수직 확장 |
| 변경 대상 | Pod 개수 | Pod CPU·메모리 |
| 대표 설정 | `minReplicas`, `maxReplicas` | `minAllowed`, `maxAllowed` |
| 주된 기준 | 현재 메트릭과 목표값 | 현재·과거 리소스 사용량 |
| 결과 | 여러 Pod으로 부하 분산 | 각 Pod의 리소스 크기 최적화 |
| 중단 가능성 | 일반적으로 새 Pod 추가·삭제 | 모드에 따라 기존 Pod 재생성 가능 |
| 기본 설치 | Kubernetes API에 포함 | 별도 설치 필요 |

##### 주의 사항

**1. Pod 재생성 가능성을 고려해야 한다**
VPA의 In-place 방식은 아직 알파 버전 기능이고, `autoscaler` API Group 자체도 아직 완전히 안정적인(LTS) 상태는 아니다. **Eviction이 사실상 기본값**이라고 보면 된다. HPA와 함께 사용할 때 `replicas: 1`처럼 낮게 설정되어 있으면, VPA Eviction 때문에 문제가 생길 수 있다.

**2. VPA와 StatefulSet이 잘 맞는가?**
1 Master–1 Slave 구조의 DB를 StatefulSet으로 구성하고 VPA를 적용하려 하면, DB는 초기화 시간이 오래 걸려서 Master가 Eviction 후 재생성될 때까지 **서비스 전체의 쓰기가 중지**될 수 있고, Slave를 Master로 승격시키는 Voting 과정, 이후 Slave 역할 재배정 등 고려할 게 많다. HPA로 하기 어려운 이유와 비슷하게, DB의 Pod 수를 무한히 늘리고 삭제하는 것도 다소 어색하다. VPA를 쓰려 해도 클러스터 규모가 어느 정도 받쳐줘야 하고(예: 1 master → 3 master), 데이터베이스 종류가 다양할 때(MySQL, MariaDB, MongoDB, Redis, Graph DB, Vector DB 등) 굳이 k8s 내부에서 이런 복잡한 관리를 해야 하는지는 신중히 판단해야 한다.

**3. `minAllowed`, `maxAllowed` 사이징을 잘 해야 한다**
- **Node Spec과의 연관**: 노드 스펙이 2GB인데 VPA가 `maxAllowed: 2Gi`로 설정되어 있고, 이미 다른 곳에서 메모리를 사용 중이라면, Pod request를 1Gi → 2Gi로 Eviction 후 재배치하려 해도 **노드 스케줄링 필터링을 통과하지 못해 Pending 상태**로 남을 수 있다. 이는 특정 파드를 장애 상황에 빠뜨리는 것과 같다.
- **Application Spec과의 연관**: 예를 들어 Spring WAS의 Tomcat Max Thread Pool이 1,000개일 때 4GB가 필요하다고 가정하면, VPA의 `maxAllowed: 8Gi` 설정 아래에서 실제로는 4Gi만 쓰는데 VPA가 request를 6Gi로 늘려버릴 수 있다. 노드 스케줄러는 실제 사용 메모리가 아니라 **request의 합산 수치만 보고 배치를 결정**하기 때문에, 이는 자원 낭비로 이어진다.

**실무에서는** `updatePolicy: Off`로 추천 도구처럼 사용하는 것이 가장 안전하다. Pod request 변경 자체가 즉각적이지 않고, k8s 1.33 이하·`autoscaler` v2 알파 미만 버전에서는 결과적으로 Pod을 삭제했다가 다시 만드는 방식이라 HPA보다 위험성이 더 높다. `Initial` 모드에서만 적용하는 것도 고려할 만하다.

##### VPA 정리

- VPA는 별도로 설치해야 하는 애드온이다.
- Pod 개수가 아니라 CPU·메모리 requests를 조정한다.
- 현재뿐 아니라 과거 사용량도 분석한다.
- 모드에 따라 Pod이 재생성될 수 있다.
- 처음에는 `Off` 모드로 추천값을 확인하는 것이 안전하다.
- HPA와 같은 CPU·메모리 지표를 동시에 관리하면 충돌할 수 있다.
- `minAllowed`, `maxAllowed`로 조정 범위를 제한해야 한다.
- VPA가 Pod을 크게 만들어도 Node 용량이 자동으로 늘어나는 것은 아니다.

#### | CA (Cluster Autoscaler)

> 💡 CA는 Pod을 배치할 공간이 부족하면 워커 노드를 늘리고, 불필요한 노드가 생기면 줄이는 **노드 단위**의 자동 확장 도구다.

##### 해결하는 문제 — 파드를 늘릴 때 배치할 노드가 없다면?

HPA·VPA는 파드의 사이징이나 개수를 늘리지만, **노드 자원은 유한하다.** 모든 노드가 자원이 충분하지 않으면 파드는 계속 Pending 상태로 대기하게 된다. CA는 이럴 때 **노드 자체를 새로 추가**하고, 반대로 필요 없어진 노드는 제거한다.

##### CA가 확인하는 값

HPA·VPA는 파드의 자원 사용량이나 커스텀 사용량을 본다. **CA는 사용량을 보지 않는다.**

> 💡 CA는 "파드들이 노드에 스케줄링 가능한가?", "지금 Pending 상태인 파드가 얼마나 많은가?"를 확인한다.

```
Pod 생성
   ↓
kube-scheduler가 배치 가능한 노드 검색
   ↓
배치 가능한 노드가 없음
   ↓
Pod: Pending / Unschedulable
   ↓
CA가 확장 필요성 검토
# Pending 되어 있는 파드의 수와, 각 파드가 필요한 request 양을 보고 CA가 결정한다.
# request 양이 너무 작으면 CA가 확장을 무시할 수도 있다.
```

##### CA는 "직접" 노드를 추가하지 않는다

CA는 그 자체로 EC2를 만드는 게 아니라, **AWS Auto Scaling Group(ASG)** 같은 인프라 그룹의 **희망 노드 개수(Desired Capacity)만 변경**한다.

```
ASG (minEC2: 2, maxEC2: 10) → Worker Node들이 여기에 포함되어 있다
CA → ASG의 현재 필요한 노드 개수를 2 → 3으로 변경
```

CA의 종류에 따라 동작 방식이 다르다.

- **일반적인 CA**: ASG의 Desired Capacity를 증가시키는 방식.
- **Karpenter**: ASG를 사용하지 않고 **직접 EC2 템플릿을 골라 생성 요청**한다. 생성 시간이 더 빠르고 더 예민하게 반응하며, 필요한 인스턴스 타입에 맞춰 EC2 개수를 늘릴 수 있다.

> 💡 ASG의 Desired Capacity를 2 → 3으로 바꿨다고 EC2가 즉시 생기는 건 아니다. CSP는 물리적인 데이터센터 장비 위에서 서비스되기 때문에(예: 300GB 물리 장비에서 t3.small을 할당), 생성 대기 시간이 생길 수 있다. **더 예민한 확장이 필요하다면 Karpenter 같은 도구를 고려해야 한다.**

##### 노드가 줄어들 땐 어떻게 동작하는가

CA는 사용량이 많지 않은 노드가 있다고 해서 바로 지우지 않는다. 다음을 함께 검토한다.

| 확인 내용 | 설명 |
|---|---|
| 다른 노드로 이동 가능한가 | 해당 노드의 Pod을 다른 노드에 배치할 수 있어야 합니다. |
| 리소스가 충분한가 | 이동 대상 노드에 CPU·메모리 공간이 있어야 합니다. |
| 스케줄링 조건을 만족하는가 | NodeSelector, Affinity, Taint/Toleration 등을 만족해야 합니다. |
| 안전하게 퇴거 가능한가 | PodDisruptionBudget 등의 정책을 위반하지 않아야 합니다. |
| 로컬 데이터가 있는가 | 노드에 종속된 데이터가 있으면 제거가 제한될 수 있습니다. |

##### HPA, VPA, CA 한눈에 비교

| 구분 | HPA | VPA | CA |
|---|---|---|---|
| 확장 대상 | Pod 개수 | Pod의 requests | Worker Node 개수 |
| 확장 방향 | 수평 확장 | 수직 확장 | 클러스터 수평 확장 |
| 주요 판단 기준 | CPU, 메모리, 사용자 정의 메트릭 | CPU·메모리 사용 이력 | 스케줄할 수 없는 Pod |
| 변경 결과 | replicas 변경 | CPU·메모리 requests 변경 | 노드 그룹 크기 변경 |
| 인프라 연동 | 일반적으로 불필요 | 일반적으로 불필요 | 필수 |

##### kubeadm 환경에서의 CA 연동

`kubeadm`은 k8s 클러스터를 초기화하고 노드를 참여시키는 도구다. 인프라 레벨에서 CA가 동작하려면, 워커 노드를 만드는 것만으로 바로 클러스터에 참여할 수 있는 게 아니라 **인프라 프로비저너** 역할이 별도로 필요하다 (containerd, CNI, 커널, 보안그룹 설정 등을 갖춰야 새 EC2가 클러스터에 참여할 수 있다). **EKS가 아니라면 CA를 사용하기 상당히 까다롭다.**

**1. 워커 노드용 AMI 준비**
새로 만들어질 EC2에 필요한 패키지(containerd, kubelet, kubeadm, CNI 동작에 필요한 커널 설정, 필요한 AWS/운영 에이전트)를 미리 설치해 AMI로 구워둔다.

**2. 새 노드가 k8s 클러스터에 join할 수 있게 구성**

```bash
# 워커노드 수동으로 만들 때
kubeadm join xxxx:6443 --token xxxx --discovery-token-ca-cert-hash sha256:xxxx
```

EC2가 실행될 때 User Data로 이 join 명령을 자동 실행하도록 미리 적어둘 수 있다.

**3. ASG 구성**
최소값·최대값·희망 구성값을 설정해두면, 그 범위 안에서 EC2 개수가 자동으로 움직인다.

**4. AWS 권한 부여**
CA가 AWS API를 호출(ASG 정보 조회, 크기 변경 요청, Auto Scaling Instance 조회, Launch Template 정보 조회, Desired Capacity 변경, 인스턴스 종료 요청, EC2 인스턴스 타입·가용 영역 정보 조회 등)할 수 있도록 IAM 권한(Access Key/Secret 등)을 부여해야 한다.

**현실적인 구성 3가지**

1. `kubeadm` + 노드 수동 관리 (CA 사용 X)
2. `kubeadm` + ASG + Cluster Autoscaler — 설정이 복잡하며, 베어메탈 환경에서 k8s를 구동할 때 필요
3. **EKS + CA(Karpenter)** — AWS의 관리형 서비스를 사용하는 가장 현실적인 조합

##### Auto Scaler 최종 정리

- **HPA**: Pod의 **개수**를 조절한다.
- **VPA**: Pod의 **CPU·메모리 requests**를 조절한다.
- **CA**: Worker **Node**의 개수를 조절한다.

> 💡 CA의 핵심 동작은 **스케줄할 수 없는 파드가 생기면 노드를 늘리고, 노드에 자원 여유가 생기면 노드를 제거하는 것**이다.
