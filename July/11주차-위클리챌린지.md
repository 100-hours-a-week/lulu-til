## 1. Deployment YML

### 1-1. backend-deployment.yaml

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: lulu-backend-deployment
  labels:
    app: lulu-backend
spec:
  replicas: 2 
  selector:
    matchLabels:
      app: lulu-backend
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1 
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: lulu-backend
    spec:
      containers:
        - name: backend-container
          image: 536697237610.dkr.ecr.ap-northeast-2.amazonaws.com/lulu-backend:latest
          ports:
            - containerPort: 8080
          envFrom:
            - configMapRef:
                name: lulu-backend-config
            - secretRef:
                name: lulu-backend-secret
          readinessProbe: 
            httpGet:
              path: /api/health-check
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 10
          livenessProbe: 
            httpGet:
              path: /api/health-check
              port: 8080
            initialDelaySeconds: 20
            periodSeconds: 20
            failureThreshold: 3
      imagePullSecrets:
        - name: ecr-secret
```

# 11주차 위클리 챌린지 - 과제 수행 과정 및 회고

## 1. 전체 설계 방향 잡기

과제 요구사항을 다시 보면 핵심은 두 가지였다.

- K8s 기본 요소(Deployment, Service, ConfigMap, Secret)를 제대로 활용하는 것
- Rolling Update로 무중단 배포가 실제로 되는지 검증하는 것

CI/CD 연동은 "핵심이 아니다"라고 명시되어 있었기 때문에, Jenkins 파이프라인을 억지로 붙이기보다는 `kubectl apply`로 직접 배포하고 그 과정에서 무중단이 성립하는지에 집중하기로 했다. DB도 아직 K8s에 넣지 말라는 조건이 있어서, 이번 과제에서는 백엔드가 RDS에 접속하는 구조를 그대로 유지하고 애플리케이션 파드만 K8s 리소스로 감싸는 방향을 잡았다.

## 2. Deployment 설계

### 2-1. 배포 전략: RollingUpdate vs Recreate

K8s Deployment의 `strategy.type`에는 크게 두 가지가 있다.

| 전략 | 동작 방식 | 장점 | 단점 |
| --- | --- | --- | --- |
| `Recreate` | 기존 파드를 전부 종료한 뒤 새 파드를 생성 | 구조가 단순하고, 신구 버전이 동시에 떠 있지 않아 스키마 호환성 문제 등을 피하기 쉬움 | 종료~생성 사이에 서비스 중단 구간이 반드시 발생 |
| `RollingUpdate` | 기존 파드를 하나씩 종료하면서 새 파드를 순차적으로 투입 | 서비스 중단 없이 배포 가능 | 신구 버전이 잠시 공존하므로 API 호환성을 신경 써야 함 |

과제의 목표 자체가 "무중단 배포 테스트"였기 때문에 고민할 필요 없이 `RollingUpdate`를 선택했다. 다만 신구 버전이 공존하는 짧은 시간 동안 프론트-백엔드 API 스펙이 깨지면 안 되므로, 이번 배포에서는 API 응답 구조를 변경하지 않는 선에서 이미지만 교체하는 것으로 테스트 범위를 한정했다.

### 2-2. maxSurge / maxUnavailable 값 선택

RollingUpdate 내부에서도 `maxSurge`와 `maxUnavailable` 조합에 따라 배포 양상이 완전히 달라진다. replicas=2 기준으로 몇 가지 조합을 비교해봤다.

| 조합 | 동작 | 가용 파드 수 | 자원 사용 |
| --- | --- | --- | --- |
| `maxSurge: 0, maxUnavailable: 1` | 기존 파드 하나를 먼저 내리고 그 자리에 새 파드 생성 | 배포 중 최소 1개로 줄어듦 | 추가 리소스 불필요 |
| `maxSurge: 1, maxUnavailable: 1` | 새 파드 하나를 추가로 띄우면서 동시에 기존 파드 하나를 내림 | 순간적으로 가용 파드 수가 흔들릴 수 있음 | 리소스 소폭 증가 |
| `maxSurge: 1, maxUnavailable: 0` (최종 선택) | 새 파드를 먼저 하나 더 띄우고, 그 파드가 Ready가 된 뒤에야 기존 파드를 하나 내림 | 배포 전 과정에서 항상 replicas 수(2개) 이상 유지 | 순간적으로 파드 1개만큼 리소스 초과 사용 |

`maxUnavailable: 0`으로 두면 배포 도중에도 항상 정상 응답 가능한 파드가 replicas 수만큼 유지된다는 점이 무중단이라는 목표와 맞아떨어졌다. `maxSurge: 1`은 한 번에 파드를 하나씩만 추가로 띄우도록 해서, 여러 파드가 한꺼번에 교체되며 발생할 수 있는 순간적인 부하 급증이나 롤백 시 추적 어려움을 줄이기 위한 선택이다. 클러스터 노드 자원이 넉넉하지 않은 상황(로컬/소규모 클러스터)이라 `maxSurge`를 2 이상으로 크게 잡지 않았다.

정리하면, "항상 최소 replicas 수를 유지"(`maxUnavailable: 0`)와 "한 번에 하나씩만 교체해서 리소스 부담과 리스크를 최소화"(`maxSurge: 1`)라는 두 가지 요구를 동시에 만족시키기 위한 조합이었다.

### 2-4. envFrom(ConfigMap/Secret 전체 주입) vs 개별 env 매핑

Deployment에서 환경변수를 넣는 방법도 두 가지를 두고 고민했다.

| 방식 | 예시 | 장점 | 단점 |
| --- | --- | --- | --- |
| `env` + `valueFrom.configMapKeyRef/secretKeyRef` | 키 하나하나를 개별 지정 | 어떤 값이 어디서 오는지 명시적, 필요한 키만 선택적으로 주입 가능 | ConfigMap/Secret에 값이 늘어날 때마다 Deployment yaml도 같이 수정해야 함 |
| `envFrom.configMapRef/secretRef` | ConfigMap/Secret 전체를 한번에 주입 | ConfigMap/Secret 값이 추가/변경돼도 Deployment yaml을 건드릴 필요 없음 | 어떤 키가 실제로 주입되는지 Deployment만 봐서는 알기 어려움 |

이번 과제에서는 백엔드에 필요한 설정값이 앞으로 계속 늘어날 가능성(DB 관련 값, AWS 자격증명 등)이 높다고 판단해서 `envFrom`을 선택했다. 값이 늘어날 때마다 Deployment를 재배포할 필요 없이 ConfigMap/Secret만 수정하면 되는 점이 운영 편의성 측면에서 더 크다고 봤다. 대신 어떤 값이 주입되는지 파악하기 어렵다는 단점을 보완하기 위해, ConfigMap/Secret 설계 표를 문서로 먼저 정리하고 시작했다.

## 3. ConfigMap / Secret 분리 기준

가장 먼저 고민한 지점은 값을 ConfigMap에 넣을지 Secret에 넣을지였다.

- ConfigMap은 접근 권한만 있으면 누구나 값을 바로 읽을 수 있는 저장소다.
- Secret도 사실 기본적으로는 Base64 인코딩일 뿐 암호화가 아니기 때문에 완벽한 보안 수단은 아니지만, 최소한 kubectl 명령 실행 시 값이 바로 노출되지 않고(디코딩 절차 필요), 민감 정보라는 시그널을 주는 리소스라는 차이가 있다.

이 기준으로 SPRING_PROFILES_ACTIVE, API_BASE_URL처럼 노출되어도 보안 사고로 이어지지 않는 값은 ConfigMap에, DB_PASSWORD/JWT_SECRET/AWS Secret Key처럼 유출 시 직접적인 피해로 이어지는 값은 Secret에 넣었다.

### 3-1. Secret의 type: Opaque를 선택한 이유

Secret에는 `type` 필드가 있고 대표적으로 아래와 같은 옵션들이 있다.

| type | 용도 |
| --- | --- |
| `Opaque` | 범용, 사용자가 정의한 임의의 key-value |
| `kubernetes.io/dockerconfigjson` | 프라이빗 레지스트리 인증 정보 전용 |
| `kubernetes.io/tls` | TLS 인증서/키 전용 |
| `kubernetes.io/basic-auth`, `kubernetes.io/ssh-auth` | 각각 basic 인증, SSH 인증 전용 |

DB_PASSWORD, JWT_SECRET, AWS 자격증명은 K8s가 정해둔 특정 스키마(TLS, dockerconfig 등)에 해당하지 않는 우리 애플리케이션 고유의 key-value 데이터이기 때문에 `Opaque`를 선택했다. 반대로 ECR 이미지를 pull하기 위한 `ecr-secret`은 별도로 `kubernetes.io/dockerconfigjson` 타입으로 만들어서 `imagePullSecrets`에 연결했는데, 이건 K8s가 이미지 레지스트리 인증 정보라는 것을 인식하고 kubelet이 이미지를 pull할 때 자동으로 활용할 수 있도록 하기 위함이다.

### 3-2. data vs stringData

Secret 작성 시 `data`(값을 직접 Base64로 인코딩해서 넣음) 대신 `stringData`(평문을 넣으면 apply 시점에 자동으로 인코딩됨)를 선택했다. `data`를 쓰면 매번 `echo -n "값" | base64`를 미리 실행해서 인코딩된 문자열을 손으로 붙여넣어야 하는데, `stringData`는 yaml에 평문으로 작성하고 K8s가 apply 시점에 알아서 인코딩해주기 때문에 휴먼 에러 가능성이 줄어든다. 다만 yaml 파일 자체에 평문이 남기 때문에, 이 파일을 Git에 커밋하지 않고 별도로 관리(.gitignore 처리 등)해야 한다는 점을 함께 인지하고 진행했다.

## 4. Service 설계

### 4-1. Service type: ClusterIP를 선택한 이유

Service의 type에는 `ClusterIP`, `NodePort`, `LoadBalancer` 등이 있는데, 과제 주의사항에 "백엔드 파드는 아직 외부에서 접속할 수 없다"는 조건이 명시되어 있었다. 이 조건을 그대로 따라서 백엔드/프론트 모두 클러스터 내부에서만 서로 통신 가능한 `ClusterIP`로 잡았다.

- `NodePort`는 각 노드의 특정 포트를 열어 외부에서 접근 가능하게 하는데, 이는 "아직 외부 접속 불가"라는 조건에 맞지 않다.
- `LoadBalancer`는 클라우드 프로바이더의 로드밸런서를 프로비저닝하는 방식이라 더더욱 외부 노출을 전제로 한다. 게다가 지금 단계에서는 별도 인그레스나 도메인 라우팅 전략이 정해지지 않았기 때문에 굳이 로드밸런서 리소스를 추가로 만들 이유가 없었다.

추후 실제 외부 서비스를 열어야 할 시점이 오면, 프론트 Service만 Ingress나 LoadBalancer로 승격시키고 백엔드는 계속 ClusterIP로 남겨서 백엔드는 프론트를 통해서만 접근 가능한 구조를 유지하는 게 자연스러울 것 같다는 결론을 내렸다.

## 5. Rolling Update 테스트

`kubectl rollout restart deployment lulu-backend-deployment`로 배포를 트리거한 뒤 `kubectl get pods -w`로 파드 상태 변화를 실시간으로 관찰했다.

### 5-1. 로그 타임라인 분석

```
[초기] lulu-backend-deployment-7444d64545-75vnc   1/1  Running       4m10s
       lulu-backend-deployment-7444d64545-dhzvs   1/1  Running       4m32s
       (기존 replicas=2 정상 서비스 중)

[1단계] lulu-backend-deployment-79f446f5d5-zk8bd  0/1  Running       1s
       → 신규 파드 zk8bd 생성. 기존 2개(75vnc, dhzvs)는 그대로 유지된 채
         파드가 하나 더 늘어남 (maxSurge: 1 동작)

[2단계] zk8bd  1/1  Running   21s   ← readinessProbe 통과, Ready 전환
       dhzvs  Terminating           ← zk8bd가 Ready 된 "이후"에야 구 파드 종료 시작
         (maxUnavailable: 0 동작 — 새 파드가 준비되기 전엔 기존 파드를 건드리지 않음)

[3단계] hxfks  0/1  Pending → ContainerCreating
       dhzvs  0/1  Error (종료 완료, Graceful Shutdown 미설정으로 인한 로그)
       → 두 번째 신규 파드 투입

[4단계] hxfks  1/1  Running   23s   ← Ready 전환
       75vnc  Terminating → Error   ← 마지막 구 파드 종료

[최종]  lulu-backend-deployment-79f446f5d5-hxfks  1/1  Running  2m59s
       lulu-backend-deployment-79f446f5d5-zk8bd   1/1  Running  3m20s
       (신규 파드 2개로 완전히 교체 완료)
```

### 5-2. 무중단 확인 근거

이 로그에서 가장 중요하게 본 지점은 **`READY 1/1` 상태인 파드 수가 전체 배포 과정에서 단 한 번도 2개 미만으로 떨어지지 않았다**는 것이다.

- 신규 파드(zk8bd)가 Ready 되기 *전까지* 기존 파드(75vnc, dhzvs)는 그대로 트래픽을 받고 있었고,
- 신규 파드가 Ready 된 이후에만 구 파드가 하나씩 Terminating으로 전환됐다.

즉 배포 중 순간적으로 파드가 3개까지 늘어나는 구간(`maxSurge: 1`)은 있었지만, 실제로 요청을 받을 수 있는(`1/1 Ready`) 파드 수는 항상 replicas 값인 2개 이상을 유지했다. 이는 애초에 설계 단계에서 의도했던 `maxSurge: 1, maxUnavailable: 0` + `readinessProbe` 조합이 실제 배포 로그로도 그대로 증명된 결과다.

`Error` 상태는 신규 파드가 이미 Ready로 전환되어 트래픽을 받기 시작한 이후, 종료 대상이 된 구 파드(dhzvs, 75vnc)에서만 나타났다. 확인해보니 Spring Boot에 Graceful Shutdown이 설정되어 있지 않아 SIGTERM을 받는 즉시 처리 중이던 작업까지 강제 종료되며 남는 로그였다. 이번 테스트에서는 이미 새 파드가 트래픽을 받고 있는 상태에서 발생한 것이라 서비스 중단으로는 이어지지 않았지만, 만약 요청이 마침 그 구 파드로 라우팅되는 시점과 겹친다면 해당 건은 실패할 수 있다는 잠재 리스크는 남아 있다고 판단했다.

## 6. 회고

### 아쉬운 점 / 추가로 고민이 필요한 부분

- Graceful Shutdown 미설정으로 인한 종료 시점 Error 로그를 이번엔 "무중단 배포 자체에는 영향 없음"으로 넘어갔지만, 엄밀히는 완전한 무중단이라 보기 어렵다. `server.shutdown=graceful`과 `terminationGracePeriodSeconds`, 그리고 `preStop` 훅으로 SIGTERM 전에 약간의 지연을 주는 방식까지 다음 과제에서는 함께 적용해봐야 할 것 같다.
- 지금은 replicas를 2로 고정해뒀는데, 배포 중 일시적으로 파드 수가 3개까지 늘어나는 구간(`maxSurge: 1`)에 대한 리소스 여유가 클러스터에 항상 보장되는지는 별도로 확인이 필요하다. 만약 노드 리소스가 빠듯하다면 새 파드가 Pending 상태로 멈춰서 오히려 배포가 막힐 수 있다.
