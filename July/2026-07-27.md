#### | RBAC (Role-Based Access Control)

**규칙 기반 접근 제어(인가) 방식**

사용자, 그룹, 또는 서비스 계정(ServiceAccount)이 특정 리소스에 대해 수행할 수 있는 작업을 **역할(Role)을 기준으로 통제**하는 쿠버네티스의 인가(Authorization) 시스템이다.

```
K8s Cluster
├── ClusterRole ──── ClusterRoleBinding   (클러스터 범위)
└── namespace
      ├── role1 ── rolebinding1 ┐
      ├── role2 ── rolebinding2 ┼─ ServiceAccount ── Pod
```

> 💡 RBAC 규칙은 크게 **namespace 레벨**에서 적용되는 것(Role/RoleBinding)과 **클러스터 레벨**에서 적용되는 것(ClusterRole/ClusterRoleBinding)으로 나뉜다.

##### RBAC가 왜 필요한가?

쿠버네티스에서는 나(관리자)뿐만 아니라 **수많은 주체가 kube-apiserver를 향해 요청을 보낸다.**

- `kubectl get pods`, `kubectl get ns` 같은 관리자 명령
- **ArgoCD** (배포)
- **Prometheus** (모니터링·시각화)
- **Ingress Controller** (인입 트래픽 컨트롤)
- **CI/CD 도구** (Jenkins, GitHub Actions)
- **Kubernetes Operator**
- **Pod 안에서 실행되는 애플리케이션** (다음 요청을 어디로 릴레이할지 확인하는 등)

이렇게 많은 주체가 API Server를 사용하기 때문에, 다음 기준으로 권한을 관리할 체계가 필요하다.

- 누가 요청했는가?
- 어떤 리소스에 접근하려 하는가?
- 어떤 작업을 수행하려 하는가?
- 어떤 네임스페이스에서 수행하려는가?

##### RBAC가 없다면 생기는 문제

**1. 모든 사용자에게 관리자 권한을 주는 것과 같아진다**
Control Plane에게 모든 권한을 양도한 상태에서, 나 / 주니어 개발자 / 시니어 개발자 / 데이터 분석가 등 누구나 구분 없이 클러스터를 조작할 수 있게 된다.

**2. 네임스페이스 분리가 의미 없어진다**
네임스페이스는 클러스터를 논리적으로 나눠 놓은 것일 뿐이라, 권한 통제가 없으면 "나눠놓기만 한" 상태가 되어버린다.

**3. 애플리케이션이 과도한 권한을 가지게 된다**
예를 들어 Pod 위에서 동작하는 **PLG(Prometheus-Loki-Grafana) 스택**처럼 메트릭·로그를 중앙에서 수집하는 모니터링 도구는 원래 모든 노드·모든 파드·모든 네임스페이스에 접근할 수 있어야 한다. 이런 도구는 운영팀, 개발자, 보안 담당자 등 여러 사람이 함께 보고, 외부에서도 접근하는 경우가 많다. **보안 사고는 외부인이 아니라 내부인에 의해 발생하는 경우가 많다는 점**에서, 권한 통제 없이 애플리케이션에 과도한 권한을 주는 것은 특히 위험하다.

**4. 사용자 개별 권한 관리가 불가능해진다**
개발자가 2명일 때는 손으로 관리할 수 있지만, 100명이 되면 `개발자 수 × 리소스 종류 × 작업 종류 × 네임스페이스 수`만큼 관리해야 할 권한의 개수가 폭발적으로 늘어난다.

> 💡 그래서 **역할(Role)을 미리 정의해두고, 사용자를 그 역할에 연결(Binding)**해서 사용하는 방식이 RBAC다.

##### 역할 설계 예시

| 역할 | 허용 작업 |
|---|---|
| **개발자** | Pod 조회, Deployment 조회 및 수정, 로그 확인 |
| **운영자** | 대부분의 워크로드 관리, Namespace 운영 |
| **모니터링** | Node, Pod, Service 상태 조회 |

##### 인증(Authentication)과 인가(Authorization)

| 구분 | 의미 | 방법 |
|---|---|---|
| **인증** | 당신이 누구인지 확인하는 과정 | 클라이언트 인증서(pem key), Token, OIDC, kubeconfig 인증 정보 |
| **인가** | 확인된 주체가 해당 작업을 수행해도 되는지 판단하는 과정 | RBAC (Role/ClusterRole + Binding) |

API Server가 요청을 받으면 **인증은 이미 완료된 요청이라고 가정하고, 인가 과정만 판단**한다. 쿠버네티스 클러스터에서 요청을 보내는 주체는 크게 2가지로 나뉜다.

- **내부 리소스**: 인증·인가된 누군가가 만들어낸 리소스(예: Pod)이므로 별도 인증이 필요 없고, 대신 **ServiceAccount**를 통해 인증한다.
- **외부 사용자**: 클러스터 외부에서 pem 키 등으로 인증 과정을 거쳐 들어왔다고 판단한다.

##### RBAC가 동작하는 방식

권한 관리를 두 축으로 나눠서 생각한다.

| 축 | 역할 |
|---|---|
| **Role** | 어떤 작업을 허용할 것인가 |
| **Binding** | 그 권한을 누구에게 줄 것인가 |

예를 들어 `backend` 네임스페이스에서 `backend-reader`라는 ServiceAccount가 Pod 목록을 조회해야 한다면, 다음과 같이 구성한다.

```
주체(ServiceAccount: backend-reader)
      │
      ▼  RoleBinding으로 연결
역할(Role: pod-reader) ── 대상: backend Namespace의 Pod / 작업: get, list, watch
```

##### RBAC 핵심 리소스

| 리소스 | 역할 |
|---|---|
| `Role` | 특정 Namespace에서 사용할 권한을 정의 |
| `ClusterRole` | 클러스터 범위 또는 여러 Namespace에서 재사용할 권한을 정의 |
| `RoleBinding` | 특정 Namespace 안에서 Role 또는 ClusterRole을 주체에게 부여 |
| `ClusterRoleBinding` | ClusterRole을 클러스터 전체 범위로 주체에게 부여 |

**1. Role — 특정 네임스페이스 안에서 허용할 권한을 정의**

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: backend
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
```

> ⚠️ Role을 만들었다고 해서 그 권한을 바로 사용할 수 있는 건 아니다. **Role은 권한을 정의할 뿐, 그 권한을 받을 주체는 아직 정해지지 않은 상태다.**

- `apiGroups`: 리소스가 속한 API 그룹을 지정. **빈 문자열(`""`)은 Core API Group**을 의미한다 (Pod, Service, ConfigMap, Secret, Namespace, PersistentVolume, PersistentVolumeClaim 등).
- `resources`: 권한을 적용할 쿠버네티스 리소스 (`pods`, `services`, `configmaps` 등).
- `verbs`: 리소스에 대해 허용할 작업.

| Verb | 의미 | 관련 명령어 예시 |
|---|---|---|
| `get` | 특정 리소스 하나 조회 | `kubectl get pod my-pod` |
| `list` | 리소스 목록 조회 | `kubectl get pods` |
| `watch` | 리소스 변경 상태 지속 감시 | `kubectl get pods --watch` |
| `create` | 새로운 리소스 생성 | `kubectl create`, 신규 `apply` |
| `update` | 리소스 전체 수정 | 리소스 교체 형태의 수정 |
| `patch` | 리소스 일부 수정 | `kubectl patch`, 일부 `apply` |
| `delete` | 특정 리소스 삭제 | `kubectl delete pod my-pod` |
| `deletecollection` | 여러 리소스를 한 번에 삭제 | 라벨 조건 일괄 삭제 |

**2. RoleBinding — Role에 정의된 권한을 특정 사용자·그룹·ServiceAccount에 연결**

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: bind-pod-reader
  namespace: backend
subjects:
  - kind: ServiceAccount
    name: backend-reader
    namespace: backend
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: pod-reader
```

- `subjects`: 권한을 받을 주체를 정의한다. 주체로는 **사용자(User)**, **그룹(Group)**, **ServiceAccount**가 올 수 있으며, 여러 주체에게 동일한 권한을 줄 수도 있다.
- `roleRef`: 어떤 권한(Role/ClusterRole)을 연결할지 정의한다.

**ClusterRole — 권한은 기본적으로 최소한만 주는 것이 원칙**

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-reader
  # namespace 없음
rules:
  - apiGroups: [""]
    resources: ["nodes"]
    verbs: ["get", "list", "watch"]
```

ClusterRole은 **특정 네임스페이스에 속하지 않는 리소스**(Node, Namespace, PersistentVolume, StorageClass 등)에 대한 권한이 필요할 때 사용한다.

**ClusterRoleBinding — ClusterRole의 권한을 클러스터 전체 범위에서 주체에게 부여**

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: bind-node-reader
subjects:
  - kind: ServiceAccount
    name: monitoring-reader
    namespace: monitoring
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: node-reader
```

##### Role ↔ ClusterRole 비교

| 구분 | Role | ClusterRole |
|---|---|---|
| 리소스 범위 | 특정 Namespace | 클러스터 범위 |
| Namespace 지정 | 필요 | 지정하지 않음 |
| Namespace 리소스 권한 | 가능 | 가능 |
| 클러스터 범위 리소스 권한 | 불가능 | 가능 |
| 여러 Namespace 재사용 | 직접 불가능 | 가능 |
| 예시 | 특정 팀의 Pod 조회 | Node 조회, 전체 Namespace의 Pod 조회 |

##### 실무 사용 예시

**1. 팀별 네임스페이스 권한 분리**
`frontend`, `backend`, `monitoring`, `argocd` 네임스페이스로 나눈 뒤, frontend 개발자는 `frontend` Namespace의 Pod 조회 / Deployment 수정 / 로그 조회 권한만 가지고, `backend`·`monitoring` 네임스페이스 접근은 제한한다.

**2. 개발자-운영자 권한 분리**

| 역할 | 허용 | 제한 |
|---|---|---|
| 개발자 | Pod 조회, Pod 로그 확인, Deployment 조회, 제한된 Deployment 수정 | Namespace 삭제, Node 수정, ClusterRole 생성, 전체 Secret 조회 |
| 운영자 | 워크로드 관리, Namespace 관리, 스토리지·네트워크 리소스 관리, 필요한 RBAC 관리 | - |

**3. 애플리케이션별 ServiceAccount 적용**
ArgoCD, Prometheus, Ingress Controller, 개인 프로젝트마다 **전용 ServiceAccount**를 따로 만들어 사용한다.

##### RBAC 최종 정리

| 개념 | 정리 |
|---|---|
| RBAC | 역할을 기준으로 Kubernetes API 접근 권한을 제어한다 |
| Role | 특정 Namespace의 권한을 정의한다 |
| ClusterRole | 클러스터 범위 또는 재사용할 권한을 정의한다 |
| RoleBinding | Role 또는 ClusterRole을 특정 Namespace에서 주체에게 부여한다 |
| ClusterRoleBinding | ClusterRole을 클러스터 전체 범위에서 주체에게 부여한다 |

#### | Service Account

**Pod와 같은 애플리케이션이 쿠버네티스 API를 사용할 때 사용하는, 클러스터 내부의 신원(Identity)이다**

```
사람            → User Account로 인증 → kubectl을 통해 Kubernetes API 사용
Pod 내부 애플리케이션 → ServiceAccount로 인증 → Kubernetes API 사용
```

##### 모든 파드가 Kubernetes API를 사용하는가? → 아니다

일반적인 WAS(Web Application Server) 흐름을 생각해보면:

```
사용자 요청
  → Ingress / API Gateway (Ingress Traffic 담당)
  → Service → EndpointSlice
  → WAS Pod → WAS Container
  → DB Container → DB Headless Service
```

이 흐름에서는 **K8s API가 필요 없다.** 반대로 아래와 같은 경우에는 Kubernetes API 호출이 필요하다.

- Prometheus가 Pod와 Node 상태를 조회할 때 (`Prometheus Pod → Kubernetes API Server → Pod/Node/Service 상태 조회`)
- ArgoCD가 Deployment와 Service를 생성하거나 수정할 때
- Ingress Controller가 Ingress와 Service 상태를 감시할 때
- 애플리케이션이 ConfigMap이나 다른 Pod 정보를 직접 조회할 때

> 💡 k8s API를 사용하려면 2가지가 필요하다. **인증**(나는 누구인가 — 내부 리소스는 ServiceAccount로 대신 인증한다)과 **인가**(나는 무엇을 할 수 있는가 — RBAC로 결정한다).

##### ServiceAccount 사용 구조

```
Pod
 └─ 사용 → ServiceAccount
              └─ 인증 정보 → Kubernetes API Server
                              └─ 권한 검사 → RBAC → 요청 허용 또는 거부
```

**전체 구성 순서**

1. **ServiceAccount 생성**

```yaml
# be-sa.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: backend-api-sa
  namespace: backend
```

2. **Role 생성**

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: configmap-reader
  namespace: backend
rules:
  - apiGroups: [""]
    resources:
      - configmaps
    verbs:
      - get
      - list
      - watch
```

3. **RoleBinding으로 연결**

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: bind-configmap-reader
  namespace: backend
subjects:
  - kind: ServiceAccount
    name: backend-api-sa
    namespace: backend
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: configmap-reader
```

4. **Pod에 ServiceAccount 연결**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: backend-api
  namespace: backend
spec:
  serviceAccountName: backend-api-sa
  containers:
    - name: backend-api
      image: example/backend-api:1.0
```

> 💡 Deployment에 적용한다면 `spec.template.spec` 부분에 `serviceAccountName`을 작성하면 된다.

##### Default Service Account 주의점

Pod에 ServiceAccount를 지정하지 않으면 해당 Namespace의 **default ServiceAccount**를 사용한다. 만약 default ServiceAccount에 권한을 부여하면, **그 네임스페이스 안에서 SA를 지정하지 않은 모든 파드가 같은 권한을 갖게 되는 문제**가 생긴다. 그래서 실무에서는 **워크로드별 SA, 네임스페이스별 SA**를 만드는 것이 일반적이다.

##### ServiceAccount는 Namespace에 속한다

```yaml
metadata:
  name: backend-api-sa
  namespace: backend
```

같은 이름의 SA라도 네임스페이스가 다르면 서로 다른 주체로 취급된다.

```
backend/backend-api-sa   →  system:serviceaccount:backend:backend-api-sa
frontend/backend-api-sa  →  system:serviceaccount:frontend:backend-api-sa
```

##### Q&A

- **하나의 SA를 여러 Pod에 사용할 수 있나?** → 가능하다. 같은 애플리케이션의 여러 Replica(파드)가 파드 템플릿에 정의된 동일한 SA를 함께 사용한다.
- **하나의 SA에 여러 권한을 줄 수 있나?** → 가능하다. Role A, Role B를 둘 다 하나의 SA에 RoleBinding으로 연결할 수 있다.

##### 실무에서 사용하는 방법

1. **애플리케이션별로 ServiceAccount 구성**: `frontend → frontend-sa`, `backend → backend-sa`, `prometheus → prometheus-sa`
2. **defaultServiceAccount에는 권한을 주지 않기**
3. **최소 권한 원칙 적용**

```
필요한 것
- Pods get, list, watch

부여하면 안 되는 불필요한 권한
- Pods delete
- Secrets get
- Namespaces create
- 모든 리소스(*)
```

4. **"생성", "삭제", "수정" 권한은 특히 유의해서 사용**
   - 클러스터에서는 **삭제보다 생성 권한이 훨씬 위험할 수 있다.** 삭제된 리소스는 원하는 상태(Desired State)에 따라 어차피 재생성되지만, 잘못된 생성 권한은 node affinity, anti-affinity 설정이 없을 경우 자원 제약을 넘어서는 리소스를 계속 만들어낼 수 있기 때문이다.
   - 다만 **삭제가 정말 위험해지는 순간은 "네임스페이스 삭제"**다. 네임스페이스를 삭제하면 그 안의 모든 리소스가 함께 삭제되기 때문이다.

##### User Account vs ServiceAccount

| 구분 | User Account | ServiceAccount |
|---|---|---|
| 주요 사용자 | 개발자, 운영자 | Pod, 애플리케이션, 운영 도구 |
| 사용 목적 | 사람이 클러스터를 관리 | 프로그램이 API Server에 접근 |
| Kubernetes API 리소스 | 기본 `User` 리소스가 없음 | `ServiceAccount` 리소스가 있음 |
| 생성·관리 | 인증서, OIDC 등 외부 인증 체계 | Kubernetes API로 생성 |
| 범위 | 인증 체계에 따라 관리 | Namespace에 속함 |
| 주요 인증 정보 | 인증서, OIDC Token 등 | ServiceAccount Token |
| 권한 부여 | RBAC | RBAC |
| 사용 예시 | 개발자, 클러스터 관리자 | Prometheus, ArgoCD |

##### AWS(EKS) 클러스터에서 User Account 관리하기

k8s 클러스터를 생성하는 방식은 크게 2가지다.

- **a. EKS** — 보통 실무에서 많이 사용
- **b. kubeadm** (kube-spray, k3s 등) — 직접 구축

EKS에서는 **AWS IAM**과 **Kubernetes RBAC**가 2단계로 동작한다.

```
AWS IAM       → 이 사용자가 누구인지 인증 → EKS 클러스터에 들어올 수 있는지 결정
Kubernetes RBAC → 들어온 사용자가 어떤 리소스에, 어떤 작업을 할 수 있는지 결정
```

```
IAM Identity Center
├─ EKS-Admins 그룹
├─ EKS-Developers 그룹
└─ EKS-LogViewers 그룹
        ↓ 각 그룹에 IAM Role 할당
   EKS Access Entry
        ↓ Kubernetes Group과 연결
   RoleBinding / ClusterRoleBinding
        ↓
   실제 Kubernetes 권한 부여
```

| EKS Access Policy | 용도 |
|---|---|
| `AmazonEKSClusterAdminPolicy` | 클러스터 전체 관리자 |
| `AmazonEKSAdminPolicy` | 관리자 수준의 Kubernetes 권한 |
| `AmazonEKSEditPolicy` | 워크로드 생성·수정 |
| `AmazonEKSViewPolicy` | 읽기 전용 |
| `AmazonEKSAdminViewPolicy` | 관리자 관점의 확장된 조회 |

```bash
aws eks create-access-entry \
  --cluster-name my-cluster \
  --principal-arn arn:aws:iam::123456789012:role/EKS-AdminRole \
  --type STANDARD
```

> 💡 **Access Entry**는 AWS IAM 사용자/역할을 EKS 클러스터에 등록해서, 그 사용자·역할이 쿠버네티스 리소스에 어떤 권한으로 연결될지 설정하는 기능이다.

##### kubeadm(직접 구축한 클러스터)에서 사용자 권한 관리

EKS를 사용하지 않으면 Access Entry를 쓸 수 없기 때문에 다음과 같은 방법을 쓴다.

1. **사용자별 클라이언트 인증서 발급** — 인증서 그룹을 Kubernetes 인증서 그룹으로 인식시키고, RoleBinding으로 그 그룹에 권한을 묶어서 사용한다.
2. **OIDC**
3. **인증 웹훅 구성**

> ⚠️ 인증서 발급·폐기, kubeconfig 배포를 직접 관리해야 하는 부담이 있어, 실무에서는 **Keycloak** 같은 OIDC 기반 인증 서비스를 함께 사용하는 경우가 많다.

##### Service Account 정리

| 개념 | 정리 |
|---|---|
| ServiceAccount | Pod와 프로그램을 위한 Kubernetes 내부 신원 |
| Role / ClusterRole | 허용할 리소스와 작업 정의 |
| RoleBinding / ClusterRoleBinding | ServiceAccount와 권한 연결 |

#### | Helm

**여러 쿠버네티스 YAML 파일을 하나의 설치 패키지인 Chart로 묶고, 설정값만 바꿔 반복적으로 설치·업데이트할 수 있게 해주는 쿠버네티스 패키지 관리자**

Node의 npm, Python의 pip와 비슷한 역할이지만, **단순한 패키지 매니저는 아니다.**

```
Helm Client (helm) → Chart Repository
       │  (Helm Chart)
       ▼
Kubernetes Cluster
   └── Kubernetes API Server
```

##### 기존 배포 방식의 문제

Express 앱 하나를 배포하려 해도 최소 3개의 YAML이 필요하다.

```
express-app/
├── deployment.yaml   # 애플리케이션 Pod을 생성하고 관리
├── service.yaml       # Pod에 접근할 수 있는 고정 주소 제공
└── configmap.yaml     # 애플리케이션 설정값 저장
```

그런데 실제 서비스에서는 Namespace, ServiceAccount, Role, RoleBinding, Secret, PVC, Ingress까지 더해져 **훨씬 많은 YAML을 관리**해야 하고, 여기에 `dev / stag / prod / feature`처럼 **환경이 여러 개** 존재한다.

```
# prod 용
- configmap.yaml
- secret.yaml
# dev 용
- configmap.yaml
- secret.yaml
# feat 용 / stag 용 ...
```

리소스의 **구조는 같은데, 값만 다른** 상황이 반복된다. 예를 들어 dev의 API URL을 바꾸려면 `configmap.yaml`, Pod의 replicas를 바꾸려면 `deployment.yaml`을 찾아 고쳐야 하는데, **이걸 정확히 찾아 고치기가 어렵고 누구나 손댈 수 있어 위험**하다.

##### Helm이 해결하는 방식

헬름은 쿠버네티스 YAML을 두 가지 구조로 나눈다. **(★ 중요)**

| 구분 | 역할 |
|---|---|
| **Template** | Deployment, Service 등의 공통(반복되는) YAML 구조 |
| **Values** | 이미지 태그, Pod 수, 포트 등 환경마다 바뀌는 설정값 |

```
Helm 동작 순서
1. Template + Values 를 해석
2. 최종 YAML 파일을 생성
3. 그 파일을 Kubernetes API Server에 전달
   → Deployment, Service, ConfigMap 등 생성
```

##### 기존 YAML → Helm Chart로 전환

```
express-app/                 express-chart/
├── deployment.yaml    →     ├── Chart.yaml
├── service.yaml              ├── values.yaml
└── configmap.yaml            └── templates/
                                    ├── deployment.yaml
                                    ├── service.yaml
                                    └── configmap.yaml
```

**1. `Chart.yaml`** — 차트의 이름·버전 등 기본 정보를 적는 파일. 쿠버네티스 리소스를 직접 정의하지 않고, **이 차트가 어떤 패키지인지 설명**하는 역할만 한다.

```yaml
apiVersion: v2
name: express-app
description: Express application Helm chart
type: application
version: 0.1.0
appVersion: "1.0.0"
```

| 항목 | 설명 |
|---|---|
| `name` | Chart 이름 |
| `description` | Chart 설명 |
| `version` | **Chart 자체**의 버전 |
| `appVersion` | Chart가 배포하는 **애플리케이션**의 버전 정보 |

**2. `values.yaml`** — 여러 템플릿에서 사용할 변경 가능한 설정값을 모아놓은 파일.

```yaml
replicaCount: 2

image:
  repository: adapterz/k8s-pod
  tag: "1.0.0"
  pullPolicy: IfNotPresent

message: "Hello Kubernetes"

service:
  type: ClusterIP
  port: 80
  targetPort: 3000

resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 256Mi
```

> 💡 이제는 replicas를 바꾸려고 `deployment.yaml`을, URL을 바꾸려고 `configmap.yaml`을 각각 찾아갈 필요 없이, **모든 값 수정은 `values.yaml` 하나로 모인다.** 환경별로는 `values-dev.yaml`, `values-prod.yaml`, `values-feat.yaml`, `values-stag.yaml`처럼 나눠서 관리한다.

**3. `templates/`** — 반복되는 구조만 담고, 실제 값은 `{{ .Values.xxx }}` 형태로 비워둔다.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-config
data:
  MESSAGE: {{ .Values.message | quote }}
```

##### 최종적으로 만들어지는 흐름

```
Chart.yaml + values.yaml + templates/*.yaml
        ↓  Helm Template 렌더링
  ConfigMap / Deployment / Service (완성된 YAML)
        ↓
  Kubernetes API Server에 전달
```

```bash
# 명령어 하나 + values.yaml 파일 하나로 관리
helm install express ./express-chart
```

##### Helm에서의 Chart vs Release

| 개념 | 의미 |
|---|---|
| **Chart** | 설치에 필요한 Template + Values를 묶은 패키지(설계도). `install`, `update`만 하면 된다 — `pip install`, `npm install`처럼 필요한 패키지(+쿠버네티스 리소스)를 설치한다. |
| **Release** | Chart를 실제 k8s 클러스터에 설치한 **결과물**. `helm install ...`로 만들어진 k8s 리소스 묶음을 Release라고 부른다. |

> 💡 Release는 기록이 남아 **되돌아갈 수 있다는 점에서 타임캡슐과 비슷하다.** 다만 단순히 코드(이미지 버전 등)만 롤백하는 것은 항상 의미가 있지만, **k8s 리소스 구조 자체가 바뀌었거나 내부 리소스 값이 바뀐 상태**라면 코드만 돌려도 에러가 계속 날 수 있다. 즉 "구조는 그대로, 코드만 바뀐" 상황에서 롤백이 안전하다.

**하나의 Chart(template + values 조합)로 여러 환경에 적용**

```bash
helm install express-dev ./express-chart \
  -f values-dev.yaml
```

##### Helm은 kubectl을 대체하지 않는다

| 구분 | `kubectl` | `Helm` |
|---|---|---|
| 주요 역할 | Kubernetes 리소스 직접 관리 | 여러 리소스를 패키지 단위로 관리 |
| 관리 단위 | Pod, Deployment, Service 등 | Chart와 Release |
| YAML 처리 | 완성된 YAML 적용 | Template과 Values로 YAML 생성 |
| 설치 이력 | 애플리케이션 전체 이력 관리가 제한적 | Release Revision 관리 |
| 롤백 | 리소스별로 다르게 처리해야 함 | **Release 단위 롤백** |
| 상태 확인 | Pod, 로그, 이벤트 확인 | Chart 설치 및 Release 상태 확인 |

실무에서는 **kubectl + Helm을 함께 사용**한다. Helm으로는 설치·롤백·업데이트(템플릿 YAML, 환경별 변수, ConfigMap/Secret 관리)를 하고, kubectl로는 Pod 상태, 로그, 이벤트, 네트워크를 확인한다.

##### Helm 패키지 매니저의 진짜 가치

오픈소스 도구를 직접 설치하려면 상당히 까다롭다. 예를 들어 Prometheus를 설치하려면 ServiceAccount, ClusterRole, ClusterRoleBinding, ConfigMap, Deployment(또는 StatefulSet), Service, PVC, Alertmanager 관련 리소스까지 전부 직접 만들어야 한다.

```bash
helm install prometheus \
  prometheus-community/prometheus \
  -f values.yaml \
  -n monitoring
```

Helm을 쓰면 이 모든 리소스를 알아서 만들어준다. Redis, MySQL, MongoDB, Nginx 등도 마찬가지이며, [Artifact Hub](https://artifacthub.io)에서 각 Chart의 설치 명령어를 확인할 수 있다.

##### 실무에서 Helm 사용하기

1. **외부 운영 도구 설치**: Ingress Controller, Prometheus, Grafana, ArgoCD
2. **애플리케이션 배포**(CI/CD와 연계)

```
Git Repository
├── Helm Chart
├── values-dev.yaml
└── values-prod.yaml
        ↓ (이미지 버전 변경 등)
ArgoCD가 변경 감지
        ↓
Helm Template 렌더링
        ↓
Kubernetes에 배포
```

CI(GitHub Actions, Jenkins)가 빌드·테스트를 마치면, CD 단계에서 **Helm values의 이미지 버전을 업데이트**하고 ArgoCD가 이 변경을 감지해 배포하는 방식이 널리 쓰인다.

3. **values에는 변경되는 값만 넣기** — 모든 항목을 다 넣을 필요 없이, 환경마다 달라지는 항목만 overrides로 넣으면 된다.
4. **Chart Repo가 안전한지 확인하고 설치하기** — Artifact Hub에 올라와 있다고 해서 항상 안전하거나 보안적으로 검증된 것은 아니다. 비공식 레포는 특히 주의해야 한다. Helm은 ServiceAccount, Role, ClusterRole 등 필요한 리소스를 전부 만들기 때문에, 잘못된 Chart는 **단일 장애 지점**이 될 수도 있다.
5. **설치하기 전에 `helm template`로 결과물을 미리 확인**

```bash
helm template express ./express-chart
# 로컬에서 렌더링 - k8s에 넣기 전에 결과를 미리 확인
```

6. **평문(Secret 값 등)을 저장하지 않기** — Helm chart, values, template이 GitOps 흐름(GitHub Actions 등)을 타고 Git에 올라가는 경우가 많기 때문이다.

#### | Ingress

**클러스터 외부의 HTTP·HTTPS 요청을 도메인과 경로에 따라 내부 Service로 연결하는 라우팅 규칙이다**

```
외부 사용자
   ↓
Public EC2 (NLB)
   ↓
Ingress Controller  ← Ingress 규칙 확인
   ↓
Service
   ↓
Pod
```

| 구분 | 한 줄 정리 |
|---|---|
| **Ingress** | 외부 요청을 어떤 Service로 전달할지 정의한 **규칙(선언)** |
| **Ingress Controller** | Ingress 규칙을 읽고 **실제로 요청을 전달하는 프로그램** (nginx, HAProxy 등) |

##### Ingress가 왜 필요한가?

기존에는 외부 요청을 Pod까지 가져오기 위해 **NodePort Service**를 사용했다.

```
사용자 → NodeIP:NodePort → Service → Pod

프론트엔드: http://203.0.113.10:30080
백엔드:     http://203.0.113.10:30081
관리자:     http://203.0.113.10:30082
```

이 방식은 다음 문제를 일으킨다.

1. **서비스마다 포트를 관리해야 한다** → 포트가 늘어날수록 공격 지점(attack surface)이 넓어진다.
2. **일반적인 웹 접근 방식이 아니다** → 사용자가 익숙한 80/443 포트가 아니라 낯설다.
3. **HTTPS 설정이 분산된다** → 서비스마다 별도의 NodePort를 열어놓는다는 건, 서비스마다 각각 SSL Termination을 처리해줘야 한다는 뜻이다.

##### Ingress의 해결 방법

외부에서는 언제나 익숙한 **80, 443 포트**로만 요청하고 (`https://example.com`), Ingress Controller가 요청의 **도메인(Host)**과 **경로(Path)**를 확인해서, 미리 설정된 규칙(Ingress)에 따라 적절한 Service로 요청을 분배한다.

```
                    ┌→ frontend-service → frontend Pod
사용자 → Ingress Controller ─┼→ backend-service  → backend Pod
                    └→ admin-service    → admin Pod
```

##### Ingress의 핵심 역할 — URL 기반 라우팅

요청 도메인이 다르면 서로 다른 서비스로 전달한다.

```
frontend.example.com → frontend-service
api.example.com      → backend-service
admin.example.com    → admin-service
```

```yaml
spec:
  rules:
    - host: frontend.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80
    - host: api.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: backend-service
                port:
                  number: 80
```

##### Ingress ↔ Ingress Controller, 다시 한번 구분

- **Ingress**: 직접 요청을 처리하지 않는다. **규칙을 적어서 저장해두는 것뿐**이며, 선언만 해두면 실제로는 아무 일도 일어나지 않는다.
- **Ingress Controller**: Ingress 리소스를 감시하고, 그 규칙에 맞게 **실제 프록시나 로드밸런서를 구성**하는 컨트롤러다. 즉, Ingress에 적어둔 규칙을 진짜로 실행하는 주체다.

대표적인 구현체: **ingress-nginx**, **Traefik**, **HAProxy Ingress**, **Kong Ingress Controller**, **AWS Load Balancer Controller**, **GKE Ingress Controller**

> 💡 실무나 팀 프로젝트에서는 Ingress Controller를 "왜 이 구현체로 쓰는지", 그리고 "왜 NodePort나 API Gateway 대신 Ingress를 쓰는지"를 스스로 분석해볼 필요가 있다.

##### 전체 동작 과정

```
1. 사용자가 Ingress YAML 생성
2. API Server가 Ingress 리소스 저장
3. Ingress Controller가 변경 감지
4. Controller가 라우팅 설정 생성
5. 외부 요청 수신
6. Host와 Path 확인
7. 대상 Service 또는 Endpoint로 전달
8. Pod가 요청 처리
```

##### Ingress Class

클러스터 안에 여러 종류의 Ingress Controller(예: nginx ingress와 AWS Load Balancer Controller)가 동시에 존재할 수 있다. 이때 **어떤 Ingress를 어떤 컨트롤러가 처리해야 하는지 지정하는 필드**가 `ingressClassName`이다.

```yaml
spec:
  ingressClassName: nginx
```

##### TLS 종료(Termination)

```
Client
   ↓ HTTPS
Ingress Controller
   ↓ HTTP 또는 HTTPS
Service
   ↓
Pod
```

인증서와 키 값은 **Secret**으로 관리한다.

```yaml
kind: Ingress
metadata:
  name: tls-ingress
  namespace: example
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - example.com
      secretName: example-tls
```

##### Ingress와 NodePort의 관계

Ingress를 쓴다고 NodePort의 어려움이 항상 사라지는 것은 아니다. **EKS 환경**에서는 Ingress를 AWS ALB 등에 편하게 연결할 수 있도록 설정할 수 있어 어려움이 줄어들지만, **베어메탈이나 kubeadm 환경**에서는 결국 `Ingress → NodePort` 형태를 띠게 되는 경우가 있다. (NLB 대신 Nginx 리버스 프록시가 있는 EC2를 앞단에 둬도 된다.)

```
외부 사용자
   ↓
NodePort 또는 외부 Load Balancer
   ↓
Ingress Controller
   ↓
Service
   ↓
Pod
```

> 💡 **왜 Ingress Controller 앞에 NLB(L4)가 있고 ALB(L7)를 굳이 또 두지 않을까?** Ingress Controller 자체가 이미 **L7 리버스 프록시** 역할(HTTP/HTTPS의 Host, Path를 구분해 요청을 배분)을 하고 있기 때문에, 그 앞에 ALB를 또 두려면 내부 Service 구성을 ALB도 알고 있어야 해서 이중 관리가 된다. 그래서 앞단은 단순 전달만 하는 **NLB(L4)**로 두는 경우가 많다.

##### Ingress 프로토콜의 한계

Ingress는 **HTTP, HTTPS만 처리**하며, **TCP, UDP 트래픽은 처리하지 않는다.** TCP/UDP를 처리해야 하는 경우에는 다음을 사용한다.

- `NodePort`
- `LoadBalancer` Service
- **API Gateway** — 최근 현업에서 표준화되고 있는 리소스로, HTTP뿐 아니라 TCP/UDP까지, 그리고 URL·Domain 기반 프록시까지 지원한다.

> 💡 사실 **Ingress는 최신 트렌드에서는 조금씩 밀려나고 있으며**, 더 넓은 트래픽 처리 범위를 가진 API Gateway가 그 자리를 대체해가는 흐름이 있다.

##### Ingress 정리

| 개념 | 정리 |
|---|---|
| Ingress | 외부 HTTP·HTTPS 요청을 Service로 전달하는 규칙 |
| Ingress Controller | Ingress 규칙을 읽고 실제 요청을 처리하는 프로그램 |
| IngressClass | 어떤 Controller가 Ingress를 처리할지 지정 |
| Host Routing | 도메인에 따라 Service 선택 |
| Path Routing | URL 경로에 따라 Service 선택 |
| TLS Termination | Controller에서 HTTPS 인증서와 암호화 연결 처리 |

### 🗨️ 오늘의 회고

- 오늘은 "누가 클러스터를 조작할 수 있는가"라는 질문을 RBAC → ServiceAccount → Helm → Ingress로 이어지는 흐름 속에서 계속 마주쳤다. kubectl뿐만 아니라 ArgoCD, Prometheus, Ingress Controller, Pod 내부 애플리케이션까지 **모두 API Server의 "주체"가 될 수 있다**는 사실을 알고 나니, RBAC가 왜 그렇게 촘촘하게 설계되어 있는지 이해가 됐다.
- **Role/ClusterRole(무엇을 허용할지)과 RoleBinding/ClusterRoleBinding(누구에게 줄지)을 분리**해서 설계한다는 점이 인상 깊었다. 이렇게 분리해두면 동일한 권한 정의(Role)를 여러 주체에 재사용할 수 있고, 권한을 바꿀 때도 Role만 수정하면 되니 관리가 훨씬 유연해진다.
- ServiceAccount 파트에서 가장 기억에 남는 건 **"생성 권한이 삭제 권한보다 위험할 수 있다"**는 관점이었다. 삭제된 리소스는 원하는 상태를 유지하려는 쿠버네티스의 특성상 다시 만들어지지만, 잘못된 생성 권한은 자원 제약이 없다면 클러스터 전체에 부담을 줄 수 있다는 설명이 실무적으로 유용했다. 다만 네임스페이스 삭제만큼은 예외적으로 위험하다는 점도 함께 챙겨야 할 포인트였다.
- Helm은 오늘 배운 것 중 가장 "왜 필요한지"가 명확하게 다가온 도구였다. YAML 파일이 환경별로 계속 중복되고, 값 하나를 바꾸려고 여러 파일을 뒤지던 문제가 **Template(구조) + Values(값)** 라는 단순한 분리로 해결되는 과정이 깔끔했다. 다만 Helm이 kubectl을 대체하는 게 아니라 **역할이 다른 도구**라는 점, 그리고 Chart(설계도)와 Release(설치 결과이자 롤백 지점)를 구분해야 한다는 점을 헷갈리지 않도록 다시 정리해두고 싶다.
- Ingress는 "왜 NodePort로는 부족한가"에서 출발해서 Ingress Controller, IngressClass, TLS Termination까지 이어지는 흐름이 자연스러웠다. 특히 **Ingress는 규칙만 저장하고, 실제 동작은 Ingress Controller가 담당한다**는 구분이 핵심이었다. 다만 Ingress가 HTTP/HTTPS만 처리하고 TCP/UDP는 처리하지 못한다는 한계, 그리고 API Gateway가 그 한계를 넘어서는 방향으로 트렌드가 이동하고 있다는 점은 다음에 더 깊게 봐야 할 주제로 남겨둔다.
- 전체적으로 오늘 배운 네 가지 주제(RBAC, ServiceAccount, Helm, Ingress)는 결국 "**누가 무엇을 할 수 있는가**"(RBAC/SA)와 "**어떻게 반복 가능하고 안전하게 운영하는가**"(Helm/Ingress)라는 두 축으로 정리된다는 느낌을 받았다.
