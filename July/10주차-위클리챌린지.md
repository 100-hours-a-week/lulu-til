## 1. 기본 실행 구조 YML

### 1-1. 백엔드 기본 실행 구조

**pod.yml**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: lulu-backend-pod
  labels:
    app: lulu-backend
spec:
  containers:
    - name: backend-container
      image: 536697237610.dkr.ecr.ap-northeast-2.amazonaws.com/lulu-backend:latest
      ports:
        - containerPort: 8080
      env:
        - name: SPRING_PROFILES_ACTIVE
          value: "prod"
        - name: DB_PASSWORD
          value: ...비밀
        - name: JWT_SECRET
          value: ...비밀
          value: ""
        - name: CLOUD_AWS_CREDENTIALS_SECRET_KEY
          value: ""
      readinessProbe:
        httpGet:
          path: /api/health-check
          port: 8080
        initialDelaySeconds: 10
        periodSeconds: 20
      livenessProbe:
        httpGet:
          path: /api/health-check
          port: 8080
        initialDelaySeconds: 10
        periodSeconds: 20
        failureThreshold: 5
        timeoutSeconds: 5
  imagePullSecrets:
    - name: ecr-secret
```

**service.yml**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: lulu-backend-service
spec:
  type: ClusterIP
  selector:
    app: lulu-backend
  ports:
    - protocol: TCP
      port: 8080
      targetPort: 8080
```

## 2. 회고록

### 개요

## 3. 선택 가능한 방식들과 비교, 그리고 고른 이유

### 3-1. Pod 유형: 단일 컨테이너 vs 멀티 컨테이너

| 구분 | 단일 컨테이너 구조 | 멀티 컨테이너 구조 (사이드카 등) |
| --- | --- | --- |
| 개념 | 하나의 Pod = 하나의 컨테이너 | 하나의 Pod 안에 여러 컨테이너가 네트워크/볼륨을 공유 |
| 장점 | 장애 지점이 명확, 독립적인 스케일링 가능, 생명주기 관리가 단순 | 로그 수집기, 프록시 등 보조 기능을 밀접하게 결합 가능 |
| 단점 | 보조 기능이 필요하면 별도 Pod/Deployment로 관리해야 함 | 컨테이너 간 포트·볼륨 충돌 우려, **생명주기가 강제로 동일**, 장애 원인 파악이 어려움, 독립적으로 확장 불가 |

**선택: 단일 컨테이너 구조**

가장 결정적인 이유는 **스케일 아웃 단위**였다. 쿠버네티스의 배포 단위는 Pod이기 때문에, 멀티 컨테이너로 구성하면 트래픽이 몰려 백엔드만 늘리고 싶어도 같은 Pod 안에 있는 프론트엔드(혹은 헬퍼) 컨테이너까지 함께 늘어난다. 우리 서비스는 실제로 트래픽 부하가 몰리는 지점이 백엔드 API 처리이기 때문에, 프론트엔드와 결합된 멀티 컨테이너 구조는 비효율적이라고 판단했다. 또한 헬퍼 컨테이너의 초기화·종료 처리 시간이 Pod 전체의 생성/삭제 속도에 영향을 주는 것도 트래픽 스파이크 대응에 불리하다고 봤다. 결과적으로 백엔드/프론트엔드를 각각 독립된 Pod(→ Deployment)로 분리하는 것이 장애 격리와 확장성 측면에서 합리적이라고 결론 내렸다.

### 3-2. 워커 노드 구성: 신규 구축 vs 기존 인프라 재활용

새로 EC2를 통째로 구축하는 방법도 있었지만, 이미 운영 중이던 프라이빗 서브넷의 BE/FE EC2를 워커 노드로 등록하고, 마스터 노드만 별도로 1대 신규 생성하는 방식을 선택했다.

- **선택 이유**
    - **비용 효율성**: 이미 떠 있는 EC2 자원을 재활용하므로 신규 인프라 비용이 마스터 노드 1대분으로 최소화된다.
    - **가용성(Node Affinity)**: 워커 노드 4대가 AZ 1, AZ 2에 2대씩 이미 나뉘어 있었기 때문에, 한쪽 AZ에 장애가 나도 반대편 AZ 노드가 서비스를 이어받을 수 있는 구조를 그대로 가져갈 수 있었다.
    - 다만 비용 문제로 실제 운영은 AZ 1의 BE/FE만 사용하고, 필요 시 AZ 2로 확장하는 것으로 축소하였다.

### 3-3. 네트워크 배치: 마스터 노드를 퍼블릭 vs 프라이빗 서브넷에 둘 것인가

- **퍼블릭 배치**: 관리 편의성(외부에서 바로 API 서버 접근)은 있지만, API 서버가 인터넷에 노출되어 공격 표면이 커진다.
- **프라이빗 배치(선택)**: 마스터 노드와 워커 노드를 모두 프라이빗 서브넷에 두고, 퍼블릭 서브넷에는 오직 Bastion Host만 남겨 클러스터 진입점을 하나로 단일화했다.

컨트롤 플레인이 뚫리면 클러스터 전체가 위험해지기 때문에, "외부에서 직접 접근 가능한 지점을 최소화한다"는 원칙을 최우선으로 삼았다. 대신 관리 편의성은 Bastion을 경유하는 방식으로 감수했다.

### 3-4. Service 타입 비교: ClusterIP / NodePort / LoadBalancer

| 타입 | 특징 |
| --- | --- |
| **ClusterIP** | 클러스터 내부 DNS로만 접근 가능, 외부 노출 없음 |
| **NodePort** | 모든 워커 노드의 특정 포트(30000~32767)를 열어 외부에서 접근 가능 |
| **LoadBalancer** | 클라우드의 로드밸런서를 자동 프로비저닝 (AWS면 ELB) |

**ClusterIP 선택**

과제의 필수 조건이 "백엔드 파드는 외부에서 접속하지 못해야 한다"였다. ClusterIP는 클러스터 내부에서만 접근 가능한 서비스 유형으로, 외부 네트워크로 노출되지 않는다.

### 3-5. Probe 종류 및 점검 방식 선택

| 프로브 종류 | 설명 및 특징 |
| --- | --- |
| **Startup Probe** | 애플리케이션의 **초기화 과정이 완료되었는지 확인**하며, 초기화 시간이 긴 애플리케이션에서도 안정적으로 동작할 수 있도록 돕습니다. |
| **Liveness Probe** | 애플리케이션이 **정상적으로 실행 중인지 지속적으로 확인**하며, 비정상 상태로 판단되면 자동 복구를 트리거합니다. |
| **Readiness Probe** | 애플리케이션이 **사용자 요청을 처리할 준비가 되었는지 점검**하며, 준비되지 않은 상태에서 트래픽이 유입되지 않도록 방지합니다. |

일반적으로 Liveness Probe의 경우, 데드락에 빠지거나 멈춰서 스스로 회복할 수 없는 애플리케이션에 적합하고, Readiness Probe는 애플리케이션 초기화 시간이 길거나, DB 연결 등 사전 작업이 필요한 경우, 롤링 업데이트 시 무중단 배포를 위해 사용한다. Startup Probe의 경우, 가동 시간이 매우 불규칙하거나 오래 걸리는 애플리케이션에 적합하며, 기동 중에 Liveness 프로브가 실패하여 무한 재시작되는 현상을 방지한다.

- **선택: Readiness Probe + Liveness Probe**

백엔드의 경우 Spring이기 때문에 애플리케이션 초기화 시간이 길고 DB 연결 등 사전 작업이 필요하다. 하지만 프로젝트가 큰 상태가 아니기 때문에 초 단위의 시간이 걸리고 롤링 업데이트가 필요하기 때문에 Startup Probe 대신 Readiness Probe를 선택하였다. 하지만 재시작을 해야 하는 경우(데드락 상황)도 발생할 수 있기 때문에 지속적인 생존 확인을 위해 Liveness Probe도 함께 사용했다.

프론트의 경우 단순하게 켜지면 바로 투입되면 되고, 지속적인 생존 확인만 필요하기 때문에 Liveness Probe와 Readiness Probe를 사용하였고, Startup Probe는 고려하지 않았다.

**일시적 장애를 고려한 설정값**

- 백엔드
    ```
    initialDelaySeconds: 10
    periodSeconds: 20
    failureThreshold: 5
    timeoutSeconds: 5
    ```
- 프론트
    ```
    initialDelaySeconds: 5
    periodSeconds: 20
    failureThreshold: 5
    timeoutSeconds: 5
    ```

| 설정 | 설명 |
| --- | --- |
| **초기 지연 시간(Initial Delay)** | 애플리케이션이 완전히 기동되기 전에는 LivenessProbe가 작동하지 않도록 설정합니다. 예: 컨테이너 시작 후 10초 동안 점검 대기 |
| **점검 주기(Period)** | 너무 짧은 주기로 점검하면, 일시적인 장애가 비정상 상태로 잘못 판단될 수 있습니다. 예: 10~30초 간격으로 점검 |
| **실패 임계값(Failure Threshold)** | 몇 번의 점검 실패를 허용할지 설정하여, 단기적인 장애를 무조건 재시작으로 연결하지 않도록 합니다. 예: 3회 이상 연속 실패 시 컨테이너 재시작 |
| **타임아웃(Timeout)** | 애플리케이션이 일시적인 부하 중에도 정상적으로 응답할 시간을 확보하도록 충분히 긴 시간으로 설정합니다. 예: 응답 대기 시간 5초 |

초기 지연 시간의 경우 앱 부팅 시간보다 여유 있게 설정했다. 특히 Startup Probe가 없기 때문에 좀 더 여유 있게 설정했다. 나머지 설정값들은 표준 권장 값에 맞춰서 설정했다.

## 4. 수행 과정에서 겪은 고민들

### 4-1. 워커노드 인스턴스 사양 문제

초기에 워커노드로 재활용하려던 EC2가 t3.micro였는데, 쿠버네티스 권장 최소 사양(vCPU 2, RAM 2GB 이상)에 미달했다. 비용을 최소화하고 싶었지만 최소 사양을 낮추면 클러스터 자체가 불안정해질 수 있어서, 비용과 안정성 사이에서 t3.small로 업그레이드하는 것으로 결정했다.

### 4-2. AZ 축소 운영 결정

원래는 AZ 1, AZ 2에 각각 BE/FE EC2가 1대씩(총 4대) 있었지만, 비용 문제로 AZ 1의 BE/FE만 워커 노드로 활용하기로 했다. 이는 앞서 설계 단계에서 강조했던 "AZ 장애 대응력"과 상충되는 결정이라, 실습 단계에서는 비용을, 운영 단계로 갈 때는 다시 AZ 2를 살려 트래픽을 분산하겠다는 계획만 우선적으로 세워두었다. 설계와 실제 운영 사이의 괴리를 어떻게 문서화해서 남겨야 하는지 고민한 부분이다.

### 4-3. 이미지 Pull 및 시크릿 관리

ECR 프라이빗 리포지토리에서 이미지를 받아와야 했기 때문에 `imagePullSecrets`로 `ecr-secret`을 등록해야 했다. 초기에 이 시크릿을 등록하지 않으면 `ImagePullBackOff` 상태로 멈추는 걸 경험하였다.

### 4-4. 환경변수로 시크릿을 그대로 노출한 점

`DB_PASSWORD`, `JWT_SECRET` 등을 Pod yml의 `env`에 평문으로 박아 넣었는데, 이 방식은 `kubectl get pod -o yaml`만 쳐도 민감정보가 그대로 노출되고, 소스 관리(yml을 git에 올릴 경우)에도 위험하다는 것을 알고 있지만, 추후 강의 진도에서 Secret을 다루게 되면 수정할 예정이다.

## 5. 전체 회고 마무리

이번 과제를 하면서 가장 크게 느낀 건, **쿠버네티스 리소스 하나하나가 "왜 이 옵션이 필요한가"를 설명할 수 있어야 한다**는 점이었다. `kubeadm init`이나 `sysctl` 설정처럼 가이드를 그대로 따라 하면 통과되는 부분도 있었지만, 실제로 왜 그 설정이 필요한지 하나씩 짚어보는 과정이 공부가 많이 됐다.

실제 구현 단계에서 설계와 타협해야 하는 순간을 마주하면서, 이상적인 설계와 현실적인 제약 사이에서 어떻게 근거를 남기며 결정할지 연습이 됐다.

### 아쉬운 점 / 다음 개선 과제

1. `DB_PASSWORD`, `JWT_SECRET`을 Pod yml에 평문으로 넣은 부분 → `kubectl create secret`으로 분리하고 `secretKeyRef`로 참조하도록 개선
2. 이미지 태그를 `latest`로 고정한 부분 → 배포 재현성과 롤백을 위해 커밋 해시나 버전 태그로 관리 필요
