##### | Agile 개발 방법론

**고객의 요구사항, 변화된 환경에 맞게 요구를 더하고 수정해나가는 탄력적인 방법론이다.** 고정된 프로세스가 아니라, **협업과 워크플로우를 바라보는 관점** 자체를 의미한다.

> 💡 Agile은 특정 툴이나 절차의 이름이 아니라, "계획을 완벽하게 세우고 그대로 실행"하는 대신 "짧은 주기로 결과물을 내고 피드백을 반영해 계속 조정"하는 사고방식에 가깝다.

**실무 적용 사례**

| 회사 | 적용 방식 |
|---|---|
| 카카오 | 2주 단위 스프린트로 서비스를 지속적으로 개선하고, 사용자 피드백을 즉각 반영 |
| 토스 | 엔지니어와 디자이너가 함께 작업하는 **소규모 크로스펑셔널 팀** 운영 |

**주기 관리 — Scrum Process**

| 구성 요소 | 설명 |
|---|---|
| 스프린트(Sprint) | 2~4주 기간의 개발 주기 |
| 데일리 스크럼(Daily Scrum) | 15분 내외로 매일 진행 상황을 공유하는 짧은 미팅 |
| 스프린트 회고(Retrospective) | 지난 스프린트를 성찰하고 개선점을 도출 |

##### | 칸반 보드 (Kanban)

**작업 흐름을 시각화해서 업무 상황을 한눈에 파악할 수 있게 하는 방법론이다.**

**칸반의 핵심 원칙**

1. 현재 진행 중인 작업 시각화
2. **동시 진행 작업 제한(WIP Limit)**
3. 작업 흐름 관리와 지속적 개선

일반적인 칸반 보드의 컬럼 구성:

```
할 일 → 진행 중 → 해결 → 완료
```

> 💡 스크럼이 "정해진 주기(스프린트)"로 일하는 방식이라면, 칸반은 **주기보다 흐름(Flow) 자체**에 집중해 진행 중인 작업 수를 제한함으로써 병목을 눈에 띄게 만드는 방식이다.

**대표 도구**: JIRA, GitHub Project, Notion 칸반보드 템플릿

##### | JIRA 사용 가이드

**Agile하게 운영되는 팀의 운영·관리 툴**이다. 개발자와 관리자 모두 사용하며, 업무 관리·모니터링·일정 관리 등에 쓰인다.

| 특징 | 설명 |
|---|---|
| 강력한 통합성 | GitHub, Confluence, Slack 등 다양한 개발 도구와 연동 |
| 유연한 커스터마이징 | 조직에 맞는 워크플로우 및 필드 설정 가능 |
| 투명한 의사소통 | 업무 진행 상황을 실시간으로 공유 |

**JIRA Software — Ticket 종류**

| 유형 | 설명 |
|---|---|
| 에픽(Epic) | 큰 작업 단위 |
| 스토리(Story) | 사용자 관점의 기능 요구사항 |
| 태스크(Task) | 일반적인 작업 항목 |
| 버그(Bug) | 오류 수정이 필요한 작업 |
| 하위 태스크(Sub-task) | 이슈를 더 작은 단위로 나눈 작업 |

> 💡 티켓은 **2~3일 안에 끝낼 수 있는 단위**로 쪼개서 만드는 것이 좋다. 너무 큰 단위로 티켓을 만들면 진행 상황을 추적하기 어렵고, 스크럼에서 공유할 때도 "거의 다 했어요"라는 애매한 상태로 오래 머무르기 쉽다.

**JIRA 이슈의 핵심 구성 요소**

- **요약(Summary)**: 이슈 제목
- **담당자(Assignee)**: 작업 책임자
- **우선순위(Priority)**: 작업의 중요도
- **컴포넌트(Component)**: 이슈가 속한 범주
- **상태(Status)**: 현재 진행 단계

**JIRA 티켓 작성 노하우**: 이슈 요약은 간결하게, (버그의 경우) 재현 경로는 상세하게 적는다.

##### | GitHub 사용 가이드

**Git**은 분산 소스 버전 관리 시스템이고, **GitHub/GitLab**은 그 Git 서비스를 제공하는 호스팅 웹 서비스다.

**Branch vs Fork — 둘 다 원본 저장소에 기여하는 방법**

| 방식 | 설명 |
|---|---|
| Branch | **원본 저장소 안에서** 분기를 나누어 작업 |
| Fork | 원본 저장소를 **복사한 독립된 저장소**에서 작업 |

> 💡 같은 조직·팀 안에서 협업할 때는 보통 Branch를, 외부 오픈소스 프로젝트에 기여할 때는 보통 Fork를 사용하는 경우가 많다.

##### PR과 코드리뷰

**브랜치 전략(Git Flow)의 대표적인 브랜치 종류**: `main`, `develop`, `feature`, `bugfix`, `hotfix`

> 💡 브랜치 전략에 정답은 없다. **팀의 상황과 필요에 맞게 운영**하는 것이 중요하다.

**실무 약속 예시**

- **브랜치 이름 규칙**: `종류/티켓번호-또는-작업내용` 형태로 통일
  - 로그인 기능 개발 → `feature/login` 또는 `feature/#12-login`
  - 결제창 버그 수정 → `bugfix/payment-error`
- **PR 규칙**
  - 모든 변경은 PR로 제출한다.
  - PR 템플릿을 사용해서 **어떤 작업인지, 왜 필요한지**를 설명한다.
  - PR은 **한 기능 단위**로 작게 쪼갠다.
- **Merge 조건**
  - 최소 1명 이상의 리뷰 승인
  - CI 빌드 통과
  - **Self-merge 금지** 룰 적용

**Pull Request란?**
특정 지점(브랜치)에 변경사항을 반영하도록 요청하는 것이다. Merge하기 전에 **충분한 토의와 코드리뷰를 거친 후** Pull Request를 Accept한다.

**코드리뷰**

> 💡 코드리뷰의 목적은 단순한 문법 지적이 아니라 **이해와 공유**다. 코드 품질 향상뿐 아니라, 지식 확산과 책임 분산이라는 효과도 함께 얻을 수 있다.

**리뷰 추천 표현**
- "이 부분에 대해 이렇게 생각해봤는데, 어떻게 생각하세요?"
- "이거 재사용 가능할 수도 있을 것 같아요. 함수로 뺄까요?"

> 💡 단정적으로 지적하기보다는, 질문과 제안 형태로 리뷰하는 편이 상대방이 방어적으로 반응하지 않고 논의를 이어가기 쉽다.

**검토 포인트**
- 로직의 정확성
- 코드 품질과 가독성
- 성능 고려사항
- 보안 취약점
- 테스트 커버리지
