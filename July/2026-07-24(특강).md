#### | 할루시네이션과 개발 속도

**할루시네이션이 발생하는 이유는 거의 하나다 — 요청에 대한 컨텍스트가 충분하지 않을 때**

**개발 속도는 왜 폭발적으로 빨라졌나 — 이제는 AI가 팀처럼 일한다**

```
기존 방식 → 보조형 AI → 코드 에이전트 → 하네스 방식
```

##### 요청 문장 하나의 차이

작업을 요청할 때 표현 방식이 결과 품질을 크게 좌우한다.

| 표현 | 평가 |
|---|---|
| "...보고서를 작성해줘" | ❌ |
| "...보고서로 작성하고자 합니다" | ⭕ |

→ 단순 명령형보다, **의도와 맥락을 함께 담은 문장**이 AI가 작업을 더 잘 수행하게 만든다.

---

#### | 엔지니어링의 초점 이동

```
프롬프트 엔지니어링 → 컨텍스트 엔지니어링 → 하네스 엔지니어링
```

| 단계 | 내용 |
|---|---|
| **1. 프롬프트 엔지니어링** | 좋은 질문을 만드는 단계 |
| **2. 컨텍스트 엔지니어링** | 정보, 규칙, 예시를 잘 넣는 단계 |
| **3. 하네스 엔지니어링** | 역할, 흐름, 검증을 설계하는 단계 |

> 💡 **중요한 것은 답 하나가 아니라, 오래 일할 수 있는 구조다.**

---

#### | AI는 왜 아직 "보조"에 머물렀나

1. 계속 지시해야 했다
2. 중간 품질을 직접 확인해야 했다
3. 긴 작업은 쉽게 흔들렸다
4. 모델은 좋아졌지만 운영 구조는 약했다

> 💬 **"핸들을 AI에게 넘겨주자"**

##### 에이전트가 오래 일하면 생기는 문제

| 문제 | 설명 |
|---|---|
| **맥락 소실** | 대화가 길어질수록 앞 내용을 놓치기 쉽다 |
| **중간 상태 누락** | 어디까지 했는지 기록이 없으면 다시 헤맨다 |
| **과한 한 번 시도** | 큰 일을 한 번에 끝내려다 중간에 무너진다 |
| **실수 누적** | 작은 오류가 이어지면 결과 품질이 떨어진다 |

> 💬 **"긴 작업에는 기억, 분해, 인계가 필요하다."**

---

#### | 하네스 기반 운영

**하네스의 핵심 구성 요소**

1. 세션 기록
2. 작업 분해
3. 도구 연결
4. 평가, 테스트
5. 실행 공간

> 💬 **"좋은 모델 위에 좋은 하네스를 얹어야 자율성이 길어진다."**

##### 코딩 에이전트에서 하네스가 특히 중요한 이유

일반적인 소프트웨어 개발 워크플로우 자체가 하네스가 관리해야 할 여러 단계로 이루어져 있기 때문이다.

```
요구사항 → 계획 → 코드 작성 → 테스트 → 수정, 제출
```

→ 한 명의 챗봇이 모든 걸 처리하는 게 아니라, **역할이 다른 에이전트들이 협업**한다 (멀티 에이전트). 이때 **점진적 로딩**을 통해 컨텍스트가 과도하게 쌓여 성능이 떨어지는 것을 방지한다.

---

#### | 단일 에이전트 vs 멀티 에이전트

**비유: 1인 주방 vs 역할형 주방**

| 구분 | 비유 | 특징 |
|---|---|---|
| **단일 에이전트** | 1인 주방 — 한 명이 주문, 준비, 조리, 검수까지 담당 | 소규모·반복 업무에 적합, 빠르고 경제적 |
| **멀티 에이전트** | 역할형 주방 — 주문·준비·조리·검수 역할을 나눔 | 확장형·복합 업무에 적합, 안정성과 확장성 확보. 단, 토큰 비용이 높음 |

---

#### | 컨텍스트 관리 = 재료 보관

**하네스 엔지니어링은 운영 전체를 설계한다.** 컨텍스트 관리는 요리에서 재료를 보관하는 것과 같다.

- **활성 문맥**과 **장기 보관**을 분리한다.
- 필요한 정보만 작업대에 올린다.
- 오래된 정보는 정리하고 핵심만 남긴다.
- 역할별로 필요한 문맥을 나눠준다.

##### Context Rot

**대규모 언어 모델(LLM)의 프롬프트가 길어질수록, 모델의 정확도와 추론 능력이 오히려 떨어지는 현상**

→ 컨텍스트를 무작정 많이 넣는 것이 능사가 아니라, 잘 정리해서 필요한 만큼만 유지하는 것이 중요하다는 걸 보여주는 개념이다.

> 📎 추천 에이전트 팀 구조는 강의 중 슬라이드 사진으로만 남겨서 노트에는 옮기지 못했다. 나중에 자료를 다시 확인해서 보충할 것.
> 📎 강사님이 GitHub에 공유하신 저장소: `revfactory/harness`

#### | 왜 하네스가 주목받나

**복잡한 업무를 팀 아키텍처로 바꾸는 방식** — 컨텍스트 분산, 역할 전문화, 재사용을 가능하게 한다.

##### 하네스 엔지니어링의 핵심 3요소

| 요소 | 역할 |
|---|---|
| **1. 에이전트** | 역할을 가진 실행 주체 |
| **2. 스킬** | 에이전트가 재사용하는 능력 |
| **3. 오케스트레이터** | 전체 흐름을 설계하고 조율 |

> 💬 **세 요소가 결합될 때, 반복 가능한 AI 협업 구조가 된다.**

##### 클로드 코드에서 에이전트란?

**역할을 가진 실행 주체**

##### 왜 스킬이 필요한가?

- 자주 쓰는 작업을 표준화한다.
- 에이전트가 같은 방식으로 실행하게 한다.
- 정확도와 일관성을 향상시킨다.

**스킬 적용 단계**

1. 마켓플레이스에 등록
2. 플러그인 설치와 리로드

#### | SubAgent vs Agent Team

| 구분 | 특징 |
|---|---|
| **1. SubAgent** | 메인 에이전트가 관리, 결과를 빠르게 회수, 집중형 단일 작업에 적합 |
| **2. Agent Team** | 팀원끼리 직접 메시지를 주고받고, 공유 작업 목록으로 조율, 논의·협업이 필요한 작업에 적합, 다만 토큰 비용이 더 클 수 있음 |

> 💡 **빠른 워커는 SubAgent, 협업 구조는 Agent Team.**
> 📎 클로드 코드 docs의 `agent-teams` 문서에 Agent Team 세팅 방식이 설명되어 있다.

> ⚠️ 강의 중 소개된 **6단계 구성 워크플로우**는 필기를 놓쳤다. 다음에 자료를 다시 확인해서 채워 넣을 것.

##### 6가지 팀 아키텍처 패턴

1. **Pipeline** — 순차 작업에 적합
2. **Fan-out/Fan-in** — 병렬 탐색 후 통합
3. **Expert Pool** — 전문가를 선택해 호출
4. **Producer-Reviewer** — 생성과 검수를 분리
5. **Supervisor** — 중앙에서 조정
6. **Hierarchical Delegation** — 상위 계획, 하위 실행으로 위임

> 📎 강사님이 GitHub에 공유하신 100가지 하네스 예시 저장소: `revfactory/harness-100`

#### | Dynamic Workflow

**반복 가동하는 에이전트 오케스트레이션의 설계와 운영.** 한 번의 요청을 **계획 → 실행 → 검증 → 통합**의 흐름으로 구조화하는 방식이다.

##### 품질을 높이는 패턴

1. 적대적 검증
2. 다양성 렌즈
3. 심사 패널
4. 고갈까지 반복

##### 피해야 할 안티 패턴

1. 단순 작업에 과투입
2. 사람 승인이 단계마다 필요
3. Barrier 남용
4. 검증 없는 대규모 실행

### 🗨️ 오늘의 회고

- 오늘은 실습 위주였던 지난주와 달리, 카카오에서 진행한 특강을 들으며 조금 다른 결의 하루를 보냈다. "수석 엔지니어는 AI에게 어떻게 일을 맡기는가"라는 주제였는데, 그동안 막연하게 "프롬프트를 잘 쓰면 되겠지"라고 생각했던 부분이 사실은 훨씬 더 큰 그림 — **프롬프트 엔지니어링 → 컨텍스트 엔지니어링 → 하네스 엔지니어링**으로 초점이 옮겨가고 있다는 걸 알게 된 게 가장 큰 수확이었다.
- 특히 "할루시네이션이 발생하는 이유는 거의 컨텍스트가 충분하지 않을 때 하나로 수렴한다"는 말이 인상 깊었다. 지금까지 AI를 쓸 때 결과가 이상하면 "모델이 별로다"라고 생각했는데, 사실은 내가 충분한 맥락을 안 줬을 가능성이 크다는 걸 다시 생각하게 됐다. "보고서를 작성해줘"와 "보고서로 작성하고자 합니다"라는 문장의 차이 하나로 결과 품질이 달라진다는 예시가 특히 와닿았다.
- 에이전트가 오래 일할수록 생기는 문제(맥락 소실, 중간 상태 누락, 과한 한 번 시도, 실수 누적)를 듣고 나니, 왜 최근 AI 도구들이 세션 기록이나 작업 분해 같은 기능을 강조하는지 이해가 됐다. "긴 작업에는 기억, 분해, 인계가 필요하다"는 문장이 오늘 강의를 한 줄로 요약해주는 느낌이었다.
- 단일 에이전트와 멀티 에이전트를 "1인 주방 vs 역할형 주방"에 비유한 부분도 쏙쏙 들어왔다. 지금 내가 쓰는 방식은 거의 1인 주방에 가까운데, 앞으로 복잡한 작업을 맡길 때는 Pipeline, Fan-out/Fan-in, Supervisor 같은 팀 아키텍처 패턴을 참고해볼 수 있겠다는 생각이 들었다.
- SubAgent와 Agent Team의 구분("빠른 워커는 SubAgent, 협업 구조는 Agent Team")도 실무에 바로 적용해볼 수 있는 기준이라 유용했다. 강사님이 공유해주신 `revfactory/harness`, `revfactory/harness-100` 저장소는 꼭 다시 찾아서 살펴봐야겠다.
- 다만 강의 중간에 슬라이드로만 지나간 "추천 에이전트 팀 구조"와 "6단계 구성 워크플로우", "문제 정의로 이동하는 인간의 일" 뒷부분은 필기를 놓쳐서 아쉬웠다. 자료를 다시 받을 수 있으면 이 부분들을 보충해서 노트를 완성해야겠다.
- Q&A에서 나온 "새로운 모델이 나오면 한계까지 몰아붙여 보라"는 조언도 실천해봐야겠다. 지금까지는 새로운 모델이 나와도 익숙한 방식으로만 써봤는데, 이전 모델이 못했던 작업을 의도적으로 시켜보면서 모델별 특성 차이를 직접 느껴보는 습관을 들여야겠다.
